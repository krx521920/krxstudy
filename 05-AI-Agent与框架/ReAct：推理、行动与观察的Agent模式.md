# ReAct：推理、行动与观察的Agent模式

> [!summary] 一句话解释
> **ReAct 将 Reasoning（推理）与 Acting（行动）结合，让大模型交替判断下一步、调用工具并读取真实结果，据此继续完成任务。它是智能体的一种工作模式，不是前端 React 库。**

## 一、React、ReAct 和 Relay 不是同一个东西

| 名称 | 所属领域 | 主要用途 |
|---|---|---|
| React | 用户界面开发 | 用组件和状态构建、更新界面 |
| ReAct | 大模型智能体 | 让推理与行动相互配合，根据环境反馈推进任务 |
| Relay | 前端数据管理 | 帮助 React 应用组织数据获取、缓存与更新 |

ReAct 的名称来自 **Reasoning + Acting**，也常写成 **Reason + Act**，中文可记为“推理＋行动”。读音可以近似记成“瑞艾克特”；只听读音不容易与 React 区分，因此要结合上下文。

通常用中间大写的 `A` 区分智能体模式 `ReAct` 与前端库 `React`。但文章或代码里可能全写小写，不能仅靠大小写判断：

- 提到组件、页面、按钮、状态，通常在讲 [[React组件化前端开发|React]]。
- 提到推理、工具、行动、观察和智能体，通常在讲 ReAct。
- 提到前端共享缓存和组件数据需求，可能在讲 [[Relay：React与GraphQL的数据管理|Relay]]。

ReAct 来自论文 *ReAct: Synergizing Reasoning and Acting in Language Models*，预印本首次发表于 2022-10-06；它不是“把前端 React 用到了智能体里”。[原始论文](https://arxiv.org/abs/2210.03629)、[React 官方介绍](https://react.dev/learn)、[Relay 官方介绍](https://relay.dev/docs/)

## 二、生活类比：带着问题查资料，再调整查找方向

假设你要确认一门课程该先读哪份讲义：

1. 先判断缺少哪些信息，例如课程主题和先修要求。
2. 去查看课程目录。
3. 发现其中引用了另一份基础材料。
4. 根据这个新信息，再去查看对应材料。
5. 信息足够后整理出学习顺序。

这里不是先凭空想出所有答案，也不是不管结果就机械地翻完所有文件，而是让“判断”与“查到的事实”相互影响。这是理解 ReAct 的生活类比，不表示模型具有人的意识或判断可靠性。

## 三、Thought、Action、Observation 分别是什么

经典教程常用三个词描述这个过程：

| 术语 | 中文含义 | 在系统中的作用 |
|---|---|---|
| Thought | 推理或当前判断 | 结合目标和已有信息，决定下一步要做什么 |
| Action | 行动 | 提出搜索、读取文件或查询记录等操作 |
| Observation | 观察结果 | 工具或环境实际返回的数据、错误或状态 |

简化顺序是：**判断下一步 → 执行行动 → 读取结果 → 调整下一步 → 必要时继续，最后回答或停止。**

原始研究强调把推理与行动交织起来，并不要求所有任务都机械地严格一对一排列；部分任务会在多个动作之间只穿插少量必要的推理。[作者项目说明](https://react-lm.github.io/)、[Google Research 原理介绍](https://research.google/blog/react-synergizing-reasoning-and-acting-in-language-models/)

这里的 Thought 是论文中的过程表达，不意味着应用必须展示模型全部内部思考。工程日志可以记录简要决策说明、工具请求、实际返回和验收结果；不要把生成出来的解释文字本身当成操作成功的证据。

## 四、具体例子：课程准备助手

任务：“根据下一节课的主题，告诉我需要提前读哪些材料。”

下面是假设已获授权、已配置查询工具的教学示例，结果是虚构的，不代表查询过真实课程。

| 步骤 | 对外可记录的操作摘要 | 假设工具返回的结果 |
|---|---|---|
| 1 | 查询下一节课的安排 | 下一节是课程 A，主题为网络基础 |
| 2 | 查询课程 A 的资料目录 | 找到主讲义，并标注需要先读材料 B |
| 3 | 读取材料 B 的说明 | 确认阅读范围和先修要求 |
| 4 | 根据已获得的资料生成准备清单 | 给出材料、阅读范围和依据 |

如果第二步找不到资料，系统可以重新检索、请求用户补充信息或停止，而不是假装已经读过。

**关键不是步骤数量多，而是后续操作会受到真实返回结果影响。** 几次模型调用全部按预先固定顺序执行，不会仅因为“多轮”就自动成为 ReAct。

## 五、为什么“模型说去查”不等于真的查了

大模型通常负责生成工具调用请求，外部运行程序才负责执行。中间至少要分清：

1. 模型提出行动请求。
2. 运行系统校验工具、参数和权限。
3. 获准的工具执行实际操作。
4. 将真实结果或错误交回模型。

只在回答中写一句“正在搜索”，却没有执行搜索工具，不能算完成了外部检索。只生成代码而没有运行，也不能据此声称测试通过。

这部分属于 [[Agent工具运行时：执行流水线、并发调度与Code Mode|工具运行系统]]；持续推进和停止的设计见 [[Prompt Engineering与Loop Engineering]]。

## 六、和 Agent、Dify、LangChain 的关系

- **Agent（智能体）**：围绕目标组织模型、工具和运行逻辑的一类系统。
- **ReAct**：可以用于组织智能体推理与行动的一种模式，不是所有智能体的唯一架构。
- **Dify**：搭建和运行应用的平台，可以提供 ReAct 等策略的具体实现。
- **LangChain**：通过代码组织模型与工具的框架，模式与框架不是同一层概念。

截至 2026-09-15，Dify 官方经典 Agent 节点文档明确列出 `ReAct (Reason + Act)` 策略；这是智能体运行策略，不是选择网页界面库。界面与可用策略应按实际版本核对。[Dify Agent 策略](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)

### 与 Function Calling 有什么关系

Function Calling（函数调用）描述模型怎样提出结构化的工具请求；ReAct 关注怎样把推理、行动和结果反馈组织起来。

概念上可以用结构化工具调用承载“推理—行动—观察”的交互。不过，某个产品可能把“经典文本式 ReAct”和“原生函数调用”包装成不同策略选项；应按该产品定义理解，不能把界面分类直接当作所有系统的理论边界。

### 与 RAG 有什么关系

RAG 是 **Retrieval-Augmented Generation，检索增强生成**，通常读作“rag”，指检索外部资料后辅助生成答案。

ReAct 的某次行动可以是检索资料，因此二者可以组合；但固定的“检索一次再回答”不必采用 ReAct，ReAct 的行动也不限于检索。详见 [[RAG、Naive RAG与GraphRAG]]。

## 七、不是新模型，也不是从零训练

ReAct 是方法，不是一个独立模型名称。原始研究展示了用提示词示例让已有模型执行这种模式，也探索了使用相关轨迹做微调；**采用 ReAct 并不要求从零训练大模型。** [原始研究说明](https://research.google/blog/react-synergizing-reasoning-and-acting-in-language-models/)

单纯把“你使用 ReAct”写进提示词，也不会自动获得工具、权限和可靠运行系统。这些仍需实际配置或开发。

## 八、常见误区与工程边界

- **误区：React 和 ReAct 是同一个技术。** 前者管界面，后者是一种智能体工作模式。
- **误区：ReAct 就是让模型多说一些分析。** 重点是结合真实行动结果继续推进，不是增加解释篇幅。
- **误区：用了工具就不会出错。** 工具可能失败，来源可能不可靠，模型也可能误读结果。
- **误区：所有 Agent 都必须采用 ReAct。** 它只是常见模式之一，实际系统可以组合多种方法。
- **误区：循环越久越好。** 可能反复调用同一工具、累积错误并增加成本。
- **误区：自主行动等于无限权限。** 访问控制、参数检查和高风险操作审批仍需可靠程序落实。

实际系统应设置次数、时间与费用上限，处理重复失败，保留工具结果，并定义完成和停止条件。这些是应用 ReAct 时的工程要求，不是原始论文名称自动提供的保证。

## 九、初学者怎么学

1. 先分清模型生成的文字与工具实际执行的操作。
2. 观察一个只读查询示例：每次工具结果怎样影响下一次请求。
3. 再检查失败情况：查不到、无权限、超时、信息矛盾时如何处理。
4. 最后学习工具调用格式、循环运行和验收；不必为了学 ReAct 先学前端 React。

记忆口诀：**React 做界面；ReAct 用“推理＋行动＋反馈”推进任务；Relay 管前端数据。**
