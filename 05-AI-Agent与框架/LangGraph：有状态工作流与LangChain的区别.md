# LangGraph：有状态工作流与LangChain的区别

## 一句话解释

**LangChain 提供较高层的模型、工具和智能体开发组件；LangGraph 提供更底层的流程编排与运行能力，让开发者显式控制步骤、分支、循环和任务状态。**

两者属于同一生态，但不是旧版与新版、前端与后端，也不是必须二选一。截至 2026-09-16，LangChain 的 Agent（智能体）构建在 LangGraph 之上；LangGraph 则可以不使用 LangChain 的高层组件，直接连接模型或普通业务代码。[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

## 名字怎么读，分别是什么

- **LangChain**：近似读“兰格切恩”，名称可从 Language（语言）和 Chain（链）理解。它是开发框架，不是大模型。
- **LangGraph**：近似读“兰格格拉夫”，Graph 是“图”，这里指节点与连接关系组成的流程结构，不是图片。
- **LLM = Large Language Model，大语言模型**，逐字母读 L-L-M：负责理解输入并生成文字或行动请求。

“框架”可以理解为开发者拿来组织代码的现成骨架和组件。“编排”则是规定多个步骤怎样配合：先做什么，什么条件下换路，失败后回哪里，什么时候停止。

注意：**LangChain 不只能写直线流程，LangGraph 也不是专门画流程图的软件。**名字中的 Chain 与 Graph 不能直接当作功能限制。

## 生活类比：现成办事助手与自定义办事流程

假设你要组织课程运营：查课表、写通知、请讲师确认、发布通知。

LangChain 像一套现成的办事组件和通用助手：你提供模型、工具和要求，就能先得到一个可工作的助手。

LangGraph 更像可以亲自设定的办事流程系统：你明确规定必须先核对课表，通知必须经人确认，未通过就修改，确认通过才能发布，而且中途退出后应能找回进度。

这只是理解分工的类比：LangChain 也支持定制、中间件和人工介入；区别是使用它提供的高层结构，还是进一步直接定义底层执行结构。

## Agent 的 Workflow 主要做什么

**Workflow（工作流）**近似读“沃克弗洛”，不是英文缩写，指把任务的处理步骤、数据流转和执行规则组织起来。**Agent（智能体）**近似读“诶真特”。

一句话：**工作流安排任务怎样推进，智能体可以在其中承担需要自主判断的部分；工作流运行引擎再按定义执行和管理过程。**这不是 LangGraph 独有的概念，Mastra、Dify 和普通业务程序也可以组织工作流。

要区分三个东西：写在纸上的流程是设计，代码或画布中的流程定义是可执行描述，运行引擎才负责实际调用步骤。画出流程图不等于已经实现权限、数据库和失败恢复。

### 工作流与智能体：主要区别在谁决定下一步

- **显式工作流**：开发者预先规定主要路径和允许的分支，例如“先查询，再生成，审批通过后发布”。有条件、有循环，也可以仍然是预设工作流。
- **智能体**：在目标、工具和权限边界内，让模型根据当前结果选择下一步，例如决定先查哪份讲义、是否继续搜索、是否向用户追问。
- **组合方式**：外层是严格业务流程，内层某一步交给 Agent 自主完成；也可以由 Agent 调用一个已经定义好的工作流作为工具。

“Agent Workflow”在不同产品和文章里用法不完全一致，有时泛指智能体的整个执行过程。判断时要看实际控制权，不能只看名称。[LangGraph 对工作流和智能体的区分](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

### 常见的八类职责

下表描述工作流系统常承担的职责；有的由框架提供机制，有的要接存储、日志系统或自行编写业务代码，并不是所有名叫 Workflow 的工具都自动具备全部能力。

| 职责 | 通俗解释 | 课程助手里的例子 |
| --- | --- | --- |
| 组织步骤与调用 | 安排先后顺序，并调用模型、工具或普通代码 | 先查真实课表，再根据结果写通知 |
| 传递与检查数据 | 明确每一步吃什么数据、输出什么结果 | 把课程日期、标题交给写作步骤；缺日期则暂停补全 |
| 路由、并行与汇总 | 根据条件选择路线；独立任务可以同时做后汇合 | 课程问题走讲义检索，订单问题走订单查询；同时查讲师和课程简介 |
| 循环、校验与退出 | 不合格就修改，但设定次数、时间和停止条件 | 草稿缺少日期则返工；超过修改上限则交人处理 |
| 状态保存与恢复 | 记录任务做到哪里，必要时在之后继续 | 保存草稿及审核状态，讲师次日批准后继续处理 |
| 人工确认与规则约束 | 在有后果的操作前设置必须通过的关卡 | 只有具备权限的人批准对应版本后，才允许发布 |
| 异常处理 | 对失败决定重试、换路、停止或交人工 | 查询超时可有限重试；权限不足则停止，不能重试绕过 |
| 运行追踪与资源约束 | 记录实际路径、耗时、调用次数等，配合限制 | 看出卡在资料查询还是模型生成，并限制总运行时间和调用次数 |

串行、分支、并行和循环属于常见控制方式；具体能力可参考 [Mastra 流程控制](https://mastra.ai/docs/workflows/control-flow)。运行追踪可以借助 [Studio 等配套工具](https://mastra.ai/docs/studio/overview)，预算限制则需要按应用需求落实，不能假定画出节点就自动生效。

### 用“准备一份课程通知”把职责串起来

假设用户提出：“整理下周课程，写一份通知，讲师批准后再发给学员。”这是教学示例，不代表本次真的发送消息。

1. **接收与检查**：确认哪门课、哪一周、准备发给谁；缺信息时先补全。
2. **获取真实资料**：用有权限的查询工具获取课表和讲师信息，不让模型凭空编日期。
3. **生成草稿**：将相关资料交给模型或写作 Agent，形成通知。
4. **检查结果**：普通代码检查必要字段；必要时用模型协助检查表达，但模型自评不能作为事实正确的唯一证据。
5. **等待审核**：保存任务编号、草稿版本和当前状态，等待有权限的人批准、拒绝或提出修改。
6. **按决定继续**：要求修改则返回草稿步骤；取消则结束；批准才进入发布步骤。
7. **实际发布与核验**：调用发布服务，记录它真实返回的结果；失败则执行预先设计的处理策略。

这里查询、字段检查、保存状态和发送通知，都可以由普通代码完成；**不是每个步骤都要调用模型，更不是每个节点都要配置一个 Agent。**多个节点也可以共用同一个模型。

流程形状和 LangChain、LangGraph 的合作方式，见下文“同一个项目里，两者怎样合作”。实际工具执行边界另见 [[Agent工具运行时：执行流水线、并发调度与Code Mode]]。

### 为什么不是写一句“按步骤做”就够了

提示词可以要求模型先检查再回答，但它主要影响模型生成的内容或行动建议。工作流可以把要求变成程序能检查的执行条件，例如：

- 审核状态不是“已批准”，就不调用发布工具。
- 批准对应的是草稿第 2 版，草稿变成第 3 版后不能直接沿用批准。
- 循环次数超过上限，就停止而不是无限调用模型。
- 数据不完整，转入补全或人工处理，不悄悄编造字段继续执行。

关键权限仍应由服务端和真实业务工具校验，不能信任模型自己输出“用户已批准”。这也是 [[Prompt Engineering与Loop Engineering]] 与 [[Agent Harness：模型之外的运行系统]] 的相关边界。

### 状态、重试和恢复不是魔法

状态可以包含“资料、草稿、审核结果、重试次数”；它不等于把所有历史对话都塞给模型。任务状态需要保存，传给模型的上下文则应按步骤挑选。

要跨进程重启恢复，需要合适的持久化存储。只保存在内存里并不足够。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

重试也有业务后果：查询课表超时后可以考虑重试，但发通知、改订单等操作可能已经成功，只是回复丢失。应先核查结果，结合 [[状态机与幂等性|幂等性]] 处理，不能简单全部重跑。

不同框架恢复时重跑的范围不同。例如 LangGraph 中断恢复可能重新执行节点内前面的代码，详见下文“有存档，不等于绝不会重复操作”。[LangGraph 中断](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Mastra 错误处理](https://mastra.ai/docs/workflows/error-handling)

### 除了课程通知，还常用于哪些任务

- **知识库问答**：检查访问权限 → 检索资料 → 组织上下文 → 生成带依据的回答 → 检查格式与引用；没有足够依据时说明不足。
- **资料整理**：读取文件 → 抽取内容 → 分类 → 生成摘要 → 人工确认 → 保存到指定位置。
- **客服处理**：识别问题类型 → 查询相关记录 → 回答或转人工；需要修改数据时再走授权步骤。
- **软件开发助手**：理解需求 → 修改代码 → 执行测试 → 检查结果 → 有界修复循环 → 请求合并或发布审批。

这些是典型设计例子，不意味着使用框架后自动拥有上述业务能力。实际权限、数据源和验收规则都要单独提供。

### 什么时候不需要复杂工作流

如果任务只是改写一句话、翻译一段短文，单次模型调用可能足够。少量条件和几步固定操作，也可以用普通程序实现，不必为了叫“智能体”而拆出很多节点。

当任务出现多步骤依赖、不同路径、人工等待、失败重试或审计需求时，显式工作流的价值才更明显。额外节点和模型调用也可能增加延迟、费用和维护难度。

学习时可以先写出“输入是什么、步骤是什么、每步输出什么、失败怎么办、何时结束”，再选择 [[Mastra：TypeScript智能体框架与LangChain、LangGraph对比|代码框架]] 或 [[Dify：可视化AI应用、知识库与工作流平台|可视化平台]]。

记忆句：**模型负责理解与生成，工具负责实际操作，工作流负责把这些能力按规则连接和推进；整个系统是否安全可靠，仍取决于具体实现与验证。**

## LangChain 主要帮你做什么

[[LangChain]] 常用于统一模型调用、定义工具、组织提示词，以及创建智能体的工作循环。

例如做一个“课程问答助手”：

1. 用户问：“下周有什么课程？”
2. 模型根据问题选择查询课程工具。
3. 程序执行查询，把结果交回模型。
4. 模型整理课程信息，回复用户。

LangChain 的 `create_agent` 提供了构建这类智能体的高层入口；开发者仍需要提供真实工具、配置模型并处理业务权限。它不是装好后就自动拥有公司数据。

如果这类模型与工具的循环已经符合需求，通常不必一开始就手工定义完整的图。

## LangGraph 里的三个核心概念

通过图式接口构建流程时，先认识 **State（状态）、Node（节点）和 Edge（边）**。[官方图接口说明](https://docs.langchain.com/oss/python/langgraph/graph-api)

### 1. State：这项任务目前知道什么、做到了哪里

状态是任务运行期间保存的一组数据，可以同时包含原始输入、查询结果、草稿、人工决定和执行记录。例如：

```text
课程日期：下周二
已查到的课表：……
通知草稿：……
人工审核结果：尚未审核
修改次数：1
发布结果：尚未发布
```

它不是模型参数，也不只是一段聊天记录。哪些字段需要存在、怎样更新和合并，由开发者设计；并行步骤同时写入数据时，还需要明确合并规则。

### 2. Node：这一步实际做什么

节点通常是一段函数，即完成某项操作的代码。例如：查询课表、生成草稿、核对日期、收集人工意见、发布通知。

节点可以调用模型，也可以只是普通代码。**一个节点不等于一个模型，也不等于一个智能体。**有需要时，节点内部还可以调用一个用 LangChain 创建的完整智能体。

### 3. Edge：这一步之后去哪里

边决定步骤之间如何连接：

- 固定连接：查询课表后生成草稿。
- 条件分支：审核通过则发布，未通过则修改或结束。
- 循环：修改后再次审核，但必须设置退出条件。

路线可以由明确的代码条件决定，也可以参考模型判断；关键业务规则不必全部交给模型猜测。

## 同一个项目里，两者怎样合作

下面是课程通知系统的教学设计示例，不代表正在查询课表或发布消息：

```text
收到“准备下周课程通知”的请求
    ↓
查询并核对课表
    ↓
调用写作助手生成草稿 ←────────┐
    ↓                        │
等待讲师审核                  │
    ├─要求修改 → 记录修改意见 ─┘
    ├─取消或达到修改上限 → 结束
    └─批准 → 发布已批准的版本 → 记录结果 → 结束
```

在这个设计中：

- **LangChain** 可以用于构建“查资料并生成草稿”的助手。
- **LangGraph** 可以负责外层审核路线、当前任务状态，以及暂停和恢复。
- **模型** 负责理解要求、生成草稿等需要语言能力的部分。
- **业务工具和服务** 负责真实查询与发布，并落实访问权限。

这是组合方式之一，不是固定分层：你也可以直接在 LangGraph 节点里调用模型厂商的接口，不使用 LangChain 高层智能体。

## 为什么“暂停和恢复”值得专门设计

用户或讲师可能半小时以后才审核，也可能应用重启后才继续。此时，不能只依赖一次函数调用里的临时变量。

LangGraph 的 **Checkpoint（检查点）**可以理解为任务的“进度存档”；**Checkpointer（检查点保存组件）**负责保存和读取这类记录。通常还需要任务会话标识，让系统找到正确的那份进度。

需要区分：

- **Checkpointer**：主要保存某个任务会话的图状态，帮助继续对话、恢复运行。
- **Store（存储组件）**：保存应用定义的跨会话信息，例如用户偏好。

两者不是模型的无限记忆，也不会自动把所有历史都塞进模型输入。[官方持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

真实部署还要配置合适的存储方式。仅保存在程序内存里的教学示例，不能保证进程退出后仍然保留进度。

### 有存档，不等于绝不会重复操作

LangGraph 可以通过 `interrupt()` 暂停等待人工输入。但恢复时，触发中断的节点会从函数开头重新执行，并不是把整台程序冻结后从同一行无缝继续。因此，中断之前的操作可能再次发生。[官方中断说明](https://docs.langchain.com/oss/python/langgraph/interrupts)

例如“发布通知”不能在重复运行后发出多份。开发者仍要设计 [[状态机与幂等性|幂等性]]：让同一次业务操作被重复请求时，不产生不应重复的结果。可以结合唯一业务编号、发布状态核对和服务端去重等措施，不能只靠模型记得“不要重复”。

同样，人工批准必须来自正确用户，并对应正确的内容版本；若草稿变了，应按业务规则重新确认。流程图中的一个“审核节点”不会自动解决身份、授权和数据安全问题。

## 和 Harness 的关系

[[Agent Harness：模型之外的运行系统|Harness]] 是围绕模型的运行支撑系统这一通用概念。

- LangChain 的 Agent 组件提供可配置的 Harness 能力。
- LangGraph 提供流程与状态运行基础，可以用来构建或定制 Harness。
- 应用仍要装配实际工具、权限、数据、预算、日志和验收规则。

因此，不是“Harness、LangChain、LangGraph 三选一”，而是“这个系统使用哪些组件来实现 Harness”。

## 对照与选择

| 问题 | LangChain | 直接使用 LangGraph |
| --- | --- | --- |
| 主要关注 | 快速组合模型、工具与智能体能力 | 明确设计执行路径和状态变化 |
| 常见开发入口 | 配置高层组件、`create_agent` 和中间件 | 定义状态、节点、连接及运行配置 |
| 流程控制 | 在预建架构基础上定制 | 更直接地控制分支、循环、并行和子流程 |
| 状态与人工介入 | 也支持，Agent 底层利用 LangGraph | 可以更细致地设计这些能力 |
| 代价 | 需要理解高层抽象及其扩展方式 | 需要承担更多流程、状态和恢复设计 |

作为初学者，可以按实际需求逐步选择：

1. **只需一次模型调用**：直接调用模型服务即可，不一定需要两者中的任何一个。
2. **需要模型自主选择几个工具**：先理解并尝试 LangChain 的通用智能体结构。
3. **需要特别安排审核、回退、并行分支和长任务恢复**：再评估是否直接使用 LangGraph。
4. **既有通用助手，又有严格业务流程**：两者可以组合，也可以选择其他实现方式。

不要因为流程有一个分支就认为必须引入 LangGraph；少量普通代码也能实现简单流程。框架的价值应当大于新增的学习、测试与维护成本。

## 加入 Mastra 后怎样比较

Mastra 是以 TypeScript 为中心的整合式智能体应用框架，也提供工作流、分支、循环、暂停恢复和开发工作台，不能简单当成“只能做轻量聊天的 LangChain 替代品”。LangChain 和 LangGraph 同样有 JavaScript/TypeScript 版本，因此区别不只是语言。

这里比较的是不同开发结构与职责范围，不是“Mastra 与 LangGraph 谁必然更强”。完整对照、同一课程通知案例和迁移注意事项见 [[Mastra：TypeScript智能体框架与LangChain、LangGraph对比]]，核对日期为 2026-09-16。

## 常见误区

- **“LangGraph 取代了 LangChain。”** 它们职责不同，当前 LangChain Agent 就使用 LangGraph 作为底层。
- **“LangChain 只能串行，LangGraph 才能循环。”** LangChain 的智能体也能循环使用工具；LangGraph 让流程结构更直接可控。
- **“LangGraph 的 Graph 就是知识图谱。”** 这里主要是执行流程图；与 [[RAG、Naive RAG与GraphRAG|GraphRAG 中的知识图谱]] 不是同一个用途。
- **“LangGraph 自带一个更聪明的模型。”** 两者都不是模型；更好的流程可以改善系统表现，但不等于模型参数变强。
- **“用了 LangGraph 就不会失败。”** 工具错误、模型错误、无限循环、权限和重复执行仍需要开发者处理。
