# Agent Harness：模型之外的运行系统

## 一句话解释

**Agent Harness 是围绕大模型的一套运行支撑软件与配置：它组织输入、协调工具执行、管理任务状态，并控制任务怎样继续、暂停和结束。**

这里的 Agent 指“智能体”，即能围绕目标选择行动并根据结果继续工作的系统。Harness 不是另一个大模型，也不是某种编程语言。

截至 2026-09-16，[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview)用 `Agent = Model + Harness` 帮助理解两者关系。这是一个有用的简化，不是全行业必须遵守的严格公式；不同项目对 Harness 的范围和自带功能有不同划分。

## Harness 这个词到底是什么意思

Harness 是普通英文单词，不是缩写，读音约为“哈尼斯”，美式音标 `/ˈhɑːrnɪs/`。本义包括马具、安全带等约束、连接和支撑用的装备。

在软件工程里，可以先理解成：**让某个核心部件在特定条件下运行起来的配套装置。**

- **Test Harness（测试支撑系统）**：组织测试输入、运行被测程序、检查结果。
- **Evaluation Harness（评测支撑系统）**：统一组织模型评测任务、模型调用和评分。例如 [EleutherAI 的语言模型评测项目](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/README.md)。
- **Agent Harness（智能体运行支撑系统）**：让模型能够在工具和环境中持续开展任务。

因此，看到 Harness 先问“给谁配套、用来做什么”。不能看到这个词就认定它一定是智能体，也不能把它当成某家公司独有的概念。

## 生活类比：聪明的顾问与实际办公系统

假设请来一位很会分析问题的顾问，但他暂时只能收到你递给他的材料，再交回一份建议。

他说“应该查看课程安排”，不等于课程安排已经查到了。他说“应该更新文档”，也不等于文档真的改好了。

还需要一套办公系统负责：

- 把有关材料递给他，而不是把所有文件一股脑塞过去；
- 提供查文件、改文件等实际办事工具；
- 检查哪些资料可以查、哪些操作需要批准；
- 把办事结果交还给他，让他决定下一步；
- 记录进度，防止重复工作或忘记未完成事项。

类比中，顾问对应模型；围绕顾问运作的办公系统对应 Harness。**工具是具体办事的程序，Harness 负责组织和协调它们。**实际项目也可能把工具代码直接包含在 Harness 内部，两者不是必须分开部署。

## 为什么模型本身不够

**LLM = Large Language Model，大语言模型，通常逐字母读 L-L-M。**它接收输入，生成文字，或者生成带有工具名称和参数的“工具调用请求”。

例如，模型输出以下内容：

```text
工具：read_file
参数：课程安排.md
```

这只是示意性的请求格式，意思是“请使用读取文件工具，读取指定文件”。**它不是已经执行成功的证据，也不会凭这几个字自动获得文件权限。**

真正读取文件，需要外部程序解释这个请求、找到对应工具，并在实际权限允许的条件下执行。执行可能成功，也可能因为文件不存在或无权访问而失败。模型需要收到这个真实结果，才能据此继续工作。[LangChain 的 Agent 文档](https://docs.langchain.com/oss/python/langchain/agents)将工具、提示词及影响运行行为的中间件放在 Harness 范围内。

## 一个完整例子：查课表，再修改课程说明

以下是教学示例，不代表正在读取或修改实际课程文件。

用户要求：“查看课程安排，把课程说明里的时间改成一致的时间。”

1. **准备输入**：Harness 组织用户要求、可用工具说明，以及必要的历史消息，交给模型。
2. **提出行动**：模型根据当前信息，请求读取课程安排和课程说明。
3. **检查并执行**：Harness 按实现中的规则检查工具、参数、路径及授权；允许后由读取工具取得内容。
4. **交回结果**：Harness 把文件内容或真实错误加入当前任务的上下文，再次调用模型。上下文就是模型本次能够看到的输入材料。
5. **提出修改**：模型比较时间后，生成修改内容或编辑工具请求；Harness 根据权限和审批规则协调编辑。
6. **核验结果**：工具重新读取修改后的文件，或运行检查；若发现改错或失败，结果继续交回模型处理。
7. **结束或暂停**：符合停止条件就返回结果；需要用户选择、权限不足、超时或达到预算上限时，则暂停或结束，不无限循环。

最值得记住的区别是：

> 模型提出行动 → Harness 协调并约束执行 → 工具与环境产生真实结果 → Harness 将结果交回模型。

不是所有任务都需要走很多轮；模型也可能不调用工具，直接给出答案。

## Harness 具体有哪些东西

下面是常见设计能力，不是每个 Harness 都默认具备的清单。

| 能力 | 负责什么 | 缺少时可能怎样 |
| --- | --- | --- |
| 输入与上下文管理 | 选择材料、装配提示词、控制输入长度 | 关键文件没给到模型，或者无关信息太多 |
| 工具接入与调度 | 提供工具说明、分发请求、接收结果 | 模型只能提出建议，不能实际操作 |
| 工作循环 | 控制何时调用模型、等待工具和继续下一步 | 工具执行完了，但没人把结果交回模型 |
| 权限与审批接入 | 限制可访问范围，必要时等待人工批准 | 请求越权执行，或把建议误当授权 |
| 状态保存与恢复 | 保存进度、结果和未完成事项 | 任务中断后重做，或遗漏剩余工作 |
| 失败与预算控制 | 处理超时、取消、重试和调用次数限制 | 一直重试、费用上涨，或无法停止 |
| 记录与验收 | 留下行动记录，运行检查或接入人工验收 | 无法解释失败原因，或把“说完成”当成完成 |

这些能力可以写在一个小程序里，也可以分散在多个模块和服务中。并不要求必须有插件系统、图形界面或多个智能体。

### 权限不能只靠提示词

“请不要删除文件”是一条行为要求，不是操作系统级的禁止删除机制。可靠的限制还要靠工具实现、账户权限、允许访问的路径、审批规则或沙箱等落实。沙箱指限制程序可以接触哪些资源的隔离环境。

网页、文件和工具返回的数据也不能因为进入上下文，就自动升级为用户指令。安全边界需要实际执行和检查，而不是给系统起名 Harness 就自然存在。

### 状态保存不等于无限记忆

长任务可以把进度写入文件或数据库，再在下一轮读取相关部分。这不表示模型一次能看到无限信息，也不表示记录已经进入模型参数。

[Anthropic 的长任务 Harness 工程文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)展示了利用进度记录、任务清单和实际测试衔接多次工作会话的做法。这是一种实现案例，不是所有 Harness 的固定结构。

## 和刚学过的概念怎样区分

| 概念 | 主要回答的问题 | 与 Harness 的关系 |
| --- | --- | --- |
| 大模型 | 如何理解输入并生成答案或行动请求？ | 是 Harness 调用的核心能力 |
| Prompt（提示词） | 这次告诉模型什么要求？ | 是输入的一部分，不负责实际执行全部工作 |
| ReAct | 怎样交替进行推理、行动和观察？ | 是工作模式，可以由 Harness 支持；不是整个运行系统 |
| Agent（智能体） | 哪个完整系统围绕目标开展工作？ | 通常由模型与运行支撑、工具等共同组成 |
| LangChain | 用什么开发组件组织模型应用？ | 其 Agent 组件提供可配置的 Harness 能力 |
| LangGraph | 怎样显式安排步骤、分支和状态变化？ | 提供构建和定制 Harness 所需的流程编排与运行基础 |
| Dify | 在什么平台搭建、配置和运行应用？ | 是更完整的应用平台，内部有智能体运行能力，不只是一个循环 |
| MCP | 不同程序怎样以统一方式交换上下文、连接工具？ | 是 Harness 可以使用的接入协议，不是完整任务运行系统 |

**ReAct = Reasoning + Acting，推理与行动，读法类似“react”。**它与制作网页界面的 React 是不同概念，详见 [[ReAct：推理、行动与观察的Agent模式]]。

**MCP = Model Context Protocol，模型上下文协议，逐字母读 M-C-P。**[MCP 官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)明确区分了协议与应用如何使用模型、管理上下文；因此“接上 MCP”并不等于完整实现了 Harness。

框架、运行时和 Harness 这些称呼会有重叠：框架强调供开发者使用的组织方式，运行时强调执行期间的支撑，Harness 强调围绕核心能力的配套。不要把它们当成处处互斥的产品类别。

两者怎样组合，以及为什么 LangChain Agent 本身就使用 LangGraph，详见 [[LangGraph：有状态工作流与LangChain的区别]]。

## Harness Engineering 又是什么

Harness Engineering 可以理解为“运行支撑系统的工程设计与优化”。在智能体语境下，它不仅问提示词怎么写，还会问：

- 每轮应提供哪些材料和工具？
- 哪些操作可自动执行，哪些要人批准？
- 失败后是否重试，如何避免重复修改或重复发送？
- 怎样保留进度，怎样判断真正完成？
- 怎样在准确性、延迟和费用之间取舍？

它通常与提示词工程、上下文工程、循环设计有交集，不是突然出现的另一种模型训练方法。可结合 [[Prompt Engineering与Loop Engineering]]、[[状态机与幂等性]] 理解。

## 常见误区

1. **“Harness 就是一段很长的提示词。”** 提示词可以是其中一部分，但不能代替实际执行、状态保存和权限控制。
2. **“Harness 就是某家的模型或产品。”** Harness 是通用词；项目名中的 Harness 表示该项目承担这类作用。具体项目另见 [[DeepSeek Harness、Everything is a Plugin与Cordis]]，其实现细节以该笔记的核对日期为准。
3. **“换 Harness 就是重新训练模型。”** 通常不是。模型参数不变，也可能因输入材料、工具和运行规则变化而表现不同。
4. **“模型外部就是我的服务器外部。”** 不是。“外部”指模型本体之外的软件层；它可以运行在本机、内网或云端。数据是否离开本机，要看模型、工具和存储的实际调用地址。
5. **“功能越多就一定越好。”** 工具越多，权限和错误路径也可能越复杂；应按任务需要选择。
6. **“运行完一轮就代表任务成功。”** 停止运行与通过验收是两回事；工具返回成功也未必证明业务目标完成。

先不背框架名称，用一个简单任务回答四个问题：**模型收到什么？工具实际做了什么？谁决定能不能做？结果怎样进入下一轮？**能解释这四点，就掌握了 Harness 的核心。
