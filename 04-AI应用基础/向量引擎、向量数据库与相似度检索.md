# 向量引擎、向量数据库与相似度检索

## 一句话解释

**向量引擎是专门根据“数字表示的相似程度”查找内容的软件组件；在知识库里，常用它来寻找意思相关、但用词不一定相同的资料。**

这里按 AI（Artificial Intelligence，人工智能，读作字母 A-I）知识库的语境，解释 Vector Search Engine（向量搜索引擎，简称向量引擎）。这个词不是某一个产品的专有名称；硬件中的向量计算引擎、数据库中的向量化执行引擎是另外的概念。

先记住：它擅长“找相似项”，不是直接“写答案”，也不等于训练大模型。[原理参考：Qdrant 官方介绍](https://qdrant.tech/documentation/overview/vector-search/)

## 一、先从一个搜索例子理解

假设笔记里写着：**账号密码重置步骤**。

你搜索的是：**忘记密码怎么办？**

- 简单关键词搜索主要看字词是否匹配，可能借助共同的“密码”找到它。
- 向量检索还尝试利用内容特征，把“忘记密码”“重置登录凭据”等不同表达联系起来。
- 即使没有完全相同的关键词，也有机会找到相关资料；但不保证每次找对。

生活类比：你向图书管理员描述“我想学让电脑同时处理很多事情”，他可能指向“并发与多线程”书架，而不只寻找书名里有没有“同时处理”。

注意这个类比有边界：真正的软件不是一个理解万事的管理员，而是利用模型生成的数字表示进行比较。[参考：Sentence Transformers 语义搜索说明](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

## 二、“向量”究竟是什么

在这里，Vector（向量）可以先理解成**一组按固定顺序排列的数字**，例如 `[0.2, -0.6, 0.8]`。

这只是格式示意，不是对上面那句话实际计算得到的结果。三个数字是三维；实际文本模型可能输出数百或数千个数字，具体取决于模型。

Embedding（嵌入，读音近似“因贝丁”）模型把文字、图片等内容转换成这种数字表示，供后续比较。可以把它想成“内容在某张特征地图上的坐标”。

需要分清：

- 通常不能把每一维直接解释为“第一位代表编程，第二位代表网络”。
- 向量不是全文的无损压缩包，不能指望把它直接解码回完整原文。
- 问题与资料必须被编码到**相互兼容的向量空间**。两个模型都输出同样多的数字，不代表它们的向量能直接混用；应按模型要求分别处理查询和文档。
- 不是维度越多就一定越好，也不是数字越大就越相关。

[参考：Qdrant 向量说明](https://qdrant.tech/documentation/manage-data/vectors/)、[查询与文档编码的区别](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

## 三、模型、索引、引擎和数据库各做什么

| 名称 | 主要职责 | 类比 |
| --- | --- | --- |
| Embedding 模型 | 把内容转成适合比较的向量 | 给资料标注“特征坐标” |
| 向量索引 | 组织向量，让搜索更高效 | 提前整理查找路线 |
| 向量引擎 | 执行相似度检索，返回候选项和分数等 | 负责查找的机器 |
| 向量数据库 | 在检索之外管理数据保存、更新、查询等 | 带管理系统的资料仓库 |
| 生成式大语言模型 | 阅读取回的原文，并组织回答 | 根据资料写说明的人 |

这是职责划分，不是要求部署五套软件。产品可能把多种能力集成在一起；“引擎”和“数据库”在产品介绍中也常有重叠。

向量数据库通常会关联资料标识、来源、正文或正文位置、日期等信息；如果只保存一串数字而没有来源关联，就不便把搜索结果展示为原文。

## 四、放进你的 Obsidian，会怎样工作

以下是示意流程，**不是说当前仓库已经部署了这些服务**。

### 准备资料时

1. 读取选定的笔记，例如“多线程”“网络代理”“Celery”。
2. 长笔记按段落或小节切分，避免一篇文章混合过多主题。
3. 用 Embedding 模型为每个片段生成向量。
4. 保存向量，并关联片段原文、文件路径、标题和更新时间。
5. 按规模和需求建立向量索引。

### 你提问时

1. 例如提问：“耗时任务怎么放到后台做？”
2. 用兼容的查询编码方式生成问题向量。
3. 向量引擎找出相似的候选片段，可能包括 [[Celery分布式任务队列]] 和 [[进程、线程、多进程与多线程]] 的内容。
4. 系统根据候选项取回原文，展示结果；也可以交给大语言模型整理答案。

“可能包括”只是教学示例，不是已经运行得到的搜索结果。实际命中情况需要测试。

笔记更新后，对应片段和索引也要更新；删除或收回权限的内容不能继续作为可用资料返回。仅把文件提交到 GitHub，不会自动完成向量化和索引同步。

## 五、它和 RAG 是什么关系

RAG 是 **Retrieval-Augmented Generation（检索增强生成，常读作“rag”）**，意思是先查资料，再让模型根据资料回答。

可以用一条简化流程记忆：

**问题 → 生成查询向量 → 检索候选项 → 取回相关原文 → 大语言模型组织答案。**

- 向量引擎负责其中的“找资料”环节，不是整套 RAG。
- 通常给回答模型看的是取回的文字片段，不是直接塞一堆检索向量。
- 新增笔记并建立向量索引，通常不等于重新训练回答模型。
- 不接回答模型，也可以只做“相似笔记搜索”。
- RAG 也能使用关键词、结构化查询或图检索，不是必须依赖向量数据库。

继续阅读 [[RAG、Naive RAG与GraphRAG]]；不要把“会搜索”与“答案一定正确”混为一谈。

## 六、为什么还需要专门的引擎和索引

少量向量可以逐条比较；向量越来越多时，每次全部比较会增加计算量。

一种选择是 **ANN（Approximate Nearest Neighbor，近似最近邻，读作字母 A-N-N）检索**：借助索引减少需要比较的候选项，用一定的漏检风险换取速度或资源节省。

例如 **HNSW（Hierarchical Navigable Small World，分层可导航小世界，读作字母 H-N-S-W）**，用多层图结构帮助寻找附近向量。这里的“图”是向量间的导航结构，不等于 GraphRAG 中的实体关系知识图谱。

- 精确最近邻：按选定的距离规则找到真正排在前面的向量。
- 近似最近邻：尽量快速找到靠前的向量，但可能漏掉一些。
- **即便距离排名完全精确，也不代表找出的资料能回答问题**，因为数字相似度本身只是相关性的线索。

常见比较规则包括余弦相似度、欧氏距离和内积。初学时先知道：它们是不同的“怎么算像”规则，应与模型匹配；分数不是答案正确率。[参考：Faiss 官方文档](https://faiss.ai/)、[pgvector 的精确与近似索引说明](https://github.com/pgvector/pgvector#indexing)

## 七、有哪些具体工具

| 工具 | 定位 | 需要避免的误解 |
| --- | --- | --- |
| Faiss | 向量相似度搜索与聚类的软件库，可嵌入程序 | 不是拿来就具备完整业务管理功能的数据库服务 |
| Qdrant | 专门的向量数据库，支持向量检索 | 不是负责生成所有答案的大语言模型 |
| pgvector | PostgreSQL 数据库的向量扩展 | 不是必须另外部署的一套独立数据库 |

因此，不必理解成“普通数据库被向量数据库取代”。例如商品价格、库存、订单金额仍需要准确的条件查询与一致性保障；“寻找描述相近的商品”则可以使用向量检索。两种能力可以配合，也可以放在同一个支持相关扩展的数据库里。

这里仅帮助识别名词，不是按性能排名或推荐购买。[Faiss 官方文档](https://faiss.ai/)、[Qdrant 官方介绍](https://qdrant.tech/documentation/overview/vector-search/)、[pgvector 官方仓库](https://github.com/pgvector/pgvector)

## 八、适合做什么，不适合包办什么

- **语义找资料**：换个说法也能尝试找到相关笔记、客服记录或产品文档。
- **以图搜图**：用适合图像的模型，把图片转成向量寻找相似图像。
- **推荐候选内容**：寻找特征相近的商品或文章；完整推荐系统通常还需要其他规则和排序。
- **不宜只靠相似度做精确核对**：订单号、药品剂量、版本号、金额等不能“差不多就行”。

实际系统可以把关键词搜索与向量搜索结合，称为 Hybrid Search（混合检索）；也可以在初步检索后，对少量候选重新判断相关性，称为 Reranking（重排序）。这不是保证正确的按钮，仍需用真实问题检验效果。[参考：Sentence Transformers 搜索与重排序介绍](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

## 九、常见误区与安全边界

1. **“向量很像，答案就是真的。”** 相似不等于正确。旧规则、错误资料、甚至意思相反但主题接近的句子，都可能被找出来。
2. **“最相似的前几条就一定有答案。”** 即使资料库没有答案，也可能返回相对最接近的项。需要允许“没有可靠资料”，不能强行回答。
3. **“向量数据库在本地，所有信息就不会外发。”** 还要看生成向量的模型和回答模型在哪里运行：远程嵌入服务可能收到原文，远程回答服务可能收到问题与取回片段。
4. **“变成数字就等于加密。”** 向量不是保密措施；不能因为不易读就公开敏感向量，原文和向量都应受访问控制保护。
5. **“搜索相关性可以代替权限。”** 系统必须确认用户有权查看资料，再把它交给用户或回答模型；不能仅按相似度绕过权限。
6. **“资料一多就必须上向量数据库。”** 是否需要取决于搜索需求、规模和维护成本。全文搜索、目录和双向链接仍有价值。

以上部署与权限提醒是依据数据处理流程作出的工程判断，不代表某款产品默认会替用户完成全部安全配置。

## 十、建议怎么学

先理解“内容 → 数字表示 → 比较相似程度 → 找回原文”，再区分嵌入模型、检索引擎和回答模型。之后看 RAG 的完整流程，最后再研究索引算法和性能参数，不用一开始就背数学公式。

对当前 Obsidian 学习库，本次只增加概念笔记与链接：没有安装向量数据库、没有生成向量，也没有把笔记上传到嵌入服务。
