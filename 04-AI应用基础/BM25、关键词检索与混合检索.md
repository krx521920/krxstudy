# BM25、关键词检索与混合检索

## 一句话解释

**是的，BM25 属于关键词检索中常用的相关性评分方法：它根据查询词与文档的匹配情况计算分数，帮助系统决定哪些结果排在前面。**

BM25 通常展开为 **Best Match 25**，可理解为一种“最佳匹配”评分方法，读作“B-M 二十五”。它不是大语言模型，也不是整个搜索系统；“关键词检索”是一类方法，BM25 是这类方法中常见的一种排序算法。[原理参考：Elastic 官方说明](https://www.elastic.co/docs/solutions/search/ranking)

生活类比：在图书馆找“课程退款”资料。检索系统先找出包含有关词语的书页，BM25 再给这些书页打分，判断哪几页更值得先看；它不是负责读完资料并写答案的人。

## 一、不是只判断有没有，也不是整句必须完全一致

假设你输入“课程退款流程”，系统可能把它分析成“课程、退款、流程”等检索词。具体怎样切分，取决于所配置的分词或文本分析方式；这里不是某个分词器的实测输出。

全文检索中的典型分工是：

1. **文本分析**：把查询和文档处理成可匹配的词项，可能包括分词、大小写归一化等。
2. **倒排索引**：记录“哪个词出现在哪些文档里”，方便快速找候选资料。
3. **查询规则**：决定要匹配任意一个词、全部词，还是连续短语，以及时间、权限等过滤条件。
4. **BM25 评分**：综合词频等信息，为匹配结果计算相关性分数。

实际引擎可能交错执行查找与评分，上面是职责示意，不意味着必须先收集所有候选再打分。

因此，“BM25 检索”是工程中的常用简称；严格地说，**分词器决定怎样切词，索引帮助查找，查询规则决定匹配条件，BM25 负责相关性打分**。它不能独自包办整个搜索过程。[Elastic：全文检索如何工作](https://www.elastic.co/docs/solutions/search/full-text/how-full-text-works)

### BM25 索引与 BM25 是什么关系

2026-10-27 补充核对：**BM25 是评分算法；“BM25 索引”通常是工程简称，指为 BM25 检索准备的可搜索数据结构和统计信息，常见核心是倒排索引。**两者不是两个相互竞争的算法，也不能把 BM25 直接定义成一种索引结构。

如果还不清楚“倒排”是什么意思，先看 [[Index的常见含义#倒排索引是什么|倒排索引的方向反转与多词查询例子]]：从“文档 → 词”变为“词 → 文档”，再用列表的交集、并集等确定匹配集合。

生活类比：书末的“关键词 → 页码”索引帮助你找到有关页面；一套评判规则再判断“这些页面里，哪页更值得先看”。索引像查找目录，BM25 像评分规则；搜索引擎负责把它们配合起来。

| 名称 | 主要是什么 | 解决什么问题 |
|---|---|---|
| 倒排索引（Inverted Index，可直接读“倒排索引”） | 词项到文档的查找结构 | 哪些文档包含这个词？如何快速定位？ |
| 支持 BM25 的统计信息 | 词频、文档或字段长度、文档数量等 | 评分需要用哪些数据？ |
| BM25（Best Match 25，最佳匹配评分方法） | 相关性评分算法 | 对当前查询，匹配文档怎样评分和排序？ |
| “BM25 索引” | 对上述检索数据或相应封装的工程叫法 | 这个工具为 BM25 搜索准备了什么？ |

这里的索引也不是 [[B+树与数据库索引原理|数据库中常见的 B+ 树索引]]：两者都服务于查找，但组织数据的方式和典型用途不同。[OpenSearch：倒排索引与相关性](https://docs.opensearch.org/latest/getting-started/intro/)

#### 例子：先准备目录，再按问题打分

假设只有下面三篇教学文档，空格表示我们人为约定的分词结果，**不是实际中文分词器输出**。这里按词项数量计算长度，不按汉字数计算。

| 文档 | 处理后的词项 | 长度 |
|---|---|---|
| A | 课程 退款 流程 | 3 |
| B | 课程 回放 教程 | 3 |
| C | 退款 申请 退款 流程 | 4 |

从“每篇文章包含哪些词”，反过来组织成“每个词出现在哪些文章”，就是“倒排”的含义：

```text
课程 → A：1 次，B：1 次
退款 → A：1 次，C：2 次
流程 → A：1 次，C：1 次
回放 → B：1 次
教程 → B：1 次
申请 → C：1 次
```

这类“一个词对应的文档清单”叫 Posting List（倒排列表）。实际引擎还可能记录词的位置等信息，供短语查询使用；不是每种配置都会保存所有信息。

为了支持常规 BM25 评分，系统还需要能取得这些统计量：

- 文档总数：本例是 3。
- 含“退款”的文档数量：2，是 A 和 C；**不是 3 次，文档数与总出现次数不同**。
- “退款”在各篇中的词频：A 为 1，C 为 2。
- 各篇长度：3、3、4；平均长度为 `10/3 ≈ 3.33`。

这些信息不必全部存在同一张表或同一个文件里，有的可以从底层计数推导，有的会压缩保存；搜索引擎也常按字段、分片等范围管理统计信息。这里先用单一小资料库说明关系。[Lucene：BM25 的文档频率与平均字段长度](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)

现在用户搜索“退款”：

1. 查询经过文本分析，得到词项“退款”。
2. 通过倒排列表定位 A 和 C；在本例的单词项普通匹配查询中，B 不命中。
3. BM25 根据 A、C 的词频、长度以及资料库统计信息分别计算分数。
4. 搜索系统按分数等排序规则返回结果，必要时读取原文展示。

**索引让系统不必每次逐篇重读全部正文；BM25 决定匹配结果怎样评分。**不能只看 C 出现两次就宣称它永远排名更高，因为评分还涉及长度、参数和实际查询；本例没有运行真实搜索引擎，也不假设具体得分。

如果用户改搜“回放”，同一份索引就可以定位 B，再对这个新查询评分。索引不是提前保存了所有问题的最终排名，也不是把所有可能答案都算好了。

#### 建索引、查索引和维护索引

可以按两个时机理解：

```text
资料准备时：文档 → 分词与规范化 → 建立倒排列表和统计信息
用户提问时：查询 → 分词 → 使用索引和 BM25 评分 → 返回相关文档
```

这表示职责关系，实际引擎可以交错查找、评分与跳过不可能入选的候选，不一定严格执行成几个独立步骤。

资料新增、修改或删除后，索引也需要相应更新；具体是增量更新还是重建，取决于实现。改变文档分词方式或文本切片方式时，旧资料通常需要重新处理。**这叫维护检索数据，不等于训练大语言模型。**仅在 Obsidian 新建文件，并不会自动更新一个未接入同步流程的外部搜索服务。

几个容易混淆的边界：

- **倒排索引不是 BM25 专属。**它也可以支持只判断词项是否匹配的布尔查询，以及在数据和配置支持下的其他评分方法。Elasticsearch 将相似度／评分方法作为可配置项，而不是把“索引”与“某一公式”视为同一个概念。[评分方法配置](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)
- **BM25 不要求唯一的索引文件格式。**小规模程序也能用内存里的词频、长度等统计量计算 BM25，甚至逐篇评分；没有高效倒排结构不代表公式不能计算，只是检索效率和实现方式不同。
- **“BM25 索引”不一定指一个独立文件。**工具可能用它指一个内存对象、一套磁盘结构，或封装了配置的检索组件；应结合该工具文档理解。某些产品中的 `index` 还指包含文档及其搜索结构的逻辑集合。
- **可以预计算部分统计量或权重，但不能因此把它当成固定排名。**最终相关性仍要结合当前查询；查询换了，匹配集合和结果排序都可能改变。
- **建了索引不代表能理解所有同义表达。**分词、同义词扩展和语义检索仍是不同能力，不能只靠“建立 BM25 索引”就自动获得。

学习时先记住：**索引是查找和统计的基础，BM25 是评分规则，检索系统把二者配合起来。**再阅读下一节的词频、词的区分度和长度调整，就能知道为什么要保存这些统计量。

## 二、BM25 主要依据哪三件事

### 1. 一个词在当前文档中出现多少次

TF = **Term Frequency，词频**，逐字母读 T-F。

在其他条件可比时，查询词在文档中出现多次，通常比只出现一次更能表明相关。但这种加分会逐渐趋于饱和：出现 100 次，不是出现 10 次就必然得 10 倍分。

可以理解为：反复提到“退款”有参考价值，但不能仅靠无限重复这个词就无限加分。

### 2. 这个词在整个资料库中有多常见

IDF = **Inverse Document Frequency，逆文档频率**，逐字母读 I-D-F。它关注有多少篇文档包含这个词，而不是只数当前文档里的重复次数。

例如在一个假设资料库中，“课程”几乎每篇都有，“退款”只在少数篇里出现。对于“课程退款”的查询，“退款”往往更有区分作用。

这里的“少见”是相对于当前用于评分统计的资料集合，不是指这个词在全世界使用得少。

### 3. 文档或字段有多长

长文章本来就更容易偶然出现某个词。BM25 会根据文档长度与平均长度等信息作调整，避免仅因文章长就占优势；在搜索引擎中，统计单位也可能是标题、正文这样的字段。

这不是“短文永远排在长文前面”，最终还要综合匹配词和其他评分因素。

初学时先记三点：**词频、词的区分度、长度调整**。以后需要调参数时，再研究控制词频饱和的 `k1` 和控制长度调整程度的 `b`，不用先背公式。[Elastic：BM25 的评分因素](https://www.elastic.co/blog/practical-bm25-part-2-the-bm25-algorithm-and-its-variables)、[BM25 参数说明](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

## 三、它与向量检索有什么区别

这里的“向量检索”主要指使用 Embedding（嵌入，读音近似“因贝丁”）模型，将文字转成数字表示后进行的语义检索。

| 比较项 | BM25 关键词检索 | 基于嵌入模型的语义向量检索 |
|---|---|---|
| 主要依据 | 分析后的查询词与文档词项匹配及统计信息 | 查询与文档的数字表示是否相近 |
| 常见优势 | 专业术语、产品名、报错标识等明确字词的查找 | 用不同说法描述相近意思的查找 |
| 常见弱点 | 没有共同词项或额外扩展时，容易漏掉同义表达 | 可能找到主题相近但细节、版本或结论不符的内容 |
| 是否必须有嵌入模型 | 基础 BM25 不需要 | 此处讨论的方案需要 |
| 能否直接保证答案正确 | 不能 | 不能 |

教学例子：

- 查询“汽车保养”，资料只写“车辆养护”：如果文本分析后没有共同词项，也没配置同义词或其他扩展，纯 BM25 不会自动理解两者意思接近；合适的语义模型可能建立这种联系。
- 查询具体报错标识 `ERR_CONNECTION_RESET`：字词检索通常很有价值，但要确认分析器没有把标识拆得不符合需求。

同义词词典、查询改写可以帮助关键词检索，但这属于搜索系统增加的能力，不是 BM25 评分公式本身忽然懂了语义。[Elastic：同义词配置](https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms)

**严格查订单号、完整产品编号或版本条件时，应使用相应的精确字段查询或过滤，不能仅靠相关性排名。**BM25 是排序方法，不是“等于某个编号”的约束。

补充边界：词项权重也可以表示成稀疏向量，向量方法并不全是语义模型。这里比较的是常见检索方案，不应机械记成“BM25 在数学上完全不能用向量表示”。

## 四、为什么会把两种检索结合起来

Hybrid Search（混合检索，读音近似“海布里德 瑟奇”）通常把关键词检索和语义向量检索的结果结合：一边抓明确术语，一边补充不同表达下的相关内容。

一种示意流程是：

**同一个问题 → 两路分别检索 → 合并去重并融合排名 → 可选重排序 → 展示资料或交给回答模型。**

融合排名可以使用 RRF，即 **Reciprocal Rank Fusion，倒数排名融合**，逐字母读 R-R-F。初步理解为“根据资料在各路结果中的名次综合排名”，而不是直接把尺度不同的原始分数随意相加；也有经过合适归一化和调参的分数融合方案。

Reranking（重排序，读音近似“瑞兰金”）则是在已有候选中再次判断相关性、重新排列，与把两路结果融合并不是同一个概念。[Elastic：排序、混合检索与重排序](https://www.elastic.co/docs/solutions/search/ranking)、[倒数排名融合](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

混合检索并不保证一定优于单一路径；更多候选也可能带来噪声，需要用真实问题、正确资料和可接受的响应成本来验证。

### 先检索：从资料库中拿到候选清单

检索（Retrieval，读音近似“瑞垂沃”）的初步候选获取也常叫“召回”。例如从很多资料片段中先找出几十条可能相关的内容；这是流程阶段名称，不等于已经达到某个“召回率”。

两种典型操作如下：

- **关键词路线**：预先分词、建立倒排索引；提问时查询索引，用 BM25 等方法评分，返回片段标识、原文或原文位置、分数与名次。
- **向量路线**：预先用嵌入模型给片段生成向量并建立索引；提问时用兼容方式生成问题向量，再比较相似度，返回候选片段。例如 `BAAI/bge-m3` 可用于生成稠密向量；它还支持其他检索模式，这里只讨论其稠密检索用法。[BGE-M3 官方模型卡](https://huggingface.co/BAAI/bge-m3)

其中模型负责生成表示，索引负责加速查找，搜索引擎负责执行检索，不要把它们全部当成同一种“模型”。向量索引的例子见 [[向量引擎、向量数据库与相似度检索#六、为什么还需要专门的引擎和索引]]。

下面用同一个问题贯穿各阶段：**“没开课的课程怎么申请退款？”**

| 片段标识 | 假设的原文内容 |
|---|---|
| A | 未开课课程可在订单页申请退款。 |
| B | 退款申请入口位于订单详情页。 |
| C | 已开课课程退款需走特殊审核。 |
| D | 课程结束后支持观看回放。 |

**这些都是教学资料，不代表真实业务政策。下面两路排名是手工设定，不是 BM25 或向量模型的实测结果。**

- BM25 路线返回前三条：`B → A → C`。
- 向量路线返回前三条：`A → C → D`。

这展示了一个常见现象：不同检索路线返回的内容可能重合，也可能有各自独有的候选。

### RRF：拿各路名次做融合

RRF 本身已经是具体算法，不是需要再找一个同名大模型。标准等权 RRF 对每个候选计算：

```text
融合分数 = 各路贡献之和
某一路的贡献 = 1 / (k + 该候选在这一路的名次)
```

名次从 1 开始；没有进入某一路返回清单，该路贡献就是 0。`k` 是控制名次差异影响的常数，不是“取前 K 条”的数量。这里用 `k = 60`，也是所引用 Elasticsearch 实现的默认值，不是所有场景都必须用 60。

套用刚才两张清单：

| 候选 | BM25 名次 | 向量名次 | RRF 分数计算 | 约值 |
|---|---|---|---|---|
| A | 2 | 1 | `1/62 + 1/61` | 0.032522 |
| C | 3 | 2 | `1/63 + 1/62` | 0.032002 |
| B | 1 | 未入选 | `1/61` | 0.016393 |
| D | 未入选 | 3 | `1/63` | 0.015873 |

融合后得到：**`A → C → B → D`**。这些数值是根据假设排名实际计算得到的，不是模型预测。

注意，B 在一路排第一，但 C 同时得到两路支持，于是在本例中排到了 B 前面。**RRF 不读原文，也不理解“未开课”和“已开课”，它只综合上游名次。**它输出的分数不是答案正确率；丢弃原始分数的大小差距，也是一种取舍。[Elasticsearch：RRF 公式与参数](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

下面是可独立运行的 Python 小例子，只计算排名，不联网、不需要安装依赖：

```python
rankings = [["B", "A", "C"], ["A", "C", "D"]]
k = 60
scores = {}

for ranking in rankings:
    seen = set()
    for rank, doc_id in enumerate(ranking, start=1):
        if doc_id in seen:
            raise ValueError("同一路清单不能重复包含同一个片段")
        seen.add(doc_id)
        scores[doc_id] = scores.get(doc_id, 0.0) + 1 / (k + rank)

result = sorted(scores.items(), key=lambda item: (-item[1], item[0]))
for doc_id, score in result:
    print(doc_id, round(score, 6))
```

- `rankings` 保存各路已排序的片段标识，`scores` 累加分数。
- 同一路重复片段会报错，防止重复计票；跨路相同片段使用相同标识，把贡献加到同一个结果上。
- 最后按总分降序排列；示例用标识字母顺序处理同分，仅是为了让输出可重复，不属于 RRF 必须遵守的业务规则。

实际工程最好统一片段标识、文档版本与权限；不要仅因标题一样就合并成同一份资料。

### RRF 属于哪类算法，还有哪些同类方法

**RRF 是具体算法，直接所属的类别叫 Rank Fusion（排名融合）；从更宽的检索流程看，它属于检索结果融合方法。**这里可直接读中文“排名融合”。相关文献还会使用 Rank Aggregation（排名聚合）等说法；不同作者的术语边界不完全相同。

检索结果融合常写作 Retrieval Fusion 或 Result Fusion；在信息检索文献里，也可能归到 Data Fusion（数据融合）下。这里的数据融合是“把多路搜索结果汇总为一份结果”，不是泛指把数据库、传感器或文件拼在一起。你说的“类”是算法分类，不是编程语言里的 `class`。

生活类比：多位评委分别给出了选手排名或分数，现在要算出总榜。有人只综合名次，有人把评分统一尺度后加权计算。

为了学习，可以先按**主要使用名次，还是使用具体分数**分成两组：

| 组别 | 具体方法 | 核心做法 | 注意点 |
|---|---|---|---|
| 按名次融合 | RRF（Reciprocal Rank Fusion，倒数排名融合） | 把各路的 `1/(k+名次)` 相加 | 不利用原始分数之间的差距 |
| 按名次融合 | Weighted RRF（加权 RRF） | 把各路的 `权重/(k+名次)` 相加 | 仍然看名次，权重需验证 |
| 按名次融合 | Borda Count / BordaFuse（博尔达计分／融合） | 名次换成积分，再把各路积分相加 | 要约定列表长度、缺席项与并列名次的处理 |
| 按分数融合 | Weighted Sum（加权求和／线性融合） | 对处理到合适尺度的分数乘权重，再求和 | 分数尺度及权重会影响结果 |
| 按分数融合 | CombSUM（组合求和，可读“康姆 萨姆”） | 将各路可比较的分数相加 | 是简单的等权分数求和思路 |
| 按分数融合 | CombMNZ（求和后乘非零贡献数，可读“康姆 M-N-Z”） | 分数之和乘以提供非零分数的路线数量 | 更强调多路共同支持；要明确零分与缺席的定义 |

CombMNZ 中的 MNZ 指 Multiply-by-number-Non-Zero，可理解为“乘以非零项数量”。**不是把各路分数直接相乘。**这些方法并非互不相关的六大类：加权 RRF 是 RRF 的变体，等权求和也可视为加权求和的一种特殊情况。

RRF 与加权 RRF 的实现可见 [Elasticsearch 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/rrf-retriever)；BordaFuse、CombSUM、CombMNZ 等属于检索融合算法，见 [ranx 官方算法目录](https://amenra.github.io/ranx/fusion/)。CombSUM 和 CombMNZ 的计算含义也可见 [检索研究报告中的组合函数表](https://trec.nist.gov/pubs/trec13/papers/cas.ict.web.pdf)。

#### 例子一：加权 RRF 是在名次贡献上加权

假设两路权重分别设为 2 和 1：

```text
总分 = 2/(60 + 关键词名次) + 1/(60 + 向量名次)
```

仍是同一候选跨路线累计；未进入某路清单，该路不贡献分数。它不是把原始 BM25 分数乘 2；权重 2 也不表示“关键词路线一定贡献最终结果的三分之二”。最终贡献还取决于名次和是否入选。

#### 例子二：加权分数融合保留具体得分信息

假设经过合适的尺度处理，某片段的关键词分数为 `0.9`，语义分数为 `0.2`，我们给两路权重 `0.7` 和 `0.3`：

```text
融合分数 = 0.7 × 0.9 + 0.3 × 0.2 = 0.69
```

这是人为构造的算术例子，不是实测分数，也不是推荐的权重。RRF 只需要各路名次；这种方法使用具体分数，因此能保留同一路中“领先很多”还是“只领先一点”的差别。[Elasticsearch：线性融合](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/linear-retriever)

为什么要处理尺度？如果一条路线经常给出 20、30，另一条路线通常只有 0.6、0.8，未经检查直接相加，前者可能仅因为数值大就占优势。Normalization（归一化）可以把分数调整到某种约定尺度；但都变成 0～1，也不意味着两路分数具有相同的概率含义，仍需要评估。

#### 例子三：CombSUM 和 CombMNZ 的区别

假设某片段两路非负分数分别为 `0.8`、`0.6`，且两路都作出非零贡献：

- CombSUM：`0.8 + 0.6 = 1.4`。
- CombMNZ：`(0.8 + 0.6) × 2 = 2.8`。

如果只有一路给出 `0.8`、另一路按缺席记为 0，则本例中两种算法都得到 `0.8`。实际系统要明确分数归一化后恰好为 0 的命中项如何计数，不能只用“找到了几次”含糊代替“非零贡献数”。

#### 和 BM25、模型重排的分类关系

- **BM25**：根据查询词与文档统计信息评分，可以产生一路搜索结果。
- **排名／分数融合**：合并已有的多路结果；RRF、BordaFuse、CombSUM 等在这一层。
- **模型重排**：例如交叉编码器重新联合处理问题与候选原文，产生新的相关性分数；不是前述简单融合公式的另一种名称。

边界不是绝对互斥：融合结果本身也形成新排序，复杂系统可以学习融合权重，也可以在重排后再次融合。这里是为了理解常见流程而按主要职责分类。

学习时先掌握 **RRF 与加权分数求和**这两种不同思路，再认识 Borda、CombSUM、CombMNZ 即可。没有一种方法适合所有资料库；选择依据应是实际查询效果、候选覆盖、延迟与维护成本，而不是公式是否复杂。这里的融合也不限于“关键词＋向量”，还可以合并多个检索器或多次查询的结果。

### 重排序：把问题和候选原文一起重新评分

重排序是一个阶段，不是唯一算法。常见实现之一是 **Cross-Encoder（交叉编码器，读音近似“克罗斯 恩扣德”）**：把“问题＋一段候选原文”一起交给模型，得到相关性分数，然后按新分数排序。

与常见双编码器向量检索的区别是：后者可以提前计算文档向量，再与查询向量比较；交叉编码器则对问题与候选进行联合处理，可以更细致地比较两者，但通常计算开销更大，因此常用于少量候选。[Sentence Transformers：检索与重排序](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

继续刚才的例子，重排模型接收：

```text
问题 + 片段 A 原文 → 新分数
问题 + 片段 C 原文 → 新分数
问题 + 片段 B 原文 → 新分数
问题 + 片段 D 原文 → 新分数
```

一个期望的改进是把 B 提到 C 前面，因为 B 说明申请入口，而 C 讨论已开课的特殊情况。于是可能变成 **`A → B → C → D`**。这只是说明重排的目标，**不是本次运行模型得到的结果，也不是保证模型一定能排对**。

具体模型例子：

| 名称 | 属于什么 | 输入与输出 |
|---|---|---|
| `BAAI/bge-reranker-v2-m3` | 可用于多语言相关性重排的具体模型 | 问题与候选文本对 → 相关性分数 |
| `Qwen/Qwen3-Reranker-0.6B` | Qwen3 重排系列中的具体模型 | 按模型要求提供指令、问题与候选文本 → 相关性分数 |

这里列举的是可核对的实现，不是性能排名；中文效果、输入长度、硬件要求、速度都要结合实际数据验证。Qwen 名称中的 B 指 billion，十亿，0.6B 表示约 6 亿参数，不是文件下载大小。[BGE Reranker 官方模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3)、[Qwen3 Reranker 官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)

下面是调用 BGE 重排模型的 Python 示例，与前面的 RRF 程序独立。需要事先准备兼容的 `sentence-transformers` 环境；首次加载可能下载模型并占用磁盘、内存与计算资源。**本次没有安装依赖、下载模型或执行推理，只做代码语法检查。**

```python
from sentence_transformers import CrossEncoder

query = "没开课的课程怎么申请退款？"
documents = {
    "A": "未开课课程可在订单页申请退款。",
    "B": "退款申请入口位于订单详情页。",
    "C": "已开课课程退款需走特殊审核。",
    "D": "课程结束后支持观看回放。",
}
candidates = ["A", "C", "B", "D"]  # 前一步融合后的候选
model = CrossEncoder("BAAI/bge-reranker-v2-m3")
pairs = [(query, documents[doc_id]) for doc_id in candidates]
scores = model.predict(pairs)
ranked = sorted(zip(candidates, scores), key=lambda item: item[1], reverse=True)
print(ranked)
```

- 前半段准备问题、候选原文及其标识。
- `CrossEncoder` 加载模型，`predict` 为每个“问题—原文”对评分；模型名称和调用方式依据官方模型卡。
- 最后按分数降序排列。实际输出取决于模型与运行环境，这里不编造固定输出。

不同重排模型及封装可能返回原始分数，或经过函数变换的 0～1 数值；**不能把 0.9 自动当作“答案有 90% 概率正确”，也不应直接跨模型比较分数**。除交叉编码器逐对打分外，也可以设计大语言模型排序、学习排序或业务规则重排；它们不是同一种实现。

### 在项目里通常怎么配置

可以先把流程看成：

**建立可检索资料 → 确认查询权限 → BM25 与向量各找候选 → RRF 融合 → 截取重排候选 → 重排模型评分 → 选取资料并核对来源 → 交给回答模型。**

例如各取前 50 条，融合后选前 40 条给重排模型，再选前 5 条作为回答资料。这里的 50、40、5 都只是教学数量，不是推荐默认值；两路结果重合时，合并后不一定有 100 条。

你们或开发者通常需要确定：

1. **资料怎样入库**：切片规则、分词、向量生成、来源、版本、稳定标识和权限。
2. **检索怎样配合**：关键词还是向量，或两路都用；分别返回多少条。
3. **怎样融合**：RRF 或其他方案、常数和候选窗口；平台提供的“混合检索权重”不一定就是 RRF。
4. **怎样重排**：用哪个模型、在哪里运行、最多处理多少候选、超时如何回退。
5. **怎样验收**：正确资料有没有进入候选、重排后是否更靠前、答案是否引用正确、耗时和成本是否可接受。

现成平台可能已完成大部分实现，开发者主要做配置和测试；并非每个平台都支持同一套参数，也不需要为了使用 RRF 另外训练模型。

边界要记住：

- 纯 RRF 不会找出两路清单都没有的资料；仅处理给定候选的重排器，也救不回根本没进入候选的答案。需要扩大或改进检索，或增加一轮新检索。
- 权限不能靠重排模型判断；应在检索与数据访问环节执行授权检查，未经授权的原文不能先发给外部重排服务再过滤。
- 输入太长可能被截断，关键条件不能因此丢失；片段版本、日期和完整上下文也需要检查。
- RRF 与重排都不是必需组件。单路检索可以直接重排；两路融合后也可以直接展示。是否增加阶段，要看实际收益。
- 在严格广义上，RRF 也会重新排列结果；这里为了说明工程职责，把“融合排名”和“读取文本的模型重排”分开讲，不能理解成两个词在所有文章中都绝对互斥。

## 五、它与 RAG 有什么关系

RAG = **Retrieval-Augmented Generation，检索增强生成**，常读作“rag”，核心是先找资料，再让模型依据资料组织回答。

- BM25 可以负责“找资料”，不负责生成答案。
- 语义向量检索也可以负责“找资料”。
- 两者结合，也可以作为 RAG 的检索环节。
- RAG 不等于向量数据库；只用关键词检索取得资料，再交给模型回答，也可以构成检索增强生成流程。

举例：你问“讲师课程退款期限是多少”，系统先找到当前有效的退款规则，再让回答模型解释并引用原文。搜到含有“退款”的文档，不表示其中一定有期限，也不表示资料仍然有效。

见 [[RAG、Naive RAG与GraphRAG]] 和 [[向量引擎、向量数据库与相似度检索]]。

## 六、常见误区与学习建议

- **“关键词检索就是整句话原样匹配。”** 不一定，分词、短语查询和匹配条件是不同层面的配置。
- **“启用 BM25，所有查询词就都必须出现。”** 不一定；是否全部匹配由查询规则决定，不能用高分替代硬条件。
- **“高分就是内容真实，或有 90% 正确率。”** 不是。分数是相关性指标，不验证事实，也不是校准后的概率。
- **“BM25 没有模型就不用维护。”** 仍需维护资料、分词规则、索引、权限和评估；新增笔记并不会让所有检索服务自动同步。
- **“中文搜不到就是评分算法不好。”** 先检查分词结果、资料是否入索引、字段和过滤条件，再判断是否要调整评分或增加语义检索。

建议先用两类问题理解差别：一类包含准确术语或报错标识；另一类用日常说法描述同一件事。观察各自找到什么、漏掉什么，再考虑混合检索，不用一开始就背公式或安装服务。
