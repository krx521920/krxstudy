# SQL 事务、锁与并发一致性

> [!summary] 一句话解释
> 事务把多步数据库修改组成一个整体；锁协调有冲突的操作；MVCC 用可见的数据版本减少读写互相等待，三者一起保护并发下的正确性。

像银行转账：甲扣 100 元与乙加 100 元必须作为同一笔业务完成；别人同时操作账户时，不能都拿过期余额各算各的。

## ACID：事务的四个目标

**ACID** 由 **Atomicity、Consistency、Isolation、Durability（原子性、一致性、隔离性、持久性，常读作 acid）** 的首字母组成。

| 特性  | 含义                 | 需要警惕的误解                   |
| --- | ------------------ | ------------------------- |
| 原子性 | 事务的数据库修改整体提交或撤销    | 不包含已经发出去的短信或外部付款          |
| 一致性 | 正确业务操作保持已定义的不变量    | 数据库不知道所有业务规则，错 SQL 也能成功提交 |
| 隔离性 | 按所选级别限制并发事务相互影响    | 不等于所有事务都按先后顺序执行           |
| 持久性 | 在配置承诺的故障范围内保存已确认提交 | 关闭刷盘或整机磁盘永久损坏不是凭空免责       |

关系见 [[数据库事务日志、主从复制与故障恢复]]：约束和业务逻辑保护规则，锁/版本参与隔离，日志与恢复机制支持原子性和持久性。不是一条日志独自实现全部 ACID。

## BEGIN、COMMIT、ROLLBACK

BEGIN 开始事务，COMMIT 提交，ROLLBACK 撤销尚未提交的修改。自动提交模式下，一条语句也可能构成一个事务。

**SAVEPOINT（保存点）** 可以提供事务内部的局部回滚位置，但不是把事务套进去就变成几个独立提交。驱动、连接池、框架对事务的管理也需要确认；跨两条连接不自动属于同一事务。

回滚不会倒转世界：已提交事务不能再靠 ROLLBACK 撤销；序列/自增编号可能留下空洞；外部服务副作用需要自己的处理。

## 抢库存：为什么先查再改会超卖

初始库存为 1，甲读到 1，乙也读到 1；两人都认为可以购买。如果程序都写成“旧值减一后设为 0”，可能两单成功而库存看起来仍是 0。

更合适的基本操作是把条件与扣减放在同一条语句中：

```sql
-- lab: reserve_one
UPDATE inventory
SET stock = stock - 1, version = version + 1
WHERE product_id = 10 AND stock >= 1;
```

本例初始 1，第一次影响 1 行，第二次影响 0 行。**必须检查影响行数**：0 行表示没成功扣库存，不能继续创建成功订单。数据库也可能返回锁等待、死锁或序列化错误，程序应处理这些分支。

完整业务流程应由程序控制，以下是伪代码，不是可直接执行的 SQL：

```text
开始事务
登记唯一的请求业务键；若已处理，读取原结果，不再次扣库存
执行带 stock >= 数量 条件的扣减
如果影响行数不是 1：回滚，返回库存不足
写入订单、明细及必要的待发送事件
所有约束和业务校验通过：提交
任何失败：回滚，按错误类型决定是否重试
```

这解决本地数据库内的扣库存与建单配合；真实支付通常还要库存预留、超时释放和 [[状态机与幂等性]]。

## 悲观锁与乐观锁

悲观策略先协调排他访问，再执行依赖读取结果的操作。PostgreSQL/MySQL InnoDB 中常见的片段是：

```sql
-- 方言示意：需要放在显式事务内，后续检查与更新在同一连接完成
SELECT stock FROM inventory WHERE product_id = 10 FOR UPDATE;
```

它对匹配行取得相应的锁，其他冲突写入可能等待。普通 SELECT 和锁定读取不是同一种可见性/等待语义；SQLite 不能直接套用 FOR UPDATE。

乐观策略在更新时验证“我读到的版本没被别人改过”：

```sql
-- lab: optimistic_update
UPDATE inventory
SET stock = stock - 1, version = version + 1
WHERE product_id = 10 AND version = 0 AND stock >= 1;
```

这里的 0 代表程序上次读到的版本，真实代码应参数绑定。没改到 1 行就重新读取或返回冲突。所有相关写入路径都要正确维护版本。乐观锁不是完全不用数据库锁，而是业务层不在读取后一直持锁等待。

## 锁有不同维度，不是一张简单大小排行榜

- 粒度：表、行或索引记录、范围。
- 模式：共享与排他等，决定哪些操作兼容。
- 用途：事务数据锁、保护表结构的锁、应用约定的咨询锁。
- 内部短锁：保护内存页、树结构的 latch，与持续到事务结束的业务数据锁不是同一层。

**S = Shared（共享，读 S）**、**X = Exclusive（排他，读 X）** 是常见记号。多个兼容读可以共存，冲突写需要等待或失败；实际兼容矩阵应查产品，不要把“有行锁”理解为绝无表级锁。

### MySQL InnoDB 的记录锁、间隙锁和临键锁

InnoDB 的记录锁落在索引记录上；间隙锁保护相邻索引值之间的空隙，限制插入；Next-key Lock（临键锁）结合记录及其前方间隙。意向锁则在表级表明事务会在更细粒度加锁，帮助检查表锁冲突。

比如索引中有 10、20，事务需要保护区间时，仅锁住现有 10 和 20 不能阻止别人插入 15。范围保护处理的正是“还不存在的记录”问题。

实际锁定范围受隔离级别、唯一/范围条件、索引和执行计划影响。READ COMMITTED 下普通搜索的间隙锁使用减少，但外键和重复键检查等仍有例外。别背“一个 UPDATE 永远只锁一行”或“RR 下所有 SELECT 都加间隙锁”。

## MVCC：让读者看到合适版本

**MVCC = Multi-Version Concurrency Control（多版本并发控制，读作 M-V-C-C）**。

设余额原来为 100，事务甲正在改为 80、尚未提交。事务乙的一致性读取可以看可见的旧版本 100，不必读取甲的半成品。甲提交后，乙下一次读是否看到 80，要看快照和隔离级别。

快照不是把整库复制一份；可以理解为一组判断规则：哪些事务已提交、哪些仍在进行、哪些版本对我可见。底层结合事务标识、提交状态、记录版本元数据等判断，并允许事务看到自己的修改。

| 产品 | 版本实现的入门理解 | 清理问题 |
|---|---|---|
| MySQL InnoDB | 当前聚簇记录关联事务信息和 undo，按需重建旧版本；Read View 判断可见性 | 旧读视图会阻碍需要保留的历史被 purge 清除 |
| PostgreSQL | 更新通常生成新行版本，表中可同时存在多个版本，按快照判断可见性 | VACUUM/autovacuum 清理不再需要的旧版本 |
| SQLite 的 WAL 模式 | 读者保留相应快照，写者在 WAL 中追加变化 | 仍通常只有一个写事务，检查点受读者影响 |

这是原理比较，不是声称三种引擎具有相同版本链或锁实现。MVCC 主要减少常见一致性读和写的冲突，**不会消除写写冲突、结构变更锁、唯一约束竞争和长事务成本**。

## 隔离级别：给并发行为定边界

常见异常：脏读是读到别人未提交的数据；不可重复读是两次读同一数据发现别人已提交修改；幻读是同一条件的结果集合变化；写偏斜则可能让两个事务各改不同行却共同破坏跨行规则。

| 名称与读法 | 入门含义 |
|---|---|
| Read Uncommitted，读未提交，RU | 标准允许读到未提交变化；产品可能提升保证 |
| Read Committed，读已提交，RC | 不读别人未提交数据，连续语句可能看到新提交 |
| Repeatable Read，可重复读，RR | 提供更稳定的读取，但具体异常与实现要看产品 |
| Serializable，可串行化 | 成功事务的结果等价于某种逐个执行顺序，可能需要重试 |

PostgreSQL 默认 RC，其 RR 用稳定快照且不允许幻读，但仍可能有序列化异常；RU 实际按 RC 处理。MySQL InnoDB 默认 RR，其一致性读与锁定读要区分，不能直接套 PostgreSQL 的描述。

可串行化不等于引擎只许一个线程工作。PostgreSQL 的 **SSI = Serializable Snapshot Isolation（可串行化快照隔离，读作 S-S-I）** 会检测危险依赖，可能中止事务；它的谓词锁机制不能等同于 InnoDB 间隙锁。

报表若分多条查询，需要一致的截面，就应明确快照方案；仅仅 BEGIN 不保证在 RC 下每条 SELECT 都看到同一个时点。

## 死锁、长事务与重试

甲先锁 A 再等 B，乙先锁 B 再等 A，就形成等待环。数据库可能选择一个事务回滚来解除死锁。

处理原则：以一致顺序访问资源；事务尽量短；不要持锁调用慢外部接口；识别可重试错误，回滚并有上限、带退避地重试**整个业务事务**。不是只重跑最后一句，也不是无限循环掩盖问题。

没有死锁也可能慢：一个长事务挡住很多人、热点库存竞争、连接池等待、老快照阻碍版本回收。看阻塞链与等待类型，而不仅看 SQL 文本。

## 外部消息与事务的边界

数据库提交成功后发通知，程序可能在两步之间崩溃；先发通知再提交，又可能通知发了但数据库回滚。

Transactional Outbox（事务发件箱）把业务数据和待发送事件记录在同一个数据库事务中，再由独立发送者投递。发送仍可能重试，消费者要按事件业务键幂等处理；它不是天然“世界范围恰好一次”。
