# OOM：内存不足、显存不足与内存泄漏

## 一句话解释

**OOM = Out of Memory，内存不足／内存耗尽，读作字母 O-O-M：程序需要的内存超出了当前系统、运行环境或设备能够提供或允许使用的范围。**

它不是某个软件的名字，也不是一种编程语言。它描述一类资源不足问题，可能表现为分配失败、异常、任务退出，或者进程被系统终止。不能看到 OOM 就认定“整台电脑的物理内存已到 100%”。

生活类比：硬盘像存放资料的柜子，内存像工作桌面。柜子还有很多空位，不代表桌面还能摊开更多资料；即使共享办公室还有空桌，某个团队也可能只能使用分给自己的那一部分。

## 一、先分清：到底是哪一层“不够”

| 场景 | 不足的资源或限制 | 初步理解 |
|---|---|---|
| 普通程序、系统压力 | 主内存以及系统可提供的内存分配资源 | 多个程序竞争资源，或一次申请过大 |
| Java 等运行环境 | 堆、其他内存区域或运行环境限制 | 整机有余量，程序仍可能达到自身上限 |
| Docker 等容器 | 容器或上层资源组的内存限制 | 宿主机还有内存，不等于容器可以继续用 |
| 本地模型、图像计算 | 图形处理器的设备内存，常称显存 | 系统主内存有余量，不代表显存也有余量 |
| 保存文件失败 | 磁盘空间、配额等 | 通常属于磁盘空间不足，不应直接叫 OOM |

**RAM = Random-Access Memory（随机存取存储器，常读“RAM／ram”）**，日常所说“电脑有多少内存”通常指主内存。**GPU = Graphics Processing Unit（图形处理器，读 G-P-U）**；**VRAM = Video Random-Access Memory（视频随机存取存储器，通称显存，读 V-RAM）**。

独立 GPU 常有专用显存，部分集成或统一内存平台会共享物理内存，不能机械理解成所有电脑都存在完全分开的两池内存。具体见 [[GPU、显存与CUDA并行计算]]、[[存储层次：RAM、SRAM、DRAM、Cache与Flash]]。

### 整台电脑有内存，为什么程序还是不够

假设某台电脑有 32 GB 主内存，但一个容器的内存硬限制是 2 GB。当容器内存使用达到这个边界、又不能充分回收时，仍可能触发容器范围的 OOM；不是自动把整台电脑剩余内存都交给它。

类似地，Java 程序可能为堆设置了更小上限。Heap（堆）可以先理解成运行时为许多对象分配空间的一块逻辑区域，不是另外一根内存条。**JVM = Java Virtual Machine（Java 虚拟机，读 J-V-M）**；Java 堆之外还存在其他内存开销，不能把堆上限直接当成整个进程用量。

上述容量只是教学假设，不是当前电脑或生产服务器的实测配置。[Docker：内存资源限制](https://docs.docker.com/engine/containers/resource_constraints/)、[Oracle：OutOfMemoryError 的不同原因](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)

## 二、OOM 通常怎样发生

程序读取数据、创建对象、处理图片或运行模型时，需要申请内存。一个简化过程是：

```text
任务需要更多内存
    ↓
运行环境或系统尝试分配，必要时回收可回收资源
    ↓
仍无法满足分配需求，或达到相关限制
    ↓
可能报错、任务失败，或者触发系统终止进程
```

这不是所有平台都固定执行的四步流程。例如受管理运行时可能先进行垃圾回收，操作系统可能先回收缓存或换出部分页面；某些失败直接返回错误，并不触发内核 OOM Killer。

**GC = Garbage Collection（垃圾回收，读 G-C）**，是自动回收不再需要的部分对象内存的机制；它不保证所有占用都能释放，也不代表程序永远不会 OOM。

在 Windows 中，还需要关注系统的“已提交”内存及提交上限，而不仅是任务管理器里一个内存百分比。Page File（分页文件）可以支持部分内存页面存放和扩展系统提交容量，但它不是同等速度的物理内存，也不是无限资源。[Microsoft：分页文件与提交上限](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file)

## 三、几个具体例子

### 1. 一次性读取过多数据

导出报表时，把大量数据库记录全部读进内存，再复制、排序、生成表格，可能产生很高的内存峰值。硬盘上的文件只有几 GB，不代表处理时也只需要几 GB：解压、对象表示和中间副本都会影响用量。

处理思路是按批、按流处理，避免无意义复制；不是一看到错误就删除硬盘文件。具体方案需要结合程序功能和实际测量。

### 2. 并发任务叠加

假设每个任务额外独占约 100 MB 内存，50 个任务的这部分峰值同时出现，则仅任务额外开销就约为 `100 × 50 = 5000 MB`，按十进制约为 5 GB；还没计算程序本体、缓存和其他开销。

这里只用简化算术解释并发放大效应；实际任务可能共享数据，峰值也不一定同时出现。限制同时执行数量、使用有界队列和背压，往往比无限接任务更可控，见 [[高并发系统：瓶颈分析、扩容与稳定性治理]]。

### 3. 内存泄漏或无界增长

Memory Leak（内存泄漏）可以先理解为：不再需要的内存没有被正确释放，或者无用对象仍被引用，导致无法回收。

例如每次请求都把一份结果永久保存在全局列表里，又没有清理规则，长期运行就可能持续增长。缓存不设容量、任务积压也会吃掉内存，但要结合业务判断是泄漏、无界设计还是正常待处理数据。

**OOM 是结果，内存泄漏是可能原因之一，二者不能画等号。**正常任务太大、限制太小或并发峰值过高，即使没有泄漏也会 OOM。内存曲线升高也不是泄漏的充分证据，缓存、预分配和分配器保留都可能影响观测。[Oracle：不能仅凭 OOM 判定内存泄漏](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)

### 4. 本地大模型或图像任务的显存不足

你可能看到 `CUDA out of memory`。CUDA 是 NVIDIA 的并行计算平台与编程模型，历史名称展开为 **Compute Unified Device Architecture（统一计算设备架构，常读“库达”）**；该错误常见于相应 GPU 设备内存分配失败。

模型权重只是运行开销的一部分，还可能需要中间结果和生成缓存。训练通常还要保存梯度、优化器状态等；更长输入、更大图片、更多同时处理的样本或请求，都可能增加峰值用量，具体取决于模型和实现。

2026-10-31 补充：[[大模型从数据、Token到训练与本地部署#“占用大量令牌”是什么意思|Token 占用]] 是序列长度或用量计数，不等于内存字节数。长上下文可能增加缓存开销，但“上下文超限”与 OOM 是不同问题；平台的累计 Token 消耗也不代表这些 Token 同时留在内存中。

Batch Size（批大小）指一次成批处理多少个样本。根据任务，可以考虑减小批大小、减少并发、缩短输入、降低图像尺寸，或选择支持的较低精度、量化及卸载方案；这些方案有质量、速度或兼容性取舍，不是任意改一个参数就能解决。

**模型文件能保存到硬盘，不等于运行时能放进显存。**主内存、专用显存、共享内存和卸载也不能简单按容量一比一替换。见 [[大模型推理加速：FP8、量化、KV Cache与多Token预测]]。

PyTorch 是常用于深度学习的计算框架。其 `empty_cache()` 释放的是未使用的缓存分配块，不会释放仍被使用的张量内存，也不能把需要更多显存的任务凭空塞进去；分配器显示的“保留”与实际张量“占用”也有区别。[PyTorch：设备内存管理](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)

## 四、OOM Killer 和 OOMKilled 是什么

OOM Killer 可理解为“内存不足时选择并终止进程的机制”。在 Linux 的某些内存不足场景下，内核会终止进程以释放资源；这不等于整个系统必然关机，也不是每次分配失败都一定杀进程。

容器常依赖 **cgroup = control group（控制组，可读 C-group）** 管理资源。cgroup v2 的 `memory.max` 是内存硬限制接口；达到限制且无法充分回收时，可能在该控制组内触发 OOM Killer。`memory.events` 中的 `oom` 和 `oom_kill` 是不同事件计数，不能把一次 OOM 事件直接等同为杀掉了一个进程。[Linux 内核：内存限制和 OOM 事件](https://docs.kernel.org/admin-guide/cgroup-v2.html)

在容器状态或管理平台中看到 `OOMKilled`，通常表示记录到了因内存不足被终止的情况。应结合发生时间、具体进程／容器、内存限制和系统事件核实；只看到普通的 `Killed` 提示或程序退出，不能直接认定是 OOM。

内核强制终止进程时，程序不一定来得及写自己的错误日志、保存中间结果或执行清理代码。不要为了让程序“不被杀”而盲目关闭保护机制，或取消所有资源限制。

## 五、看到 OOM，先怎样判断

以下是排查思路，不代表本次已经检查你的电脑或服务器，也不是让你直接修改生产配置。

1. **保留完整错误文字和发生时间。**区分 Python 的 `MemoryError`、Java 的 `OutOfMemoryError`、GPU 的 `CUDA out of memory` 和容器 OOM 事件。Python 官方也说明，抛出 `MemoryError` 不保证解释器一定能完整恢复。[Python：MemoryError](https://docs.python.org/3/builtins/exceptions.html#MemoryError)
2. **确认错误来自哪里。**本机软件、构建任务、容器、本地模型，还是远程服务？若是远程接口返回服务端 OOM，给自己的电脑增加内存未必有用。
3. **对照同一时间的用量、峰值和限制。**主内存、Windows 已提交值、进程占用、容器上限、设备显存需要分开看；进程退出后用量下降，不能据此否认之前曾不足。
4. **判断是突发峰值还是持续增长。**是否只在大文件、长输入、批量任务或高并发时发生？在相近负载下运行越久是否越容易失败？这些只是线索，不是单凭曲线就下结论。
5. **用小输入或低并发验证假设，再选择措施。**在安全测试环境比较变化，评估分批、限制缓存和队列、修复泄漏，或在资源确实充足时合理调整额度。

示例中的日志若需要分享，应先遮蔽账号、密钥和业务数据。堆转储可能包含大量敏感内容，不应随意公开上传。

## 六、常见误区与学习建议

- **“硬盘还有空间，所以不可能 OOM。”**硬盘与内存不是同一资源；分页／交换只是特定机制，不能自动代替所有内存需求。
- **“OOM 必然是内存条坏了。”**不是。它首先说明分配需求或限制出现问题，不等于硬件故障。
- **“OOM 必然有内存泄漏。”**不是。任务规模、并发、限制、地址空间或分配器约束等也可能导致失败。
- **“增加机器内存就一定解决。”**如果受限的是容器额度、运行时堆或专用显存，只加主内存未必有效。
- **“重启后好了，就修复了。”**重启可能暂时释放资源，但泄漏、无界缓存或峰值超限可能再次出现。
- **“打开交换空间或清缓存就能永远不 OOM。”**这些机制有适用范围和性能代价；不能保证解除其他层的上限，也不能清掉仍在使用的数据。

学习顺序：先区分内存、显存和硬盘，再理解进程、运行时、容器各自的资源边界，最后学习峰值监控、垃圾回收、泄漏分析与容量规划。
