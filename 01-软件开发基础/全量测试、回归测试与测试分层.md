# 全量测试、回归测试与测试分层

## 一句话解释

**全量测试通常指：针对指定版本，在约定的环境与范围内，执行整套已定义的测试，而不只测本次修改涉及的几个功能。**

它强调“测试范围”，不是某一种专用测试工具，也没有一个能适用于所有项目的“全量”按钮。英文可根据语境说 running the full test suite（运行完整测试套件）或 full regression testing（全量回归测试），两者不应在所有场景下混用。

**全量测试不等于穷尽所有可能情况，更不等于保证软件没有错误。**

## 生活类比：修车后的检查

车子的刹车修好了：

- 只检查刚修的刹车问题是否消失，相当于修复确认。
- 检查维修是否影响了其他相关部件，相当于回归测试。
- 按这次约定的整套检验清单逐项检查，相当于在该清单范围内做全量测试。

即便清单全部通过，也不代表汽车在所有天气、所有路况、任何年限下都绝不会出问题。检查清单的范围与质量，同样重要。

## 1. 先理解测试用例与测试套件

**测试用例（Test Case）**是一个具体的检查场景，通常要说明前提、操作或输入，以及预期结果。执行后，再记录实际结果是否符合预期。

例如，直播平台的一个测试用例可以是：

```text
前提：课程需要登录才能观看，当前用户尚未登录。
操作：直接访问这门课程的播放页面。
预期：不能直接播放，应按产品规则进入登录或鉴权流程。
```

这是一个用例，不是完整测试方案。登录成功后的播放、退出登录后的访问、没有课程权限时的访问，都可能需要其他用例。

**测试套件（Test Suite）**是组织在一起的一组用例，例如登录测试套件、直播测试套件、后端自动化测试套件。

“跑全量”通常意味着把约定套件的用例都执行，而不是只挑选其中一部分。若用例被跳过、环境导致无法运行、执行提前终止，应如实披露，不算这些用例已经通过。

## 2. “全量”的范围必须先说清楚

不同团队说“全量”，可能分别指：

| 说法 | 实际可能包含什么 | 不能直接推断什么 |
|---|---|---|
| 后端全量单元测试 | 后端现有的全部单元测试 | 前端、真实数据库、浏览器流程也测过了 |
| 全量自动化测试 | 约定的全部自动化套件及配置组合 | 人工体验检查、压力和安全专项也包含在内 |
| 全量回归测试 | 本次确定的完整回归用例集合 | 所有潜在缺陷都能被发现 |
| 版本全量验收 | 按约定清单检查业务、环境及其他交付条件 | 线上所有真实条件已被完全复现 |

要问清至少四件事：**测哪个版本、哪些模块、哪些环境、哪些用例集合。**

例如：测试库里只有 30 条登录用例，就算 30 条全部通过，也不能称为“直播、支付、红包、后台管理全部测试通过”。

“全量数据核对”“全量发布”也不是全量测试：前者强调数据检查范围，后者强调让全部目标用户或实例使用新版本。

## 3. 和冒烟、回归、单元、端到端测试的区别

这些词描述的维度不同，并不是互相排斥的几种选项。

| 名称 | 主要回答的问题 | 直播平台教学例子 |
|---|---|---|
| 冒烟测试（Smoke Test） | 最关键的基本功能能不能工作，值得继续深入测吗？ | 能启动、打开首页、完成基本登录 |
| 修复确认（Confirmation Testing） | 刚修的那个错误还会不会出现？ | 原来登录报错的场景，现在是否正常 |
| 回归测试（Regression Testing） | 改动有没有让原本正常的行为变坏？ | 改登录后，讲师后台和课程权限是否仍正常 |
| 单元测试（Unit Test） | 一小块逻辑是否符合预期？ | 红包额度计算是否正确，使用纯测试数据 |
| 集成测试（Integration Test） | 多个组件连接起来能否正确合作？ | 登录服务与测试数据库是否正确交互 |
| 端到端测试（End-to-End，E2E） | 一条约定的完整业务链路能否走通？ | 测试用户登录、选课、进入直播、退出 |
| 全量测试 | 在约定范围里，这次执行的是不是整套用例？ | 执行所有纳入计划的用例，而非只测登录 |

E2E 中的 2 表示英文 to，常读作“E-two-E”。“端到端”的端点也要约定：从浏览器到后端，是否包括真实第三方系统，不能只看名称猜测。

因此，可以说“全量单元测试”，也可以说“全量端到端测试”。前面的“全量”描述范围，后面的词描述检查的层次或方式。

**回归强调目的，全量强调范围。**回归可以只选择受影响的用例，也可以运行约定的整套回归用例。[软件测试基础级大纲，第 2.2.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

单元与集成的基础区别也可参考 [Microsoft 测试说明](https://learn.microsoft.com/en-us/dotnet/core/testing/)。以上直播平台例子为教学设计，不是实际项目的测试结果。

## 4. 为什么只改登录，也可能需要更广泛的测试

登录功能可能共享用户身份、会话和权限逻辑。一次修改除了影响登录页面，还可能影响：

- 普通用户进入课程和直播间。
- 讲师进入自己的管理页面。
- 管理员查看和修改后台数据。
- 用户退出后，旧会话能否继续使用。
- 未授权用户是否能越权读取他人数据。
- 与用户身份关联的订单或红包领取资格。

测试范围不能只按“改了几个文件”决定，还要看它影响哪些业务依赖。共享组件、权限体系、数据库结构或基础依赖发生变化时，通常更有理由扩大验证范围。

不过，也不意味着每改一段文字都必须立即跑几小时全量测试。应依据风险、执行成本和发布要求安排。

## 5. 一次实际测试通常怎样进行

1. **固定对象与范围**：记录代码提交或构建版本，确定用例、浏览器和环境清单。
2. **准备环境和数据**：使用隔离的测试账号、数据库和适用的第三方测试环境。
3. **执行测试**：按计划运行自动化测试，完成需要人工判断的项目；必要时分批或并行执行。
4. **收集证据**：保留用例结果、日志和必要截图，区分失败、跳过、阻塞与未执行。
5. **修复并重测**：先确认原错误是否修复，再按影响范围做回归；代码改动后，旧结果不能自动证明新版本通过。
6. **报告剩余风险**：说明哪些通过、哪些没测、为什么没测，以及哪些问题阻止发布。

分片运行也可以最终覆盖全量，但必须确认所有分片都结束并汇总结果。只完成其中一个分片，不能说全套已完成。

## 6. 看到 `pnpm test` 就意味着跑全量了吗

**不一定。命令名称不能代替测试范围说明。**

pnpm 是 JavaScript 项目常见的包管理工具。`pnpm run test` 调用的是项目配置文件 `package.json` 中名为 `test` 的脚本；具体运行哪些测试，取决于脚本和被调用工具的配置。[pnpm 官方说明](https://pnpm.io/cli/run)

例如，它可能只运行后端单元测试，浏览器测试则由另一个脚本运行。即使脚本名叫 `test:all`，也需要核对它实际包含什么。

Playwright 是常用的浏览器自动化测试工具。其运行范围会受到配置、文件选择和项目选择等条件影响；它支持只跑指定文件、只重跑失败用例、限定项目以及分片执行。[Playwright 命令行文档](https://playwright.dev/docs/test-cli)

因此，判断一次执行是不是约定范围内的全量，需要同时看：

- 实际命令和配置，而不只是命令名称。
- 发现和选择了哪些用例，是否存在过滤或跳过。
- 需要运行的项目、环境和分片是否全部完成。
- 是否因为报错、超时或提前退出而剩下未执行项目。

本笔记只是解释，没有运行上述项目测试命令。

## 7. 怎样看懂“全部通过”的测试报告

下面是一份**虚构的教学示例**：

```text
目标版本：示例版本 A
环境：预发布环境，测试账号和模拟第三方支付
计划用例：500
通过：480
失败：0
跳过：10
因环境问题阻塞、未执行：10
未纳入本次范围：真实付款、大规模压力测试
```

准确结论是：**已完成的 480 条用例通过，另有 20 条尚未验证；真实付款和压力能力没有在本次得到验证。**

不能写成“500 条全量测试全部通过，平台完全没问题”。

还要注意“重试后通过”的不稳定用例。第一次失败、第二次成功，可能与网络、等待时机、共享状态或并发有关；应单独说明，而不是把不稳定性隐藏在一个绿色结果里。

“报告对应哪个代码版本”也很重要。测试通过后又改了代码，至少需要按影响范围重新验证，不能把旧版本报告直接当成新版本的证明。

## 8. 全量通过，不代表覆盖率 100%，也不代表没有错误

“全部现有用例都执行并通过”和“软件全部行为都验证过”是不同的事情。

- 某个重要功能可能根本没有对应测试。
- 用例可能只覆盖正常流程，没覆盖异常或边界。
- 预期结果可能写错，或者检查得太宽松。
- 测试时用模拟对象替代了外部系统，没有验证真实连接。
- 本地和生产环境的权限、数据规模、网络与配置可能不同。

**代码覆盖率（Code Coverage）**衡量测试执行触及代码的情况，例如运行过多少行或分支；它不是业务正确率，也不能仅凭百分比证明检查充分。

普通复杂软件通常无法穷尽所有输入、状态和环境组合；测试能发现错误，却不能据“没发现错误”证明错误不存在。[软件测试原则，第 1.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

构建成功、类型检查通过和代码规范检查通过，同样是有价值的检查，但它们不能替代业务运行测试。参见 [[ESLint与JavaScript静态代码检查]]。

## 9. 全量测试与生产发布、金丝雀的关系

测试可以在本地或持续集成环境执行，也可以针对测试、预发布环境执行。“全量”不等于必须在生产服务器上运行。

CI = Continuous Integration，持续集成，逐字母读 C-I；常用于代码变更后自动执行构建和检查。可以安排快速检查先反馈，再根据风险运行更大范围的测试，或在定时任务、发布前补充完整套件。这是常见安排示例，不是每个项目唯一正确的顺序。

[[金丝雀发布、灰度发布与渐进式交付|金丝雀发布]]则强调先让少量真实流量使用新版本，观察结果再扩大范围；它不是全量测试的另一种名称，也不能替代发布前测试。

**涉及发红包、付款、发短信、删除或批量修改数据的测试，可能真的产生外部影响。**应优先使用隔离环境、测试数据和适用的第三方沙箱；如果只是模拟外部响应，报告必须写明模拟边界。

生产验证需另行明确授权、范围和停止条件，不能因为用户问“全量测试是什么”就连接生产服务器或执行测试。本次未访问任何生产服务器，也未触发真实业务操作。

即便约定套件全部通过，上线仍需要考虑配置、监控、备份、回滚和风险接受。参见 [[开发、测试、预发布与生产环境]]、[[软件供应链：代码签名、SBOM与发布门禁]]。

## 10. 学习建议：听到“全量测试通过”，问这五句话

1. **这个“全量”包含哪些模块和测试层次？**
2. **测的是哪个版本、哪个环境，是否用了模拟服务？**
3. **计划多少条，执行多少条，多少通过、失败、跳过或阻塞？**
4. **登录权限、核心业务和异常情况，有哪些明确验证证据？**
5. **哪些没有测，是否还有阻止上线的问题？**

现在先记住三个区分：**全量看范围，回归看改动影响，端到端看业务链路。**
