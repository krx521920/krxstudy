# 系统代理、VPN 与端口

> [!summary] 一句话结论
> **“系统代理”是一项操作系统设置，它告诉愿意遵守该设置的应用先把网络请求交给某个代理地址；“梯子”通常是实际接收、加密和转发流量的客户端与远程服务；“端口”则是这些程序在一台设备上收发网络数据的编号入口。**

这三个概念经常同时出现，但它们不是同一个东西。

---

## 先建立最小理解

假设代理软件在你的电脑上监听：

~~~text
127.0.0.1:7890
~~~

这串地址分成两部分：

- 127.0.0.1：表示你自己的电脑；
- 7890：表示代理软件打开的某个网络入口，也就是端口。

当 Windows 系统代理被设置为这个地址时，愿意读取系统代理的应用会这样发送请求：

~~~mermaid
flowchart LR
    App["浏览器或其他应用"] --> System["Windows 系统代理设置<br/>使用 127.0.0.1:7890"]
    System --> Local["本机代理客户端<br/>监听 127.0.0.1:7890"]
    Local --> Node["远程代理/VPN 节点"]
    Node --> Site["目标网站"]
~~~

系统代理本身不负责转发数据。它更像一张“路线通知单”，真正转发数据的是监听 7890 端口的代理客户端。

> [!important] Clash 的“系统代理”按钮通常做什么
> 在 Clash 类客户端的传统系统代理模式中，这个按钮通常只是修改 Windows 的用户代理地址、端口和绕过规则，例如指向 127.0.0.1:7890。它不会凭空建立远程隧道；节点连接、规则判断、加密和转发仍由正在运行的 Clash 客户端负责。不同 Clash 分支和版本的具体设置方式可能不同，因此这里说的是常见行为。

| Clash/代理客户端 | Windows 系统代理 | 常见结果 |
|---|---|---|
| 运行 | 开启 | 遵守系统代理的应用把请求交给本地客户端 |
| 运行 | 关闭 | 只有单独配置代理的应用会使用它；TUN 模式另算 |
| 已退出 | 仍开启 | 应用继续连接失效的本地端口，可能无法联网 |
| 已退出 | 已关闭 | 应用通常恢复直连 |
| TUN 开启 | 系统代理关闭 | 很多流量仍可能被虚拟网卡和路由接管 |

如果代理客户端已经退出，但系统代理仍指向 127.0.0.1:7890，应用就会把请求发给一个没有程序接收的入口，于是出现“开着系统代理却上不了网”。

---

## “梯子”到底是什么

“梯子”是日常口语，不是严格的网络协议名称。人们可能用它指：

- 一个本地代理客户端；
- 一项远程代理服务；
- 一组服务器节点；
- VPN 客户端；
- TUN 模式；
- 浏览器代理扩展；
- 上面几项的组合。

因此只说“我开了梯子”，还不能判断流量怎样走。至少要继续看：

- 它是否打开了 Windows 系统代理；
- 它是否启用了 TUN/VPN 模式；
- 当前是规则、全局还是直连模式；
- 本地监听的是什么协议和端口；
- 是否允许局域网设备连接；
- DNS 是否也经由代理处理。

## 没有代理时怎样联网

正常直连可以简化成：

~~~mermaid
flowchart LR
    App["应用"] --> Network["路由器 / 运营商网络"]
    Network --> Site["目标网站"]
~~~

例如访问 HTTPS 网站时，应用通常会：

1. 通过 DNS 查询域名对应的 IP；
2. 选择一个本机临时源端口；
3. 连接目标服务器的 443 端口；
4. 建立 TLS 加密连接；
5. 发送 HTTP 请求；
6. 接收响应。

这里仍有路由器、运营商和其他网络设备参与，只是没有由你主动配置的应用代理或 VPN 隧道。

---

## 使用本地代理时怎样联网

很多代理客户端不会让浏览器直接连接远程节点，而是先在本机启动一个代理服务：

~~~text
HTTP 代理：127.0.0.1:7890
SOCKS 代理：127.0.0.1:7891
控制面板：127.0.0.1:9090
~~~

数字只是示例，不同软件的默认值和用户配置可能完全不同。

流量路径可能是：

~~~mermaid
sequenceDiagram
    participant A as 应用
    participant L as 本地代理客户端
    participant R as 远程节点
    participant W as 目标网站

    A->>L: 把访问目标交给本地代理端口
    L->>R: 通过代理协议建立加密或封装连接
    R->>W: 代表用户连接目标网站
    W-->>R: 返回数据
    R-->>L: 通过隧道返回
    L-->>A: 把响应交给应用
~~~

目标网站通常看到的是远程节点的公网出口 IP，而不是你家庭宽带的公网出口 IP。

## 系统代理是什么

### 它是一项“配置”，不是一条隧道

Windows 的系统代理通常包含：

- 代理服务器地址；
- 代理端口；
- 自动检测设置；
- PAC/设置脚本地址；
- 不走代理的例外列表。

Windows 设置入口通常是：

~~~text
设置
→ 网络和 Internet
→ 代理
~~~

微软官方文档说明，Windows 支持自动检测、设置脚本和手动代理三类配置。

### 哪些应用会受影响

系统代理只会影响愿意读取并支持这套配置的应用。

可能出现：

~~~text
浏览器能走代理
Git 不走
某个游戏不走
Windows 服务不走
WSL 中的命令也不走
~~~

原因不是系统代理“失效”，而是不同程序可能：

- 使用 Windows 系统代理；
- 使用自己的代理设置；
- 只读取 HTTP_PROXY 等环境变量；
- 使用 WinHTTP 等另一套 Windows 网络配置；
- 直接建立 TCP/UDP 连接；
- 运行在 WSL、容器或虚拟机的独立网络环境中；
- 根本不支持所配置的代理协议。

所以：

> **系统代理不是“强制接管整台电脑所有网络流量”的总开关。**

---

## 自动代理、PAC 和手动代理

### 自动检测

Windows 或应用尝试从当前网络发现代理设置。企业和校园网络可能使用它，家庭用户不一定需要。

### PAC 设置脚本

**PAC（Proxy Auto-Configuration，代理自动配置）**是一段规则脚本，用来判断某个 URL：

- 走哪个代理；
- 直接连接；
- 在多个代理中怎样选择。

可以把 PAC 理解成一张自动分流表。

### 手动代理

用户直接填写：

~~~text
代理地址：127.0.0.1
端口：7890
~~~

本地代理客户端常通过这种方式接入 Windows 系统代理。

---

## 开启梯子时通常发生了什么

不同软件实现不同，但常见步骤是：

1. 代理客户端程序启动；
2. 程序在本机打开一个或多个监听端口；
3. 客户端连接选中的远程节点；
4. 客户端打开系统代理，或创建 TUN/VPN 虚拟网卡；
5. 分流规则判断每个目标应直连、代理还是阻止；
6. 被代理的流量通过远程节点访问目标；
7. 网站把远程节点的地址视为连接来源。

关闭时应反向清理：

1. 停止接收新流量；
2. 关闭本地监听端口；
3. 断开远程节点；
4. 关闭系统代理或移除虚拟路由；
5. 恢复 DNS 和网络设置。

如果程序异常退出，第 4、5 步可能没有完成，就会留下“残余代理设置”。

## 系统代理、TUN 和 VPN 有什么区别

### 系统代理模式

应用主动把请求交给代理。

优点：

- 结构简单；
- 对浏览器和常见 HTTP 应用很方便；
- 通常容易开关；
- 不必接管所有网络包。

限制：

- 应用可能不读取系统代理；
- 某些非 HTTP 协议无法使用；
- UDP、游戏和特殊程序可能不受影响；
- DNS 行为取决于应用与代理协议。

### TUN 模式

**TUN** 是一种虚拟网络接口。代理客户端把它表现得像一张虚拟网卡，再通过路由规则接收 IP 流量。

简化路径：

~~~mermaid
flowchart LR
    App["应用<br/>以为自己在正常联网"] --> OS["操作系统网络栈"]
    OS --> TUN["TUN 虚拟网卡"]
    TUN --> Client["代理客户端"]
    Client --> Node["远程节点"]
    Node --> Site["目标"]
~~~

应用不需要主动支持系统代理，因此覆盖范围通常更广。

但它也更容易影响：

- UDP；
- 游戏；
- DNS；
- 局域网访问；
- Docker、WSL 和虚拟机路由；
- 防火墙；
- 其他 VPN 软件。

### VPN 模式

**VPN（Virtual Private Network，虚拟专用网络）**通常建立一条网络层隧道，通过虚拟接口和路由决定哪些 IP 流量进入隧道。

TUN 是实现网络隧道的一种接口机制；“VPN”描述的范围更广，两者不能简单看成完全同义。

### 对比表

| 对比 | 系统代理 | TUN/网络层代理 | VPN |
|---|---|---|---|
| 怎样接入 | 应用读取代理设置 | 虚拟网卡和路由接管 | VPN 虚拟接口和路由 |
| 覆盖应用 | 取决于应用是否支持 | 通常较广 | 通常较广 |
| HTTP/HTTPS | 常见 | 可以 | 可以 |
| UDP | 常常有限或不处理 | 视实现而定 | 视协议与配置而定 |
| DNS | 取决于应用/代理 | 常由客户端接管 | 可由 VPN 配置接管 |
| 对本地网络影响 | 通常较小 | 可能较大 | 可能较大 |
| 排查难度 | 相对直观 | 更复杂 | 更复杂 |

“VPN 一定安全”也不准确。安全性取决于隧道协议、加密、证书、服务提供者、终端安全和配置。

## 规则模式、全局模式和直连模式

### 规则模式

客户端根据域名、IP、进程或规则集决定：

~~~text
目标 A → 直连
目标 B → 代理
局域网地址 → 直连
广告域名 → 阻止
~~~

优点是速度、访问能力和本地网络兼顾；缺点是规则可能过期或判断错误。

### 全局模式

所有能够被客户端接管的流量尽量走同一代理节点。

影响包括：

- 更多网站看到代理出口 IP；
- 本地常用网站可能变慢；
- 流量消耗更高；
- 局域网和本地服务可能需要额外排除；
- 账号可能因登录地区突然变化触发安全检查。

### 直连模式

客户端可能仍在运行，但规则让流量不经过远程代理。系统代理开着不等于所有网站一定经过远程节点，最终还要看客户端模式。

### VPN 的全隧道与分流

微软把 VPN 路由常见模式区分为：

- **Force Tunnel（强制/全隧道）**：所有匹配范围的流量进入 VPN；
- **Split Tunnel（拆分隧道）**：只有指定路由进入 VPN，其余使用物理网络。

这和代理客户端的“全局/规则”概念相似，但实现层次不同。

## HTTP 代理、SOCKS5 和 Mixed Port

### HTTP 代理

应用使用 HTTP 协议与代理沟通。它很适合 HTTP 请求，也常通过 CONNECT 方法为 HTTPS 建立双向隧道。

### SOCKS5 代理

**SOCKS5** 更接近通用的连接转发协议，不要求里面一定是 HTTP。它可以让支持 SOCKS 的应用请求代理连接目标主机和端口。

DNS 由本地还是远程解析，取决于应用用法和 SOCKS 配置。例如有的软件会区分 socks5 与 socks5h。

### Mixed Port

一些客户端提供 **Mixed Port（混合端口）**，同一个本地端口可以识别并接受多种代理协议。

不要仅根据端口数字猜协议。即使地址和端口正确，应用发送 HTTP 代理格式，而端口只接受 SOCKS，也会连接失败。

---

## HTTPS 经过代理还加密吗

通常仍然加密。

使用 HTTP 代理访问 HTTPS 时，客户端常先向代理发送 CONNECT 请求，请代理建立到目标主机和端口的隧道。之后 TLS 加密数据在隧道中传输。

~~~mermaid
sequenceDiagram
    participant B as 浏览器
    participant P as HTTP 代理
    participant S as HTTPS 网站

    B->>P: CONNECT example.com:443
    P->>S: 连接 example.com:443
    P-->>B: 隧道已建立
    B->>S: 通过隧道进行 TLS 握手
    B->>S: 加密的 HTTPS 请求
    S-->>B: 加密的 HTTPS 响应
~~~

正常端到端 TLS 下，转发隧道的中间服务通常不能直接读取 HTTPS 正文，但仍可能看到：

- 连接时间；
- 流量大小；
- 目标 IP；
- 某些情况下的目标域名；
- 你的入口 IP；
- 连接持续时间。

### 什么时候代理可能看到 HTTPS 内容

如果设备被安装并信任了某个自定义根证书，同时代理进行 TLS Inspection/MITM（TLS 检查/中间人解密），代理可能分别与客户端和网站建立两条 TLS 连接，从而检查内容。

这在受管企业网络中可能是合规安全措施，在来源不明的软件中则是高风险信号。不要随意安装不理解的根证书，也不要为了消除证书错误而关闭 TLS 验证。

---

## DNS 会怎样受影响

**DNS（Domain Name System，域名系统）**把域名转换为 IP 地址。

代理开启后，DNS 可能有几种路径：

1. 应用在本地解析，再把 IP 交给代理；
2. 应用把域名交给代理，由远程侧解析；
3. TUN/VPN 客户端接管 DNS；
4. 某些域名直连解析，另一些通过代理解析；
5. 浏览器使用自己的加密 DNS 设置。

如果访问流量走代理，但 DNS 查询仍直接发给本地网络，就可能出现：

- DNS 泄漏；
- 本地结果与远程网络不一致；
- 域名解析到不可达地址；
- 规则根据域名判断时出现偏差。

DNS 问题和“代理端口不通”是两类问题，不要混在一起排查。

## 端口到底是什么

### IP 找设备，端口找程序

最常用的类比是：

~~~text
IP 地址 = 一栋办公楼的地址
端口 = 楼里的部门窗口
协议 = 到窗口后使用的办事规则
~~~

例如：

~~~text
127.0.0.1:7890
~~~

表示：

- 设备：自己的电脑；
- 网络入口：7890；
- 还必须知道它使用 TCP 还是 UDP，以及 HTTP/SOCKS 等上层协议。

### 端口范围

TCP 和 UDP 端口号都是 16 位数字，范围为：

~~~text
0 到 65535
~~~

IANA 将它们分为：

| 范围 | 名称 | 常见理解 |
|---|---|---|
| 0–1023 | System Ports | 常见标准系统服务 |
| 1024–49151 | User Ports | 已注册或普通应用服务 |
| 49152–65535 | Dynamic/Private Ports | 常用于临时源端口或私有用途 |

这是注册管理分类，不表示应用绝对不能采用其他范围。

### TCP 端口和 UDP 端口不是同一个入口

同一个数字可以分别存在：

~~~text
TCP 7890
UDP 7890
~~~

因为 TCP 和 UDP 是不同传输协议。防火墙规则也经常分别控制它们。

---

## 一次连接其实经常有多个端口

很多初学者只看到 7890，就以为整个互联网都使用 7890。实际上可能同时出现四类端口。

### 1. 应用的临时源端口

浏览器主动连接本地代理时，操作系统可能分配：

~~~text
127.0.0.1:53124
~~~

53124 是此次连接的临时源端口，通常不需要用户手工设置。

### 2. 本地代理监听端口

~~~text
127.0.0.1:7890
~~~

代理客户端在这里等待应用连接。

### 3. 远程节点服务端口

本地代理客户端还要连接远程服务器，例如：

~~~text
node.example:443
~~~

这里的 443 是远程代理服务监听端口，不是本机 7890。

### 4. 目标网站端口

远程节点最终可能访问：

~~~text
example.com:443
~~~

这个 443 是目标 HTTPS 网站的服务端口。

完整路径可以想成：

~~~text
浏览器临时端口 53124
→ 本地代理端口 7890
→ 远程节点端口 443
→ 目标网站端口 443
~~~

两个 443 即使数字相同，也属于不同设备上的不同连接。

## 修改代理端口会有什么影响

假设原来：

~~~text
代理客户端监听：127.0.0.1:7890
系统代理指向：127.0.0.1:7890
~~~

如果只把客户端改为 7891，却没有修改系统代理：

~~~text
代理客户端监听：127.0.0.1:7891
系统代理仍指向：127.0.0.1:7890
~~~

应用仍然敲 7890 这个“旧窗口”，自然没人响应。

因此要保持三件事一致：

- 地址；
- 端口；
- 代理协议。

端口数字本身通常不会让代理明显更快。把 7890 改成 9999，主要作用是避免冲突或配合配置，不是网络加速。

---

## 端口冲突是什么

如果两个程序都尝试监听同一个：

~~~text
IP + 传输协议 + 端口
~~~

后启动的程序通常会报告：

~~~text
address already in use
端口已被占用
无法绑定端口
~~~

例如：

- 代理 A 已监听 127.0.0.1:7890；
- 代理 B 也尝试监听 127.0.0.1:7890；
- 代理 B 启动失败。

少数程序会使用特殊的端口复用机制，但初学阶段可以先记住：同一入口通常只能有一个监听者。

## 127.0.0.1、0.0.0.0 和“允许局域网”

### 127.0.0.1

**Loopback（回环地址）**，只指向本机。

代理监听：

~~~text
127.0.0.1:7890
~~~

通常只有这台电脑上的程序能连接，安全边界相对清楚。

### 0.0.0.0

服务监听：

~~~text
0.0.0.0:7890
~~~

通常表示在本机所有 IPv4 网络接口上接受连接。局域网网卡、虚拟网卡等都可能包含在内。

这不等于一定直接暴露到整个互联网，外部是否可达还受路由器 NAT、防火墙和网络结构影响；但它明显扩大了可访问范围。

### 允许局域网

代理客户端的“Allow LAN（允许局域网）”通常会改变监听地址或防火墙行为，让手机、平板等同一局域网设备把你的电脑作为代理。

风险包括：

- 局域网其他设备未经许可使用你的流量；
- 未设置认证时被滥用；
- 代理控制面板或 API 一起暴露；
- 公共 Wi‑Fi 中被陌生设备发现。

没有明确需求时，代理端口优先只监听 127.0.0.1。

---

## 防火墙与端口的关系

### 监听不等于一定可访问

程序打开端口只是第一步。连接还可能被以下环节阻止：

- Windows 防火墙；
- 安全软件；
- 路由器；
- 云服务器安全组；
- 公司网络策略；
- 代理客户端自己的访问控制。

### 入站与出站

- **入站**：其他设备主动连接你的程序；
- **出站**：你的程序主动连接远程节点或网站。

本机浏览器连接 127.0.0.1 通常属于本机回环通信；远程节点连接属于代理客户端的出站通信。

“开了梯子”通常不等于主动在路由器上做了公网端口映射，也不等于别人自动能从互联网连接你的电脑。

---

## 开代理后对上网有什么影响

### 1. 公网出口 IP 改变

被代理的网站通常看到远程节点的公网 IP。

可能影响：

- 网站显示地区；
- 搜索结果与语言；
- 流媒体或内容可用性；
- 广告地域；
- 登录安全提醒；
- 验证码频率；
- 支付、银行和风控判断。

规则模式下，不同网站可能分别看到你的直连 IP 和代理 IP。

### 2. 延迟增加或变化

流量多走了一段路：

~~~text
你 → 远程节点 → 网站
~~~

节点距离、线路拥塞、加密开销和服务器负载都会影响延迟。

代理可能让某些线路更顺，也可能让原本很近的网站变慢。不能只用“是否开代理”预测速度。

### 3. 带宽和流量消耗

代理服务可能有：

- 速度上限；
- 月流量限制；
- 高峰拥塞；
- 单连接限制；
- UDP 支持限制。

全局模式通常比规则模式转发更多流量。

### 4. 稳定性依赖增加

以前只依赖：

~~~text
本地网络 → 网站
~~~

现在还依赖：

~~~text
本地代理程序
→ 节点配置
→ 节点可用性
→ 代理协议
→ 分流规则
→ DNS
→ 远程线路
~~~

任何一环出错都可能表现成“网络打不开”。

### 5. 电量和资源消耗

TUN、加密、大量规则匹配和持续连接会消耗 CPU、内存和电量。普通电脑上可能不明显，移动设备或高流量场景更容易观察到。

---

## 对隐私和安全有什么影响

### 谁可能看到什么

| 参与者 | 直连时可能看到 | 通过完整隧道时可能看到 |
|---|---|---|
| 本地网络/运营商 | 目标 IP、时序、流量；DNS 取决于配置 | 通常看到你连接代理/VPN 节点及流量特征；DNS 泄漏时仍可能看到查询 |
| 代理/VPN 服务 | 不参与 | 入口 IP、目标元数据、时间和流量；明文协议内容可能可见 |
| 目标网站 | 你的直连出口 IP | 远程节点出口 IP |
| HTTPS 内容 | 受 TLS 保护 | 正常端到端 TLS 下仍受保护，除非被受信任中间证书解密 |

代理不是“绝对匿名按钮”：

- 网站仍可通过登录账号、Cookie、浏览器指纹识别你；
- 服务提供者可能记录连接日志；
- DNS 或部分流量可能直连；
- 规则模式会产生不同出口；
- 恶意本机客户端有很高的系统可见性。

### 不要随意关闭证书验证

遇到 TLS 或证书错误时，不要直接：

- 关闭 HTTPS 验证；
- 接受来源不明的根证书；
- 长期使用跳过证书检查的参数。

证书错误可能表示系统时间、代理检查、杀毒软件、公司网络或真正的中间人问题，应先查清原因。

### 订阅链接和控制端口也敏感

代理订阅链接可能包含访问凭证。不要公开截图、上传到公开仓库或发送给陌生人。

客户端的控制 API、Web 面板和日志也可能包含节点、域名和连接信息，不应随意暴露到 0.0.0.0。

---

## 对浏览器、Git、pnpm、pip 等有什么影响

### 浏览器能用，不代表终端工具能用

浏览器可能遵守 Windows 系统代理，但命令行工具可能需要：

- 自己的配置；
- 环境变量；
- 启动参数；
- TUN/VPN 接管；
- 直接连接。

因此经常出现：

~~~text
网页能打开
但 git clone、pnpm install 或 pip install 超时
~~~

### 常见代理环境变量

不少命令行工具会识别：

~~~text
http_proxy
HTTPS_PROXY
ALL_PROXY
NO_PROXY
~~~

但不同工具支持的大小写、协议和语义并不完全一致，应查各自官方文档。

**NO_PROXY** 用来声明不经过代理的地址，例如：

~~~text
localhost,127.0.0.1,::1
~~~

这对本地开发很重要。

PowerShell 当前窗口的示例：

~~~powershell
$env:http_proxy = "http://127.0.0.1:7890"
$env:HTTPS_PROXY = "http://127.0.0.1:7890"
$env:NO_PROXY = "localhost,127.0.0.1,::1"
~~~

关闭该 PowerShell 窗口后，这种会话级变量通常消失。当前窗口中可以移除：

~~~powershell
Remove-Item Env:http_proxy -ErrorAction SilentlyContinue
Remove-Item Env:HTTPS_PROXY -ErrorAction SilentlyContinue
Remove-Item Env:ALL_PROXY -ErrorAction SilentlyContinue
~~~

不要机械照抄端口，应使用客户端实际提供的地址、端口和协议。

### 为什么 HTTPS_PROXY 的值可能以 http:// 开头

变量名 HTTPS_PROXY 常表示“访问 HTTPS 目标时使用哪个代理”；值开头的 http:// 描述“客户端怎样与代理沟通”。

因此下面不一定矛盾：

~~~text
HTTPS 目标
→ 通过 HTTP 代理的 CONNECT 隧道
~~~

### Git 的额外配置

Git 可能读取环境变量，也可能保存自己的 http.proxy 配置。

排查可以先查看：

~~~powershell
git config --global --get http.proxy
git config --global --get https.proxy
~~~

如果确认是过期配置，可以取消：

~~~powershell
git config --global --unset http.proxy
git config --global --unset https.proxy
~~~

不要不加判断地删除公司统一配置。还要注意，Git 的 HTTP 代理设置主要影响 HTTP/HTTPS remote；SSH remote 是另一条协议路径。

### pnpm、npm、pip 和 conda

这些工具可能分别读取：

- 环境变量；
- 自己的配置文件；
- 系统代理；
- 软件源/镜像配置。

以前手工写入的永久代理即使系统代理已关闭，也可能继续生效。反过来，某个工具完全不读取系统代理，也可能需要单独设置。

详见 [[Node.js与pnpm]] 与 [[Anaconda与Python环境管理]]。

### Docker、WSL 和虚拟机

它们可能拥有：

- 独立网络命名空间；
- 虚拟网卡；
- 自己的 DNS；
- 自己的 localhost；
- 独立代理配置。

Windows 的 127.0.0.1 在某些架构中不一定等于容器或虚拟机内部所理解的 127.0.0.1。不要假设 Windows 系统代理必然自动传进所有环境。

## 对本地开发端口有什么影响

开发 Web 项目时常见：

~~~text
前端：http://localhost:3000
后端：http://localhost:8000
代理：http://127.0.0.1:7890
~~~

它们使用不同端口，可以同时运行。

可能的问题有：

### localhost 被错误送进代理

如果代理规则没有排除 localhost，访问本地开发服务可能绕到代理，导致：

- 页面打不开；
- 请求变慢；
- OAuth 回调失败；
- 开发服务器来源判断异常；
- 本地 API 请求被远程节点处理。

应把 localhost、127.0.0.1 和 ::1 加入绕过列表。

### 端口碰撞

如果代理、前端和后端碰巧都配置成 7890，只有一个程序通常能成功监听。

### WebSocket/HMR 失败

[[Webpack与HMR|HMR]] 开发服务器可能使用 [[TCP、HTTP、HTTPS与WebSocket|WebSocket]]。中间代理不支持升级、超时太短或规则错误时，普通网页能打开，热更新连接却不断断开。

### HTTPS 本地证书问题

本地开发证书、企业 TLS 检查和代理证书可能相互影响，导致浏览器或工具报告证书不受信任。

## 关掉梯子后为什么可能断网

最常见原因：

~~~text
代理客户端已关闭
但 Windows 系统代理仍指向 127.0.0.1:7890
~~~

浏览器继续把流量交给已经不存在的本地服务。

另一类原因是：

- TUN 虚拟网卡没有正确关闭；
- 路由表残留；
- DNS 被改动后没有恢复；
- Git/npm 等工具留有永久代理；
- PAC 脚本仍启用；
- 多个代理/VPN 软件相互覆盖；
- 防火墙规则没有恢复。

恢复思路不是“到处重装”，而是逐层确认当前流量还被谁接管。

## 常见现象与原因

| 现象 | 优先怀疑 |
|---|---|
| 开着客户端能上网，关闭客户端全断 | 系统代理仍指向本地端口，或 TUN/DNS 没恢复 |
| 浏览器能上，Git/pip 不行 | 工具不读取系统代理，或另有过期配置 |
| Git 能上，浏览器不行 | 浏览器/系统代理配置错误，Git 单独配置仍有效 |
| 只有部分网站打不开 | 规则、DNS、节点、IPv6、网站风控 |
| 本地 localhost 打不开 | 没有绕过本地地址，或端口冲突 |
| 提示 connection refused | 目标 IP/端口没有程序监听，或程序拒绝 |
| 提示 timeout | 路径被阻断、节点不可达、协议不匹配或防火墙丢弃 |
| 提示 address already in use | 监听端口被占用 |
| 提示 certificate error | TLS 检查、自定义证书、时间或信任链问题 |
| 网站地区变化 | 被代理流量使用了远程出口 IP |
| 游戏或语音异常 | UDP/TUN/路由/MTU/延迟问题 |
| 手机连电脑代理失败 | 监听仅限 127.0.0.1、防火墙阻止或地址填错 |

## 怎样一步步排查

### 第 1 步：确认使用哪种模式

查看客户端：

- 系统代理是否开启；
- TUN/VPN 是否开启；
- 当前规则/全局/直连模式；
- 当前选择的节点；
- 本地代理协议与端口；
- 是否允许局域网。

不要同时改变五个选项，否则很难知道哪个变化解决了问题。

### 第 2 步：确认本地端口真的在监听

假设端口是 7890，可使用 PowerShell：

~~~powershell
Get-NetTCPConnection -State Listen -LocalPort 7890
~~~

或者：

~~~powershell
netstat -ano | findstr :7890
~~~

看到 LISTENING 只说明有程序监听，还要确认 PID 对应的确是代理客户端。

### 第 3 步：测试能否连接本地端口

~~~powershell
Test-NetConnection 127.0.0.1 -Port 7890
~~~

如果失败，常见原因：

- 客户端没启动；
- 实际端口不同；
- 监听的是 UDP；
- 地址不是 127.0.0.1；
- 客户端启动失败；
- 端口冲突。

### 第 4 步：显式测试代理

如果 7890 确实是 HTTP 代理，可以测试：

~~~powershell
curl.exe -x http://127.0.0.1:7890 https://example.com/
~~~

如果是 SOCKS5 端口，应使用对应 SOCKS 参数，不能把协议混用。

### 第 5 步：检查 Windows 系统代理

进入：

~~~text
设置 → 网络和 Internet → 代理
~~~

核对：

- 地址；
- 端口；
- 自动脚本；
- 例外地址。

### 第 6 步：检查应用自己的代理

分别查看：

- 浏览器代理设置；
- Git 配置；
- npm/pnpm 配置；
- pip/conda 配置；
- IDE；
- Docker Desktop；
- WSL 环境变量。

### 第 7 步：检查本地地址绕过

确认：

~~~text
localhost
127.0.0.1
::1
局域网网段
~~~

是否应该直连。

### 第 8 步：再检查 DNS、路由和证书

只有在本地端口、系统代理和应用配置确认无误后，再深入：

- DNS；
- IPv4/IPv6；
- TUN 路由；
- MTU；
- 防火墙；
- TLS 证书；
- 节点可用性。

## 三个具体例子

### 例子 1：关闭软件后浏览器断网

当前状态：

~~~text
系统代理 = 127.0.0.1:7890
代理客户端 = 已退出
~~~

浏览器把请求发到 7890，没有程序监听，于是失败。

解决方向：

- 重新启动客户端；
- 或关闭残留系统代理；
- 确认客户端以后正常退出时能恢复设置。

### 例子 2：浏览器正常，pnpm 下载失败

可能路径：

~~~text
浏览器 → 系统代理 → 成功
pnpm → 忽略系统代理/使用旧配置 → 超时
~~~

检查 pnpm/npm 配置、代理环境变量和 TUN 模式，而不是反复修改浏览器。

### 例子 3：本地网页能打开但 HMR 一直断

可能路径：

~~~text
HTML 请求成功
WebSocket 升级经过代理后失败
~~~

检查 localhost 绕过、WebSocket 支持、代理规则和开发服务器端口。

## 常见误区

### 误区 1：系统代理就是 VPN

不是。系统代理通常是应用层配置；VPN 通常在网络层通过虚拟接口和路由处理流量。

### 误区 2：开了系统代理，所有程序一定走代理

不是。应用可以忽略系统代理或使用另一套网络配置。

### 误区 3：端口 7890 是某种固定国际标准

不是。它只是一些软件常用的默认值或用户配置。必须以当前客户端显示为准。

### 误区 4：换一个端口就能提速

通常不能。端口主要用于区分服务，性能主要受线路、节点、协议、拥塞和硬件影响。

### 误区 5：开了代理等于电脑向公网开放 7890

不一定。监听 127.0.0.1 时通常仅本机可达；公网可达还需要监听范围、防火墙、NAT 和路由等条件。

### 误区 6：HTTPS 经过代理后一定变成明文

正常 CONNECT/TLS 隧道下不会。TLS 检查和受信任中间证书是另一种情况。

### 误区 7：网站看不到真实 IP 就完全匿名

不是。账号、Cookie、浏览器指纹、行为和泄漏流量仍能关联身份。

### 误区 8：浏览器能用说明整个网络配置正确

浏览器只代表浏览器的路径。终端、游戏、WSL、Docker 和系统服务可能走不同路径。

### 误区 9：关闭代理软件就一定恢复所有设置

正常退出通常会恢复，但崩溃、强制结束或多个软件互相覆盖时可能留下系统代理、路由、DNS或永久工具配置。

---

## 初学者的安全使用原则

1. 先学会区分系统代理模式与 TUN/VPN 模式；
2. 没有特殊需求时，先从规则模式和系统代理模式理解；
3. 本地代理端口优先只监听 127.0.0.1；
4. 不需要时不要开启 Allow LAN；
5. 不公开订阅链接、控制面板和日志；
6. 不随意安装来源不明的根证书；
7. 不为了消除错误而关闭 TLS 验证；
8. 将 localhost、127.0.0.1、::1 加入合理绕过；
9. 记录客户端实际地址、端口和协议；
10. 不要同时运行多个会修改系统代理或路由的工具；
11. 公司、学校网络应遵守组织安全与使用政策；
12. 修改永久 Git/npm/pip 配置前，先知道怎样查看和撤销。

## 学习建议

建议按这个顺序继续理解：

1. IP 地址、DNS 与端口；
2. TCP 和 UDP；
3. HTTP、HTTPS 与 TLS；
4. 客户端和服务器；
5. 代理与 VPN；
6. 路由表；
7. 防火墙与 NAT；
8. 虚拟网卡、容器和 WSL 网络。

先能画出一条请求实际经过的设备、地址与端口，再学习各种软件的按钮名称，会更不容易混乱。
