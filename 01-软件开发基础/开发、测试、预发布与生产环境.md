# 开发、测试、预发布与生产环境

> [!summary] 一句话解释
> **生产环境不是“把本地程序搬到一台更大的电脑”，而是程序开始面对真实用户、真实数据、真实网络、真实权限和真实故障；高并发只是生产问题中的一个小部分。**

很多程序在开发者电脑上运行正常，一上线就出问题。这不一定表示代码完全错误，而是因为程序实际行为由很多东西共同决定：

```text
程序行为
= 代码
+ 构建产物
+ 配置
+ 操作系统与运行时
+ 依赖服务
+ 网络
+ 权限和密钥
+ 数据
+ 流量
+ 发布与运维方式
```

本地环境只覆盖了其中一部分，生产环境则必须同时处理全部因素。

---

## 一、先纠正：“本地”和“开发”不是完全同义

### Local（本地）描述运行地点

“本地环境”通常指程序运行在开发者自己的电脑上，例如：

```text
http://localhost:5173
```

它回答的是：**程序在哪里运行？**

### Development（开发环境）描述运行目的

开发环境用于编写、调试和快速验证代码。它可以在开发者电脑上，也可以是一台共享的远程开发服务器。

它回答的是：**这个环境用来做什么？**

所以：

- 本地运行的 Vite 开发服务器，既是本地环境，也是开发环境；
- 公司云端的一台共享开发服务器，不是本地环境，但仍是开发环境；
- 在自己电脑运行 `vite build` 的产物，是本地生产构建测试，但不是真正生产环境；
- 真正服务外部用户、处理真实数据的系统，才是 Production（生产环境）。

## 二、常见环境分别是什么

| 环境 | 英文 | 主要用途 | 数据 | 谁通常使用 |
|---|---|---|---|---|
| 本地开发 | Local Development | 写代码、调试、快速试错 | 假数据或个人测试数据 | 开发者本人 |
| 集成/测试 | Integration / Test | 验证多个模块和服务能否协作 | 可重置测试数据 | 开发、测试和自动化程序 |
| 验收测试 | UAT，User Acceptance Testing（用户验收测试） | 让业务人员确认功能是否符合需求 | 脱敏或专门验收数据 | 产品、客户代表、业务人员 |
| 预发布 | Staging / Pre-production | 尽量模拟生产，做上线前最后验证 | 通常是隔离的仿真数据 | 开发、测试、运维 |
| 生产 | Production，常缩写为 Prod（生产） | 为真实用户提供正式服务 | 真实业务数据 | 客户和正式用户 |
| 灾备 | DR，Disaster Recovery（灾难恢复） | 主生产区域故障时恢复服务 | 生产数据副本或备份 | 运维与应急团队 |

不同团队的命名不完全相同。有的只有开发、测试、生产三个环境；有的会增加 QA、UAT、Staging、Canary 等环境。关键不在名称数量，而在于每个环境的目的、访问权限和数据边界是否明确。

### 理想的软件交付路线

```mermaid
flowchart LR
    Local["本地开发：快速反馈"] --> CI["CI：自动构建与测试"]
    CI --> Test["测试环境：集成验证"]
    Test --> Staging["预发布：模拟生产"]
    Staging --> Canary["生产金丝雀：少量真实流量"]
    Canary --> Prod["生产全量：正式用户"]
    Prod -. "出现严重问题" .-> Rollback["回滚到已知稳定版本"]
```

**CI** 是 **Continuous Integration（持续集成，读作 C-I）**：代码变更后自动构建、检查和测试。金丝雀发布与回滚详见 [[金丝雀发布、灰度发布与渐进式交付]]。

## 三、除了高并发，还有哪些根本区别

### 1. 数据从“随便重置”变成“不可随便损坏”

本地开发数据库里的十条假订单删掉了，可以重新生成。生产数据库里的订单、病历、财务记录或用户文件一旦损坏，可能产生真实损失。

生产数据问题包括：

- 数据库迁移是否会锁表或失败；
- 新旧版本能否同时理解同一种数据格式；
- 删除和批量修改能否撤销；
- 备份是否真的可以恢复；
- 多个请求同时修改时是否发生 Lost Update（更新丢失）；
- 重试是否会重复扣款、创建订单或发送消息；
- 测试人员是否误操作了真实数据；
- 日志和备份是否泄露敏感信息。

所以生产变更经常需要：备份、事务、幂等键、分阶段数据库迁移、审计日志和恢复演练。参见 [[状态机与幂等性]]。

### 2. 配置不同，而且配置错误同样能让程序崩溃

相同代码在不同环境需要不同配置：

| 配置项 | 本地示例 | 生产示例 |
|---|---|---|
| API 地址 | `http://localhost:8000` | `https://api.example.com` |
| 数据库 | 本地 SQLite | PostgreSQL/MySQL 集群 |
| 日志级别 | `debug` | 通常为 `info` 或更谨慎配置 |
| 邮件 | 写入测试邮箱 | 真实发送服务 |
| 对象存储 | 本地目录或 MinIO | 正式对象存储 Bucket |
| 功能开关 | 开发者自由打开 | 按用户、租户或发布批次控制 |

如果把地址和密钥硬编码进源代码，就容易出现：

- 测试代码连接生产数据库；
- 生产版本仍访问 `localhost`；
- API Key 被提交到 Git；
- 不同服务器上的配置不一致；
- 回滚代码后，配置却没有一起回滚。

配置应与代码分离，并明确哪些值属于哪个部署环境。但“放进环境变量”也不等于绝对安全：环境变量仍需由受控的 Secret Manager（密钥管理系统）注入，不能随意打印进日志。

### 3. 操作系统、CPU 和运行时可能不同

开发者可能使用：

```text
Windows + Node.js A版本 + x86-64 CPU
```

生产可能使用：

```text
Linux容器 + Node.js B版本 + ARM64 CPU
```

由此可能产生：

- Windows 路径使用 `\`，Linux 路径使用 `/`；
- Windows 文件名通常不区分大小写，Linux 常区分；
- 文件权限和可执行位不同；
- 换行符、字符编码和字体不同；
- Node.js、Python、Java 或系统库版本不同；
- 原生依赖只为一种 CPU 架构编译；
- 时区和 Locale（地区格式）不同；
- 本地有某个工具，生产镜像里没有。

容器和锁文件能缩小差异，但不能消灭真实流量、真实网络、外部服务和数据规模的差异。

### 4. 依赖的数据库、缓存和队列可能不是同一种产品

本地为了方便可能使用 SQLite，生产使用 PostgreSQL；本地把任务存在内存，生产使用 Redis 或消息队列。

即使代码使用统一接口，它们仍可能在以下方面不同：

- SQL 语法和数据类型；
- 并发写入能力；
- 事务隔离级别；
- 排序和大小写规则；
- 最大连接数；
- 超时和故障恢复；
- 消息是否会重复投递；
- 缓存数据何时过期。

这也是为什么 [[SQLite、SQLCipher与PostgreSQL|SQLite 与数据库服务器]] 不能只因为“都支持 SQL”就当成完全相同。

### 5. 网络路径突然变长、变复杂、也更不可靠

本地调用：

```text
浏览器 → localhost API
```

可能只经过一台电脑。生产调用则可能是：

```text
用户浏览器
→ DNS
→ CDN / WAF
→ 负载均衡器
→ 反向代理
→ 应用服务器
→ 缓存 / 数据库 / 第三方API
```

**CDN** 是 **Content Delivery Network（内容分发网络，读作 C-D-N）**；**WAF** 是 **Web Application Firewall（Web 应用防火墙，读作 W-A-F）**。

网络问题包括：

- [[DNS域名系统|DNS]] 解析错误或缓存尚未更新；
- [[TLS与数字证书|TLS]] 证书过期、域名不匹配或证书链错误；
- [[防火墙与端口对外开放|防火墙和端口]] 未放行；
- 反向代理没有转发正确请求头；
- 浏览器 CORS（Cross-Origin Resource Sharing，跨来源资源共享）限制；
- HTTPS 页面调用 HTTP API 造成 Mixed Content（混合内容）拦截；
- 网络延迟、抖动、丢包和超时；
- 代理空闲超时切断 WebSocket；
- 第三方 API 限流、故障或返回格式变化。

本地 `localhost` 成功，只能证明程序在极短、极简单的网络路径上工作。

### 6. 权限模型完全不同

开发者在自己电脑上可能拥有管理员权限，还能读取所有项目文件。生产进程通常应该以低权限服务账户运行，只能访问完成工作所需的目录、端口和密钥。

常见问题：

- 本地能写任意目录，生产容器文件系统只读；
- 本地有管理员权限，生产服务账户被 ACL 拒绝；
- 服务账户没有访问数据库或对象存储的权限；
- 密钥过期或 Secret 挂载位置不正确；
- 多租户权限检查遗漏，用户读到别人的数据；
- 开发调试接口在公网暴露。

“为了让它先跑起来，直接给管理员权限”会把配置问题变成严重安全风险。参见 [[身份认证与授权：ACL、RBAC、MFA、OAuth、OIDC、SAML与SCIM]]。

### 7. 程序不再只启动一次，而要长期运行

本地开发时，程序运行半小时没有问题，开发者可以看着终端并手动重启。生产服务可能要连续运行数月，并在无人盯着屏幕时自动恢复。

长期运行会暴露：

- 内存泄漏；
- 文件句柄和数据库连接没有释放；
- 临时文件不断增长直至磁盘写满；
- 日志无限增长；
- 定时任务重复执行；
- 证书、Token 或缓存过期；
- 进程崩溃后无法重启；
- 服务器重启后服务没有自动拉起；
- 时钟偏差造成签名、过期时间和任务调度异常。

生产服务需要进程管理、健康检查、资源限制、优雅关闭和故障恢复。参见 [[高可用、健康检查与故障恢复]]。

### 8. 多实例带来的问题不等于单纯高并发

即使访问量不高，为了容灾也可能同时运行两个实例：

```text
负载均衡器
├─ 实例 A
└─ 实例 B
```

这会立即产生新的状态问题：

- 用户第一次请求到了 A，第二次到了 B；
- A 内存里的登录状态，B 看不到；
- 两个实例同时执行同一个定时任务；
- WebSocket 连接在 A，但后台事件由 B 产生；
- 两个实例竞争更新同一条数据；
- 只更新了 A，导致新旧版本同时提供服务。

因此生产架构常把共享状态放到数据库、缓存或消息系统中，并设计分布式锁、幂等和版本兼容。这是“分布式状态”问题，不只是“请求太多”。

### 9. 缓存会让用户看到旧内容

本地开发经常关闭或绕过缓存；生产为了性能会使用：

- 浏览器缓存；
- CDN 缓存；
- 反向代理缓存；
- Redis 等应用缓存；
- PWA Service Worker 缓存；
- 数据库查询缓存或客户端状态缓存。

缓存可能造成：

- 代码已经发布，用户仍加载旧 JavaScript；
- HTML 与旧/新资源版本不匹配；
- 修改数据后列表仍显示旧值；
- 不同地区的 CDN 节点内容不一致；
- PWA 的 Service Worker 长期控制旧页面；
- 敏感响应被错误地共享缓存。

缓存不是简单的“让程序更快”，还需要版本化、失效策略和一致性设计。

### 10. 开发构建和生产构建不是同一个程序形态

以前面学习的 [[React前端技术栈：Vite、Router、Zustand与PWA|React + Vite 技术栈]] 为例：

```text
pnpm dev
→ Vite开发服务器
→ HMR、详细错误和快速反馈
```

而：

```text
pnpm build
→ 生产优化后的HTML、CSS和JavaScript
→ 部署到静态服务器或CDN
```

生产构建会涉及：

- 代码压缩和 Tree Shaking（移除未使用代码）；
- 文件哈希与长期缓存；
- 不同的 `import.meta.env` 环境变量；
- 资源基础路径 `base`；
- 代码分割和懒加载；
- 浏览器兼容目标；
- Source Map 是否上传给错误监控系统；
- 调试代码、开发警告和 HMR 被移除。

因此“`pnpm dev` 能打开”不能证明“正式构建可以部署”。至少还要运行类型检查、测试、`pnpm build`，并在接近生产的服务器配置下验证构建产物。

### React/Vite/PWA 的典型生产坑

- React Router 子页面直接刷新时，服务器没有回退到 `index.html`，出现 404；
- `VITE_API_URL` 构建时写错，所有用户都访问错误 API；
- 把密钥写进 `VITE_` 变量，以为它是秘密，实际被打进前端 JavaScript；
- HTTPS 页面仍连接 `ws://`，浏览器阻止不安全连接，应使用 `wss://`；
- 反向代理未正确处理 WebSocket Upgrade；
- Service Worker 缓存了旧入口，用户反复刷新仍看见旧版本；
- 静态资源部署到子目录后，`base` 配置错误导致全部 404。

### 11. 真实用户行为远比开发者测试复杂

开发者通常只测试“正常路径”，真实用户会带来：

- 重复点击提交按钮；
- 上传空文件、超大文件或特殊格式文件；
- 在请求进行中关闭页面；
- 同一个账号在多个设备登录；
- 使用旧浏览器、手机小屏或辅助技术；
- 输入表情、不同语言、超长姓名和特殊字符；
- 网络在 Wi-Fi、蜂窝网络和离线之间切换；
- 浏览器恢复休眠标签页后使用过期连接；
- 把同一个请求刷新、重放或并发提交。

所以生产质量还涉及输入校验、无障碍、兼容性、国际化、取消请求和异常流程，不只是服务器吞吐量。

### 12. 安全威胁从“自己使用”变成“任何人都可能尝试攻击”

本地端口只给自己使用时，很多问题不容易显现。生产一旦对公网开放，就会不断遇到扫描、弱口令尝试、恶意输入和自动化攻击。

需要考虑：

- 身份认证和权限校验；
- SQL 注入、XSS、CSRF、SSRF 等攻击；
- 安全响应头和 Cookie 属性；
- 依赖漏洞和供应链风险；
- 接口限流与反自动化；
- 密钥轮换和最小权限；
- 调试页面、备份文件和管理接口暴露；
- 日志是否包含密码、Token 或个人信息。

HTTPS 只能保护传输链路，不能自动解决上述应用安全问题。

### 13. 失败会发生，而且必须能被看见

本地报错时，开发者看着终端就能发现；生产没有人一直盯着每台服务器。

因此需要 Observability（可观测性）：

- Logs（日志）：具体发生了什么；
- Metrics（指标）：错误率、延迟、流量和资源使用怎样变化；
- Traces（链路追踪）：一次请求经过哪些服务、慢在哪里；
- Alerts（告警）：什么时候必须通知人处理。

监控不仅看 CPU。常见核心信号包括：

- Latency（延迟）；
- Traffic（流量）；
- Errors（错误）；
- Saturation（饱和度，例如线程池、连接池或磁盘快满）。

如果没有监控，服务可能已经坏了，只是团队还不知道。

### 14. 发布本身就可能制造故障

即使代码正确，发布过程仍可能出错：

- 漏传文件；
- 构建产物不是测试过的那一份；
- 数据库先升级，但应用还没升级；
- 新旧实例的 API 或消息格式不兼容；
- 一次把全部服务器替换，无法快速止损；
- 配置改变后没有审计记录；
- 回滚代码时，数据库已经无法回滚。

生产发布需要可重复构建、版本标识、自动检查、金丝雀、监控判定和回滚方案。发布不是“把文件复制上去”这么简单。

### 15. 成本、合规和责任发生变化

开发环境用一点资源通常问题不大，生产环境中的错误配置可能持续产生云账单。真实数据还可能受到隐私、数据保留、数据驻留和审计要求约束。

例如：

- 日志保存多久；
- 谁能访问生产数据库；
- 备份存放在哪个地区；
- 用户删除账号后哪些数据必须删除；
- 哪些操作必须留下审计记录；
- 第三方模型 API 是否会让数据离开内网。

这类问题与 QPS（Queries Per Second，每秒查询数）无关，但同样决定系统能否正式上线。

## 四、用一个例子理解“本地正常，生产失败”

假设你开发一个任务看板。

### 本地环境

```text
一个开发者
→ http://localhost:5173 Vite
→ http://localhost:8000 API
→ 本地SQLite
```

本地测试结果：创建任务、查看列表、WebSocket 进度都正常。

### 生产环境

```text
全国用户
→ HTTPS/CDN
→ 负载均衡器
→ 两台API服务器
→ PostgreSQL + Redis
→ 对象存储 + 第三方短信服务
```

可能发生：

1. CDN 缓存了旧前端，新前端和旧 API 格式不兼容；
2. 负载均衡器的空闲超时关闭 WebSocket；
3. 实例 A 和 B 都执行定时任务，用户收到两条短信；
4. PostgreSQL 连接池配置太大，把数据库连接耗尽；
5. 短信服务返回限流错误，但程序没有退避；
6. 用户重复点击，创建两条相同任务；
7. 生产服务账户不能写本地上传目录；
8. 数据库迁移锁住大表，正常查询也被阻塞；
9. 日志中记录了用户 Token；
10. 团队没有告警，直到用户投诉才发现故障。

这里只有第 4 条部分属于容量/并发问题，其余分别是缓存、网络、分布式任务、外部依赖、幂等、权限、数据、安全和监控问题。

## 五、Staging 为什么有用，又为什么不能完全代表生产

Staging（预发布环境）应尽量接近生产：

- 使用相同操作系统或容器镜像；
- 使用相同构建产物；
- 使用相同种类的数据库、缓存和队列；
- 使用相似的反向代理、TLS、路由和权限；
- 执行数据库迁移、升级和回滚演练；
- 使用脱敏数据或具有代表性的测试数据。

但它仍不能完全复制生产，因为：

- 流量和用户行为不同；
- 数据规模通常较小；
- 第三方服务可能使用 Sandbox（沙盒）账号；
- 服务器数量和地域不同；
- 很多稀有故障只会在长时间运行后出现；
- 不能为了测试故意破坏真实生产依赖。

因此正确思路不是“Staging 测过就绝对安全”，而是：

```text
尽量缩小环境差异
+ 自动测试
+ 生产金丝雀
+ 实时监控
+ 快速回滚
+ 故障演练
```

---

## 六、容器能否让本地和生产完全一样

Docker 等容器可以统一：

- 操作系统用户空间；
- 运行时和系统依赖版本；
- 应用启动命令；
- 文件结构；
- 构建与部署制品。

但容器无法自动统一：

- 真实数据量；
- 用户行为；
- 网络距离和丢包；
- 云厂商负载均衡器；
- 外部 API 限流；
- DNS 和证书；
- 多实例并发；
- 生产权限；
- 磁盘故障和区域故障；
- 监控、值班和回滚流程。

所以容器解决的是“环境一致性的一部分”，不是生产可靠性的全部。

## 七、上线前最小检查清单

### 构建和版本

- 是否从确定的 Git Commit 构建；
- 是否锁定依赖并保存构建记录；
- 类型检查、Lint、测试和生产构建是否通过；
- 部署的是否正是已经测试过的制品；
- 是否能识别当前运行版本。

### 配置和密钥

- API、数据库、对象存储地址是否属于正确环境；
- 密钥是否通过受控方式注入；
- 前端环境变量中是否误放秘密；
- 调试模式、测试账号和默认密码是否关闭；
- 服务账户是否遵循最小权限。

### 数据

- 数据库迁移是否向前、向后兼容；
- 是否有备份；
- 是否真正验证过恢复流程；
- 写操作是否考虑事务、重复请求和并发更新；
- 旧版本回滚时能否继续读取新数据格式。

### 网络和安全

- DNS、TLS 证书、端口和防火墙是否正确；
- HTTPS、WSS、CORS 和安全响应头是否验证；
- 管理接口、备份和调试文件是否暴露；
- 反向代理、上传大小和超时是否合理；
- 依赖漏洞和权限边界是否检查。

### 可靠性和运维

- 健康检查和自动重启是否有效；
- 日志、指标、追踪和告警是否可用；
- 容量、连接池、磁盘和外部配额是否足够；
- 是否有超时、重试、退避、熔断和限流；
- 是否有金丝雀、暂停和回滚方案；
- 谁负责值班，出现问题怎样联系和升级。

## 八、怎样缩小本地与生产的差距

### 1. 同一份代码、同一个制品逐级晋升

理想情况下，不要在测试环境构建一次、生产环境重新随意构建一次，而是让通过测试的同一制品逐级进入预发布和生产。

### 2. 配置和代码分离

相同程序通过明确配置连接不同环境资源。配置应版本化、可审计；秘密则进入专门密钥系统，不提交到 Git。

### 3. 锁定版本和可重复构建

使用依赖锁文件、容器镜像摘要和构建编号，避免“今天重新安装依赖，得到另一套程序”。

### 4. 本地使用与生产相同种类的关键依赖

如果生产依赖 PostgreSQL、Redis 和消息队列，本地或集成测试也应覆盖它们，不能只使用行为不同的简化替代品。

### 5. 自动化测试覆盖不同层次

- Unit Test（单元测试）：验证小函数或组件；
- Integration Test（集成测试）：验证数据库、队列和服务协作；
- End-to-End Test（端到端测试）：从用户入口验证完整流程；
- Load Test（负载测试）：验证容量、延迟和退化方式；
- Security Test（安全测试）：验证权限、配置和常见攻击面；
- Recovery Test（恢复测试）：验证备份、故障切换和回滚。

### 6. 在生产中安全地继续验证

任何预发布环境都不能完全复制生产，所以还需要金丝雀、Feature Flag（功能开关）、监控和自动回滚，让少量真实流量先验证新版本。

## 九、最常见的误区

### 误区 1：生产只是并发更高

错误。数据不可逆、安全攻击、网络拓扑、权限、多实例、缓存、发布、监控、成本和合规都可能与并发无关。

### 误区 2：本地测试通过，代码就一定没问题

本地通过只证明它在当前代码、配置、依赖、数据和网络组合下通过。换一个组合仍可能失败。

### 误区 3：用了 Docker，本地就等于生产

Docker 能固定部分软件依赖，不能复制生产用户、数据、网络、权限、外部服务和运维流程。

### 误区 4：测试环境越像生产，就可以使用生产数据

不一定。真实数据可能包含隐私和商业秘密。应优先使用合成数据或经过严格脱敏、授权和访问控制的数据。

### 误区 5：生产出错就打开 Debug 模式

Debug 页面可能泄露源码、路径、配置甚至密钥。生产应通过受控日志、指标、追踪和转储诊断，而不是向用户暴露详细错误。

### 误区 6：只要有备份就能恢复

没有定期恢复演练的备份，可能在真正需要时才发现损坏、缺文件、缺密钥或恢复时间过长。

### 误区 7：发布成功就是服务正常

文件上传成功或容器启动成功，只说明部署动作完成。还要验证健康检查、业务请求、错误率、延迟和关键用户流程。

## 十、初学者应该先记住的十句话

1. **本地描述地点，开发与生产描述用途。**
2. **程序行为由代码和环境共同决定。**
3. **高并发只是生产问题的一类。**
4. **生产数据通常不能随便删除或重建。**
5. **配置错误和代码错误一样能造成事故。**
6. **多实例会产生共享状态和一致性问题。**
7. **缓存、代理、TLS 和权限会改变程序行为。**
8. **开发构建成功不等于生产构建可用。**
9. **没有监控，就可能不知道系统已经坏了。**
10. **可靠上线依赖测试、金丝雀、监控和回滚共同工作。**
