# 生产安全五件套：KMS、Secret、IAM、配置管理与 Egress 授权

> [!summary] 一句话解释
> **KMS 管加密密钥，Secret 管理管机密凭据，IAM 管身份与操作权限，配置管理管运行参数及其变更，Egress 授权管向外连接的边界。它们协作保护一个运行中的系统，但谁也不能替代全部其他能力。**

这里的“五件套”是方便学习的叫法，不是一个固定技术标准，也不意味着必须购买五款产品。下文是通用职责划分；以云服务和容器网络文档作为具体例子，不要求使用某个厂商。

“Egress 授权”也不是只有一种标准含义：它可能指平台的出网审批、网络访问策略，或应用层的数据外发许可。本篇先区分这些边界，避免把“能连出去”和“什么都能发出去”混为一谈。

## 一、先用一个公司的类比理解

假设你在经营一个有保密资料的公司：

| 概念 | 英文、中文与读法/用途 | 公司类比 | 主要回答的问题 |
|---|---|---|---|
| KMS | Key Management Service，密钥管理服务，按 K-M-S 读 | 受控的加密钥匙保管与使用系统 | 谁能使用哪把加密钥匙，何时轮换或停用？ |
| Secret 管理 | Secrets Management，机密信息管理；Secret 读 /ˈsiːkrət/ | 保管密码和访问凭据的保险柜 | 凭据放哪里，怎样交给需要它的程序？ |
| IAM | Identity and Access Management，身份与访问管理，按 I-A-M 读 | 工牌、门禁和岗位权限制度 | 是谁在操作，对哪些资源能做什么？ |
| 配置管理 | Configuration Management；此处侧重应用配置 | 带版本的运行规程 | 程序使用哪些参数，谁能更改，出错如何恢复？ |
| Egress 授权 | Egress Authorization，出站访问授权；Egress 读 /ˈiːɡres/ | 向外寄件的出口检查 | 哪个程序可以连接哪些外部目的地？ |

类比不是严格的一一对应：产品能力可能重叠，身份策略也会贯穿其他系统，而不是只在“登录”时检查一次。

## 二、KMS：保护加密钥匙，并控制它的使用

**加密密钥**是加密或解密运算使用的关键材料。知道算法不一定能解密，还需要正确的密钥。

KMS 的职责通常包括生成和管理密钥、执行允许的密码运算、控制权限、记录操作、支持轮换与停用。它不是普通的“把所有密码存起来”的文件夹。

一个常见做法是：业务数据由数据密钥加密，再让 KMS 保护这把数据密钥。授权程序可以请求必要的解密操作，但不一定能导出 KMS 内部的高价值密钥原文。这种做法叫信封加密，完整原理见 [[密钥管理：DEK、KEK、KMS、HSM与信封加密]]。

例如：Secret 管理系统把大模型服务的访问凭据加密保存，其加密保护可能依赖 KMS。

需要分清三个边界：

1. **加密密钥与访问凭据不是同一个概念。** 网站提供的 API Key 通常用于证明调用资格，不意味着它就是拿来加密数据库的密钥。API 是 Application Programming Interface（应用程序编程接口），用于软件互相调用，详见 [[SDK与API]]。
2. **拿不到主密钥，不等于拿不到解密结果。** 某个应用被授权获取秘密后，秘密仍可能出现在它的运行内存中。
3. **KMS 不自动阻止数据外发。** 已被合法解密的数据，之后会不会被乱用，要靠其他权限和运行时控制。

AWS KMS 的密钥层级与数据密钥是一个具体实现例子，不应把其所有导出、轮换和权限细节推广到每个 KMS。[官方说明](https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html)

## 三、Secret 管理：保存、发放、更新和回收机密凭据

### 什么算 Secret

常见例子包括数据库密码、第三方 API Key、访问令牌、签名私钥等。公开证书与私钥不同，不能只看文件名里有没有“证书”。

Secret 管理通常解决：

- 在受保护的存储中保存秘密，而不是写进代码、镜像或普通共享文档；
- 允许指定程序读取指定秘密，而不是一次给全公司的密码；
- 管理版本、有效期、更新和撤销，并记录谁访问过；
- 通过受控方式交付给程序，而不是让开发者复制粘贴真实密码。

例如配置中只写 `secret-ref: prod/model-access`，它表示一个**秘密引用**：去受控存储寻找名为 `prod/model-access` 的记录。这个字符串是本文示意，不是通用可执行语法，也不是凭据本身。

### 为什么不直接存到普通配置文件

普通配置文件可能进入 Git、安装包、备份、调试输出或浏览器下载内容。Secret 即使被加密保存，也必须控制谁能读取解密后的值。

`.env` 文件是一种常用配置载体，不是加密保险柜；环境变量也只是向进程传值的方式，可能通过日志、子进程继承或调试权限暴露。给前端代码、手机安装包或桌面安装包内置一个全体用户共享的长期供应商密钥，通常也无法把它当成可靠秘密保存。

### 轮换不是随便改一串字符

轮换某个 API Key 时，需要供应商提供创建或更新凭据的能力，并协调：新凭据生效、应用更新和验证、旧凭据撤销。只更改保险柜里的文字，不会让对方服务器自动接受它。

另外，**轮换 KMS 的加密密钥，不等于更换 Secret 里保存的数据库密码或 API Key**。若这些凭据已经泄漏，需要到实际签发方撤销或更换，而不只是重新加密同一串旧凭据。

AWS Secrets Manager 展示了“用 KMS 保护静态秘密、授权后安全传输给应用”的组合；秘密的运行时保护和轮换流程仍需要设计。[AWS 文档](https://docs.aws.amazon.com/secretsmanager/latest/userguide/best-practices.html)、[OWASP 秘密管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 四、IAM：不仅识别人，也识别正在运行的程序

可以用下面这句话理解一条权限规则：

> **某个身份，在指定条件下，能对指定资源执行指定操作。**

例如，不是笼统地说“助手有权限”，而是：

- 正式环境的模型调用服务可以读取 `prod/model-access`；
- 测试环境的同类服务只能读取测试凭据；
- 模型调用服务不能读取支付服务的凭据；
- 能读取凭据，不代表能修改权限、删除凭据或销毁加密密钥。

这里的“身份”可以是人，也可以是服务账号，或由运行平台确认的**工作负载身份（Workload Identity）**。工作负载就是实际运行的应用、任务或服务。

这解决了一个问题：程序怎么证明自己有资格向 Secret 系统要密码？在支持的环境里，可以由平台给程序分配身份并提供短期凭据，避免为了取一个密码，又在代码里藏一个长期万能密码。它仍然依赖受信任的身份签发和运行环境，不是“完全没有信任基础”。

基础原则是**最小权限**：只给完成任务所必需的资源、操作和有效范围。还要区分“你的应用能拿到供应商凭据”与“供应商允许这个凭据调用哪些接口”，这是不同系统各自执行的授权。[IAM 官方实践](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html)

IAM 与登录、角色和资源访问控制的关系见 [[身份认证与授权：ACL、RBAC、MFA、OAuth、OIDC、SAML与SCIM]]。

## 五、配置管理：不只是保存几个参数

**配置**是程序运行时使用的参数，常常不需要修改业务代码就能调整，例如：

- 使用哪家模型服务、哪个模型；
- 请求最多等 30 秒还是 60 秒；
- 一次允许多少个任务同时运行；
- 是否启用某项新功能；
- 日志记录到什么详细程度。

这里侧重应用配置。更广义的配置管理还可能包括服务器软件版本、系统状态等基础设施管理。

示意配置如下，全部是假数据与示意值，不是可直接部署的配置：

```text
model_endpoint = https://model.example.com
request_timeout_seconds = 30
debug_logging = false
credential_reference = prod/model-access
```

前三行描述运行行为；最后一行只指明去哪里取凭据，并没有保存凭据原文。地址若本身带密码或访问令牌，也必须按 Secret 对待。

配置管理要回答的不只是“值是多少”，还包括：谁能改、用于哪个环境、当前是什么版本、怎样验证、何时生效、怎样逐步发布和回滚。部分配置需要重启才能生效，不能默认都有热更新能力。

**不是秘密的配置，也可能是高风险配置。** 比如把模型服务地址改成错误站点，可能让业务数据甚至附带的凭据被发错地方。因而修改权限、目标校验和出站约束都重要。

配置验证、渐进发布、监控和回滚可参考 [AppConfig 官方说明](https://docs.aws.amazon.com/appconfig/latest/userguide/what-is-appconfig.html)。关联 [[开发、测试、预发布与生产环境]]、[[金丝雀发布、灰度发布与渐进式交付]]。

## 六、Egress 授权：哪些连接能离开这个边界

### 先认清方向

**Ingress（入站）**是进入所讨论边界的流量；**Egress（出站）**是离开这个边界的流量。边界可以是一个程序、容器、服务器或整个网络，不一定是国境，也不一定特指公网。

- 用户访问你的服务器：对服务器而言是入站访问；
- 服务器主动请求外部大模型：对服务器而言是出站访问；
- 服务 A 请求同一公司里的服务 B：对 A 的边界来说也可以是出站。

连接的应答流量与新建连接的放行策略，需要按具体网络产品理解，不能把“收到响应”误认为必须向所有人开放入站端口。参见 [[防火墙与端口对外开放]]。

### 网络出站许可与数据外发许可不是同一层

| 控制层次 | 可以检查什么 | 不能自动保证什么 |
|---|---|---|
| 网络层出站策略 | 来源、目标网络地址、协议和端口等 | 不会自动知道请求里是不是客户隐私 |
| 支持域名或应用协议的出口代理/网关 | 允许的服务、连接目标；具备相应可见性时可做更细检查 | 不一定能检查端到端加密连接里的完整内容 |
| 业务层外发授权 | 谁发起、什么用途、哪些字段可发送、是否需要用户批准 | 不能只写在文档或提示词里，必须有程序执行 |

例如“允许该服务连接批准的模型端点”与“允许它发送客户身份证号”是两项不同许可。只放行某个域名或 443 端口，不代表对所有上传内容都作出了业务授权。

对于 HTTPS（Hypertext Transfer Protocol Secure，安全的超文本传输协议）连接，普通网络防火墙通常不能直接看见加密后的正文。内容规则可以在应用发送前执行，或由具有相应受控终止/转发能力的网关执行；不能假定所有防火墙都能检查正文。

### 怎样形成真正的限制

示例目标是：应用只能经批准的出口连接指定服务，其他不必要目的地被阻止。限制必须在应用不能随意绕开的边界执行；仅配置一个代理地址，或仅在提示词里告诉 Agent“不要外发”，都不是可靠的网络隔离。

实现方式可能是主机防火墙、云网络策略、容器网络策略或强制出口网关，各自能力和边界不同：

- Kubernetes（容器编排平台）的标准 NetworkPolicy（网络策略）需要网络组件支持才能实际执行，不能把“配置文件已经存在”当成“已经拦截”。它也不等于任意的应用层或域名授权能力。[官方文档](https://kubernetes.io/docs/concepts/services-networking/network-policies/)
- Istio（服务间通信管理系统）的文档特别提醒：某些出口路由示例不是安全隔离，恶意应用仍可能绕过旁路代理，必须结合强制路径等措施。[官方安全说明](https://istio.io/latest/docs/tasks/traffic-management/egress/egress-control/#security-note)

设计时要核对域名解析、目标地址变化、跳转和备用路径，并允许实际需要的身份、Secret、监控等依赖。错误地“一刀切断网”也会让业务无法启动或运行。这是学习原理，不建议直接照着概念去修改当前电脑或生产网络。

## 七、串起来：一个后端服务调用外部大模型

以下是示意架构，不代表用户现有项目已经这样实现。真实产品可能把多项能力集成在一起，也可能由网关集中持有凭据。

1. **确认身份**：运行平台为模型调用服务提供工作负载身份；业务系统还要核对发起任务的用户权限。
2. **读取配置**：获得批准的模型服务地址、超时设置和秘密引用，不从模型生成的文本中直接接受新出口地址。
3. **检查读取权限**：服务请求所需 Secret，相关授权机制核对它是否可以读取该项秘密。
4. **取得可用凭据**：Secret 服务按其与 KMS 的集成方式解密、返回或注入凭据；不要求每种实现都由业务程序直接调用 KMS。
5. **检查业务外发范围**：应用确认任务能否发送给该供应商，按需要删去或遮盖不应外发的字段；敏感操作按策略请求批准。
6. **检查出站路径**：网络或出口网关只允许符合目标、协议等条件的连接，不能让应用任意绕开。
7. **供应商再次授权**：对方校验收到的凭据及其权限，通过后才处理请求。
8. **记录审计与处理异常**：记录身份、目标、操作、策略/配置版本及结果，不把完整秘密和敏感正文写进日志。

> [!important] 不是排成一条固定流水线的五个盒子
> IAM 会贯穿读取 Secret、使用密钥和修改配置等操作；KMS 可能由 Secret 服务间接调用；Egress 规则必须在真正的出站边界执行。更强隔离的方案还可以让受控网关持有供应商凭据，业务程序只提交经授权的请求。

接上此前的私有化问题：**即使后端在自己公司的服务器上，只要向外部模型服务发送了内容，那部分内容仍然离开了本地边界。** KMS 和 Secret 管理主要保护密钥与凭据，不会把外部调用变成本地计算。参见 [[内网、公网与私有化服务器部署]]。

## 八、少一项，会留下什么缺口

| 只有什么或缺少什么 | 可能出现的问题 |
|---|---|
| 有 KMS，但读取权限过大 | 任意内部服务都能请求获得本不该获取的秘密 |
| 有 Secret 管理，但发给所有应用同一套凭据 | 一个低风险服务被攻破，扩大到其他系统 |
| 有身份权限，但配置没人管 | 正式服务误连测试环境，或将数据发往错误地址 |
| 只保护入站，出站任意开放 | 被攻破的程序或不受控插件可能主动向外发送资料 |
| 只允许一个模型域名 | 仍可能向这家合法供应商发送不该发送的业务数据 |
| 五类系统都采购了，但应用能绕开检查 | 产品清单齐全，实际边界仍未成立 |

## 九、初学者常见误区

1. **“叫 Key 的都归 KMS。”** API Key 往往是身份凭据；用途和生命周期比名称更重要。
2. **“Secret Manager 与 KMS 完全一样。”** 二者可组合，但管理的主要对象和交付方式不同；有些产品同时提供两类功能。
3. **“加密了，应用就看不到。”** 加密存储不等于运行时不可读取，授权应用通常需要可用凭据或操作结果。
4. **“把旧密码从配置里删掉就撤销了。”** 真正撤销取决于数据库、供应商或身份系统是否拒绝它；已有副本不会因此消失。
5. **“云 IAM 自动管第三方网站的一切权限。”** 外部供应商有自己的授权机制，必须分别核对。
6. **“有出网白名单就能保证不泄漏。”** 被允许的渠道也可能承载敏感数据，仍需业务权限、内容规则和运行时防护。
7. **“Secret 或 KMS 故障时，先回落到写死的万能密码。”** 敏感操作应该按设计拒绝或受限降级；不能为了可用性擅自取消安全边界。受控缓存与恢复策略需要预先设计。

## 十、学习顺序与自测

推荐顺序：API 与凭据 → 身份认证和授权 → 普通配置与秘密的区分 → Secret 生命周期 → KMS/信封加密 → 入站/出站 → 数据外发边界。

用下面五个问题检查自己是否理解一个系统：

1. 哪些东西是秘密，保存在哪里？
2. 谁可以读取、修改和撤销它们？程序怎样证明自己的身份？
3. 哪些数据被加密，密钥由谁管理，怎样恢复？
4. 谁能改运行配置，如何知道当前使用哪个版本？
5. 系统能连接哪些目的地，可以发送哪些数据，拒绝规则是否真的生效？
