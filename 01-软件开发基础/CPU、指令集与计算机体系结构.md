# CPU、指令集与计算机体系结构

> [!summary] 一句话解释
> CPU 按指令规则执行计算与控制；指令集是软硬件之间的重要约定，同一指令集可以由结构、速度和成本不同的处理器实现。

**CPU = Central Processing Unit（中央处理器，读 C-P-U）**。它不是整台主机，也不是操作系统，而是执行通用计算和控制工作的硬件。

像几种机器都遵循同一本操作手册：手册规定“这个命令应产生什么结果”，机器内部可以采用不同结构。操作手册类似体系结构约定，具体机器结构类似微架构。

## CPU 内部有什么

| 部件或机制 | 做什么 |
|---|---|
| 控制逻辑与译码 | 识别指令，组织需要的操作 |
| 运算单元 | 进行整数、浮点、逻辑等运算 |
| 寄存器 | 保存当前指令直接使用的少量数据和状态 |
| Cache | 缓存近期或附近可能使用的指令和数据 |
| 内存访问与地址转换相关单元 | 访问数据、配合虚拟内存与权限检查 |
| 分支预测、流水线等 | 提高执行效率，具体实现各不相同 |

**ALU = Arithmetic Logic Unit（算术逻辑单元，读 A-L-U）**，是其中进行算术与逻辑操作的一类单元。不是所有运算都由同一个 ALU 完成。

现代处理器可能有多个核心。核心是能执行指令流的重要计算单元；线程是软件执行活动，二者不能简单画等号。多线程技术和操作系统调度见 [[进程、线程、多进程与多线程]]。

## 取指、译码、执行是什么

入门模型：从指令地址取出机器指令 → 译码 → 取得操作数 → 运算/访存 → 更新结果与下一步位置。

**PC = Program Counter（程序计数器，读 P-C）** 是保存指令位置的概念，实际架构可能采用别的寄存器名称，例如 x86 的指令指针。它不是 Personal Computer（个人计算机）那个 PC，也不是 PCB。

现代 CPU 会重叠处理多条指令，甚至进行推测和乱序执行，但对软件呈现的结果必须遵守体系结构规定的行为。因此“取指→译码→执行”是理解模型，不是所有时刻只能处理一条指令。

## 时钟频率为什么不等于性能

GHz 是 Gigahertz（吉赫兹，读 G-H-z），表示每秒十亿个时钟周期的量级。一个周期不是一条完整指令，也不是一种固定工作量。

实际速度还受每周期可完成的有效工作、核心数、缓存命中、内存带宽、程序可并行程度、供电和温度影响。不能只凭“4 GHz 大于 3 GHz”断言不同处理器在所有任务上更快。

加核心也不保证成倍提速：如果步骤严格依赖前一步，很多核心可能等不到可并行工作。复杂度与实际耗时关系见 [[算法复杂度与ASL：渐近符号、平均情况和查找长度]]。

## ISA：处理器与软件约定哪些指令

**ISA = Instruction Set Architecture（指令集体系结构，读 I-S-A）**。它不仅是指令名称列表，还涉及程序可见的寄存器、数据类型、寻址方式、异常和部分内存行为等约定。

同样是“相加”，不同架构可以使用不同机器编码和寄存器名称。CPU 不会因为两段源代码表达相同意思，就天然理解另一架构的机器码。

| 层次 | 重点 | 举例 |
|---|---|---|
| 体系结构 | 对软件可见的行为约定 | 指令集、寄存器、地址与异常规则 |
| 组成/微架构 | 怎样组织部件实现约定 | 流水线、执行单元、缓存组织 |
| 物理实现 | 怎样把设计做成可工作的芯片与系统 | 电路、工艺、布局布线、封装与板级连接 |

教材的“计算机组成”范围可能还包括存储与输入输出系统；微架构更多聚焦处理器内部。它们密切相关，但不需要把所有术语强行当完全同义词。

## Arm 与 x86 是什么

**Arm/ARM** 指处理器架构家族及相关公司品牌；历史 ARM 名称来自 Acorn RISC Machine，后来与 Advanced RISC Machines 的公司名称关联。今天不要把它误认成 RAM 的另一种拼法。

**x86** 源于 Intel 8086 及后续兼容处理器的命名传统，不是某个需要逐字展开的英文缩写。

| 名称 | 常见理解 | 注意 |
|---|---|---|
| x86 | 一族长期演化的指令集；安装包中有时特指 32 位版本 | 看具体语境 |
| x86-64 / x64 / AMD64 | x86 的 64 位扩展家族的常见名称 | AMD64 软件并不因此只能在 AMD CPU 运行 |
| AArch64 / ARM64 | Arm 架构中的 64 位执行/软件目标的常见名称 | 不代表与 x86-64 机器码兼容 |

Arm 不只用于手机，也用于嵌入式设备、电脑与服务器；x86 也不只用于个人电脑。具体产品适用场景取决于设计与生态，不是名称决定用途。

**RISC = Reduced Instruction Set Computer（精简指令集计算机，读 risk）**；**CISC = Complex Instruction Set Computer（复杂指令集计算机，读 sisk）**，是常用的指令集设计风格概念。

不能从“精简/复杂”四个字直接推出谁永远更快、更省电。现代实现很复杂，工艺、微架构、频率策略和负载都影响结果。[Arm 体系结构与微架构说明](https://www.arm.com/architecture/cpu)

## 为什么同为 64 位，程序也不能随便互换

64 位只是某些架构宽度的概括，不代表两台机器使用同一组指令。二进制程序能否运行还需要：

1. 指令集及所需扩展受支持。
2. 操作系统提供相应加载、系统调用与运行环境。
3. **ABI = Application Binary Interface（应用程序二进制接口，读 A-B-I）** 一致，包括调用约定、寄存器使用与数据布局等。
4. 程序依赖的库、设备和权限可用。

因此，同一 x86-64 CPU 上也不能把 Windows 程序和 Linux 程序简单等同。跨平台可以重编译、移植，或在适当条件下使用仿真/二进制翻译；虚拟机也不自动消除所有架构差异。

源代码可移植性与编译后二进制兼容性是两回事，关联 [[常见编程语言及其用途]]、[[Web端、桌面软件与CLI程序的区别]]。

## x86 与 Arm 各方面差别：先明确比较对象

以下主要比较电脑和服务器常见的 **x86-64 与 Arm AArch64**，不是把全部 Arm 微控制器与高性能桌面处理器混在一起比较。

Arm 有面向不同需求的架构和处理器系列。一个运行简单控制程序的微控制器，不能仅凭“也是 Arm”就被当作可安装普通 Ubuntu 的电脑。

可以把两种架构想成两套机器操作规范：都能建设强大的工厂，但规范不同；遵守同一规范的工厂，也可以采用完全不同的规模、生产线和能源管理。

### 1. 一张表看全貌

| 维度 | x86-64 | Arm AArch64 | 应怎样判断 |
|---|---|---|---|
| 指令集传统 | 常归入 CISC | 常归入 RISC | 设计风格不是性能排名 |
| 指令编码 | 变长编码，最长通常为 15 字节 | A64 指令固定为 32 位，即 4 字节 | 64 位处理器不意味着每条指令长 64 位 |
| 常见算术与访存形式 | 某些算术指令可带内存操作数 | 普通算术主要对寄存器运算，加载/存储单独表达 | 不是在比较现实机器只需多少步或多少周期 |
| 芯片来源与生态 | 个人电脑、服务器中常见 Intel、AMD 产品 | 多家厂商基于 Arm 架构设计不同芯片 | 同一家族也会有很大差别 |
| 性能与功耗 | 有低功耗和高性能设计 | 也有低功耗和高性能设计 | 看具体任务、芯片、整机与软件 |
| 传统桌面软件 | 大量历史软件围绕 x86 平台积累 | 需原生版本或合适兼容机制 | 检查自己真正需要的软件和插件 |
| 操作系统 | 可有 Windows、Ubuntu 等对应版本 | 也可有对应 Windows、Ubuntu 等系统环境 | 支持架构不等于支持所有设备 |
| 硬件驱动 | 同样依赖系统和具体设备支持 | 同样依赖系统和具体设备支持 | 应用兼容不能替代驱动兼容 |
| 集成与扩展 | 有可升级台式机，也有高度集成、焊接式产品 | 有高度集成产品，也有可扩展服务器 | 是否能换内存、接显卡由产品决定 |
| 安全与可靠性 | 依靠具体硬件机制、系统与维护 | 同样依靠具体实现与维护 | 两者都不天然免疫漏洞或程序错误 |
| 成本 | 受产品、供货、软件与运维影响 | 也受产品、供货、软件与迁移影响 | 不存在只靠架构名称决定的固定价差 |

编码边界按 Intel 指令手册和 Arm A64 指南理解；**A64 固定长度的结论不要套到 Arm 家族的所有其他指令集上**。[Intel 指令格式](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-2a-manual.pdf)、[Arm A64 指南](https://documentation-service.arm.com/static/656f49c7130be919349bb533)

### 2. “精简指令集”不是只能干简单事情

RISC 的“精简”强调指令集设计思路，不表示现代 Arm 只有几条指令，也不表示不能运行复杂软件。CISC 的“复杂”也不是说每条指令都很慢。

现代高性能 x86 处理器会把许多指令译码成内部微操作；高性能 Arm 处理器也可能有复杂的译码、流水线、乱序执行和预测机制。不能简化成“x86 内部已经完全变成 Arm”，因为对软件可见的指令和行为约定仍不同。

例如，只考虑有效可写地址中的普通 32 位整数、无并发修改的情况，下面表达“该整数加 1”的两种汇编示意：

```asm
; x86-64，Intel 语法；假定 rdi 指向该整数
add DWORD PTR [rdi], 1
```

这一形式在同一条体系结构指令中表达读、加、写。方括号表示访问地址指向的内存，DWORD 在这里表示 32 位数据。

```asm
// AArch64；假定 x0 指向该整数
ldr w1, [x0]
add w1, w1, #1
str w1, [x0]
```

分别是加载到寄存器、加 1、写回。两段只是帮助理解普通算术与访存的表达差异，不是完整程序，也不比较其他寄存器或标志状态。

**一条 x86 指令不等于一个时钟周期，也不意味着这里的操作具有多线程原子性。** 两段不能凭汇编行数判断谁更快。本次只整理指令语义，没有在本机汇编或执行这些片段。

### 3. 性能：不能只看频率、核心数或指令数

比较之前先问“快”指什么：一次任务完成时间、多任务吞吐量、交互响应，还是长时间满载表现？

影响因素包括核心微架构、缓存、主内存带宽、制造工艺、频率与功率限制、编译器优化、任务并行程度，以及程序是否原生支持该平台。

如果用一台低功耗笔记本对比一台高功率台式机，结果反映了整套设计，不是单独测出了“指令集谁更好”。同理，两边核心的能力不同，不能把 8 核对 8 核当作硬件条件完全一致。

正确做法是用相同任务、相同正确性要求，记录软件版本、线程配置、整机功耗与持续时间。不在本笔记给出脱离型号的百分比排名。

### 4. 功耗、能耗、续航不是同一个指标

功耗是单位时间消耗能量的速率，常用瓦 W；能耗是完成工作总共使用的能量，常用焦耳 J。恒定功率的简化关系是：

$$
E=P\times t
$$

假设两台设备完成相同任务：A 以 20 W 用了 10 秒，约 200 J；B 以 10 W 用了 30 秒，约 300 J。B 瞬时功率更低，但这次任务的总能耗更高。这是计算例子，不代表某个架构的实测结果。

手机和移动设备长期受电池、体积和散热约束，许多 Arm 产品围绕这些目标优化；这不能推出“所有 Arm 都比所有 x86 省电”。笔记本续航还受电池容量、屏幕、网络、待机和软件后台活动影响。

### 5. 软件兼容：至少有三层问题

1. **源代码层**：算法和业务代码是否用了平台专用功能？
2. **二进制层**：编译后的指令、ABI、系统接口和库是否匹配？
3. **完整产品层**：插件、驱动、安装器、更新程序和外设是否都受支持？

例如同一份纯 Python 脚本，可能在两种架构对应的 Python 解释器中运行；但它依赖的原生扩展、计算库和设备驱动仍需分别支持。Java 字节码同样依赖目标平台可用的运行环境，不能因此忽略本地库。

Windows、Linux、macOS 是另外一个兼容维度。同样是 arm64 的 macOS 应用和 Ubuntu 应用，也不能仅凭 CPU 架构相同直接互换。

### 6. 原生运行、转译、虚拟机与容器

- 原生运行：程序的目标指令集和系统环境与当前执行平台相配。
- 重编译/移植：用相应工具为目标平台生成程序，并处理平台差异。
- 仿真/二进制翻译：用软件模拟目标行为，或把代码块转换成宿主可执行形式；覆盖范围和开销取决于实现。
- **VM = Virtual Machine（虚拟机，读 V-M）**：提供虚拟硬件环境；常见同架构硬件虚拟化并不会自动把 x86 变成 Arm，跨架构通常还涉及仿真或翻译。
- Docker 容器：通常共享运行它的内核，隔离运行环境，不自动抹平指令集差异。

例如 Windows on Arm 可以为部分 x86/x64 应用提供兼容执行，但不能据此推断所有插件和设备功能都可用。特别要单独核对驱动与所用系统版本。[Microsoft：Arm 上的应用仿真](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)

Docker 的 `linux/amd64` 与 `linux/arm64` 是不同目标平台；多平台镜像通常组织相应平台的多个制品供选择，不是把机器码变成通用码。也可能借助仿真运行，但计算密集任务可能付出明显代价。[Docker 多平台构建](https://docs.docker.com/build/building/multi-platform/)

关联 [[Docker容器与DI容器：运行隔离和对象装配]]、[[开发、测试、预发布与生产环境]]。

### 7. 内存、并发和加速指令也有差异

两种架构都可以使用缓存、主内存、虚拟内存和多核心。共享内存并不保证多个核心观察到所有读写的顺序都与源代码直觉一致；不同架构的内存顺序约束存在差异。

迁移底层并发程序时，应使用语言和系统规定的锁、原子操作与屏障，不能依赖“在旧电脑上一直没出问题”。缓存一致性也不等于没有数据竞争。[Linux 内存屏障说明](https://www.kernel.org/doc/html/latest/core-api/wrappers/memory-barriers.html)

**SIMD = Single Instruction, Multiple Data（单指令多数据，读 S-I-M-D）**，让一条指令对多项数据做相似工作。两种架构都有向量计算能力，但具体扩展并不一样：例如 x86 的 **AVX = Advanced Vector Extensions（高级向量扩展，读 A-V-X）**，Arm 的 Neon 或 **SVE = Scalable Vector Extension（可伸缩向量扩展，读 S-V-E）**。

不要假设同架构的每颗芯片都支持所有扩展。软件若要求某个扩展或架构基线，旧芯片可能无法运行；换用另一个架构则可能需要另一个优化实现。新版本操作系统的最低 CPU 要求也可能变化，下载前应核对具体发行版要求。

### 8. GPU、显存和整机升级能力不由 CPU 架构单独决定

**GPU = Graphics Processing Unit（图形处理器，读 G-P-U）** 是另一个计算单元。x86 与 Arm 系统都可能配备集成或独立 GPU，但实际支持由主板、接口、驱动和产品设计决定。

**CUDA（历史全称 Compute Unified Device Architecture，统一计算设备架构，常读“库达”）** 的可用性要检查所支持的 GPU、主机平台与软件组合；不是“有 Arm 就不能使用”，也不是“有 x86 就自动具备”。详见 [[GPU、显存与CUDA并行计算]]。

同样，焊接内存、插槽内存、能否换处理器或增加硬盘，都属于具体产品设计，不能简单说“Arm 都不能升级、x86 都能升级”。

### 9. 厂商模式与成本：架构不是免费开放图纸

Arm 生态中有许可现成处理器设计和取得架构许可后设计兼容处理器等不同方式；这不是说所有厂商使用完全相同的核心，也不是说可以无条件免费制造兼容芯片。[Arm 对架构许可的说明](https://investors.arm.com/node/8361/html)

可以把“遵循同一本规范”和“直接使用同一份核心设计”分开理解。这里讨论架构与许可，不把某家公司的产品范围永久写死。

实际成本包括采购、软件授权、迁移验证、电力、运维和长期支持。已有软件只能在某平台完整运行时，迁移成本可能比硬件价格差更重要。

### 10. Ubuntu 把这些层次连接起来

**Ubuntu（通常读“乌班图”）是一种 Linux 发行版，不是 CPU 架构。** 它有面向 x86-64 和 Arm64 等平台的不同制品。Ubuntu 中 `amd64` 通常对应 x86-64，适用于满足要求的 Intel 或 AMD 处理器；`arm64` 对应 64 位 Arm 目标。

但安装成功还需要启动固件、驱动、设备资源与系统版本匹配。Arm64 手机、开发板、笔记本和云服务器不能被当作完全相同的平台。完整入门见 [[Ubuntu：Linux发行版、软件管理与架构选择]]。

如果只是在学习 Python、Git、网络和数据库原理，先理解这些层次，不必为了学习就立即更换架构或重装系统。只有实际软件或硬件需求明确之后，才需要进行具体平台选择。

## IBM 系列机：为什么体系结构很重要

**IBM = International Business Machines（国际商业机器公司，读 I-B-M）**。在计算机组成/体系结构课程中，“IBM 系列机”常以 System/360、System/370 为经典案例，不是指全部 IBM 产品都用同一种 CPU。

IBM 于 1964 年推出 System/360，重要思想是：让多个不同价位与性能的型号围绕共同体系结构形成兼容家族。用户升级机器时，已有软件投资尽量延续，而不必每次全部重写。

类比同一套电器插头规范：有小功率和大功率设备，但大家遵守共同接口。规范兼容不代表内部元件、吞吐量和价格相同。

System/370 延续并发展了这种兼容思路。这里最该记住的不是型号年份，而是：

> **同一体系结构，可以有不同组成和物理实现；改变实现可以提升性能，而不必改变软件看到的全部约定。**

实际兼容仍受指令子集、操作系统、外设和特定型号能力等约束，不是无条件让任何旧系统原封不动运行。谈兼容方向时用“新机器支持旧程序”等明确描述，比脱离语境只说向上/向下更清楚。[IBM System/360](https://www.ibm.com/history/system-360)、[IBM System/370](https://www.ibm.com/history/system-370)

IBM 大型机体系与 IBM PC 及其兼容机的历史不是同一条线。看到 IBM 不应直接等同于 x86，也不应把所有 IBM 系列归入 Arm。

## CPU 与主板、GPU、OS 怎样配合

CPU 需要主板供电与散热，访问主内存和外设；操作系统利用其权限与调度机制运行进程；GPU 在合适计算任务中提供大量并行处理，仍需要系统软件配合。

**SoC = System on Chip（片上系统，读 S-O-C）** 可以在一套芯片设计中集成 CPU、GPU、内存控制器等多个功能。因此“CPU 和 GPU 职责不同”不意味着它们永远是两张独立板卡。

## 常见误区与学习建议

- CPU 核心数等于程序线程数：不对，需要操作系统调度，硬件线程也不是完整复制一套核心。
- 频率高就一定快：不对，要看工作量与瓶颈。
- Arm 一定低功耗，x86 一定高功耗：不能脱离具体实现判断。
- 同架构意味着同速度：不对，共同指令约定可以有不同实现。
- IBM 系列机就是所有电脑的型号分类：不对，它是特定厂商和历史架构案例。

学习顺序：寄存器与基本指令 → 取指/译码/执行 → 指令集与微架构区别 → 二进制兼容 → 用 IBM 系列机复述共同架构的价值。
