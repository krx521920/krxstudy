# 测试岗面试题库：笔记覆盖与待补清单

> [!summary] 一句话结论
> **已有笔记覆盖了不少计算机、数据库、网络和 AI 原理；这份题库带来的主要缺口，是测试方法、测试工具实操、移动端专项，以及 AI 评测方法。**“知道技术是什么”和“能设计测试、操作工具并分析结果”是两层能力。

## 核对范围与判断标准

- 对照资料：用户提供的《云象序动测试岗面试基础题库.md》，文内标题为“测试岗面试速查手册”。
- 核对日期：2026-11-15。
- 笔记范围：本次整理前，主知识库中的 **149 个 Markdown 文件**，包含索引和日常笔记；排除嵌套的 `krxstudy` 目录、Git 元数据、Obsidian 配置和协作规则文件。
- 方法：检索标题、别名、正文和常见英文名称，回看命中段落；排除 URL、普通英文词和其他含义造成的误命中。例如 Python 的 monkey patch 不能算 Android Monkey 测试已收录，MyBatis 的 `sqlmap-xml` 文档链接也不能算 SQLMap 工具已收录。
- 本页是**覆盖审计与待补清单**，不表示下列教程已经补完，也不表示已安装或使用这些工具。

采用三档判断：

| 状态 | 判断标准 |
|---|---|
| 已有基础 | 有正文解释、例子或相对完整的概念笔记，可以作为学习起点 |
| 部分覆盖 | 仅出现名称、代码示例、短介绍，或只讲原理，缺少题库要求的测试方法 |
| 待补 | 在本次范围内未找到对应讲解；后续新增后需要重新核对 |

不计算一个笼统的“覆盖率”：一道题可能同时涉及网络原理、业务规则、工具和实际经验，不能靠名词出现次数判断会不会。

## 三、最需要补的测试方法

### 1. 测试流程和缺陷管理

- [ ] 需求评审、测试计划、用例评审：分别做什么、产出什么。
- [ ] 需求与用例的对应关系：怎样检查遗漏，而不是承诺“绝不漏测”。
- [ ] 提测准入和上线准出：通过率如何计算，阻塞项和遗留风险如何记录。
- [ ] 缺陷生命周期：新建、确认、修复、验证、关闭、重开。
- [ ] 严重程度与优先级：影响有多大，与应该多快修复，是不同问题。
- [ ] 完整缺陷单、缺陷分布/密度、线上问题复盘与测试报告模板。

现有测试笔记已经讲了范围、用例基础和结果报告；上述内容适合在它附近形成更完整的测试学习路线。

### 2. 测试用例设计方法

- [ ] 等价类划分、边界值分析。
- [ ] 场景法、因果图与判定表。
- [ ] 错误推测、正交试验，以及它们各自适合的条件。
- [ ] 从状态机生成测试：正常迁移、禁止迁移、重复操作和异常中断。
- [ ] 用登录、购物车、文件上传和金额计算做具体练习。

例如“允许购买 1～10 件商品”：不仅测购买 5 件，还应考虑边界两侧、空值、小数、非数字等输入，并写清每一种结果依据哪条业务规则。这类练习比只记“边界值”三个字更有用。

### 3. 测试分类与覆盖方法

- [ ] 黑盒、白盒、灰盒；语句覆盖、分支覆盖。
- [ ] 静态与动态测试；评审与运行测试怎样配合。
- [ ] 系统测试、用户验收测试，以及 Alpha/Beta 的目的和边界。现有环境笔记只对 UAT 有短介绍。
- [ ] 探索性测试、随机测试、模糊测试分别怎样组织。
- [ ] 易用性、用户体验、兼容性、文档、无障碍、适老化、国际化与本地化测试。

### 4. 接口、抓包与自动化方法

- [ ] 接口测试：参数、状态码、响应结构、业务结果和最终数据状态怎样分别断言。
- [ ] 接口关联：把上一步结果传给下一步，管理账号、环境变量和测试数据。
- [ ] Mock：用可控的替代响应模拟外部依赖，包括错误、延迟和超时。
- [ ] 抓包、断点改包、HTTPS 解密代理，以及证书信任的边界。
- [ ] PO（Page Object，页面对象，读 P-O）模式：页面操作和测试业务怎样分开。
- [ ] 数据驱动、Fixture（测试前置资源与清理机制）、`conftest.py`、参数化。
- [ ] 元素定位、iframe、窗口切换、显式/隐式/固定等待；失败截图、日志与报告。
- [ ] 测试独立性、失败重跑与不稳定用例：不能靠不断重试把真实失败掩盖掉。

### 5. 性能、移动端和其他专项

- [ ] 压测场景与数据准备、负载模型、参数化、关联、监控和测试报告。
- [ ] 基准、容量、全链路压测的设计；现有负载/压力/突发/浸泡基础继续复用。
- [ ] 弱网、断网恢复、中断事件、安装卸载升级、机型选择。
- [ ] 移动端耗电、流量、发热、帧率、秒开率和卡顿率的测量口径。
- [ ] Android 崩溃与 ANR（Application Not Responding，应用无响应，逐字母读 A-N-R）的差别及排查。
- [ ] 埋点、数据一致性、资损、防暴力破解、隐私与脱敏的测试方案。
- [ ] 故障注入、故障切换、备份恢复的可复现用例；已有可靠性笔记可作为基础。
- [ ] 精准测试：怎样根据代码和依赖影响选择用例，以及漏选风险。

## 四、AI 测试最明显的知识缺口

已有笔记偏重“模型和 Agent 怎样工作”，本题库增加的是“怎样证明它达到质量要求”。

| 待补主题 | 初学者需要弄清的问题 |
|---|---|
| 评测集、黄金测试集 | 题目从哪里来，如何标注、分层、版本管理，如何防止只对熟悉题目有效？ |
| 意图识别、分域、拒识 | 什么任务应接收、澄清、转交或拒绝，怎么统计误判？ |
| 槽位 Slot | 多轮对话里需要收集哪些信息；修改、遗漏、覆盖和串位怎样测？ |
| 准确率、精确率、召回率、F1 | 各自分母是什么，适合什么任务，为什么不能互相替代？ |
| Recall@K、MRR | 检索是否找全了相关材料，第一条有用材料排在什么位置？MRR 是 Mean Reciprocal Rank，平均倒数排名，逐字母读 M-R-R |
| 幻觉率、忠实度、答案相关性 | 怎样定义“错”，依据是外部事实、给定资料还是业务规则？ |
| LLM-as-a-Judge | 大语言模型充当评委怎样评分，怎样检查评分偏差并与人工结果校准？ |
| Bad Case 与效果漂移 | 失败案例怎样分类积累，版本、数据和用户问题变化怎样影响表现？ |
| 提示注入、越狱和对抗测试 | 安全边界怎样转化为测试集，并检查误拒绝和权限误用？ |
| RAG 分层评测 | 区分入库、切分、检索、重排、上下文组装和生成阶段的错误 |
| 流式专项 | SSE 断流、重连、内容完整性、首 Token 时间和用量对账怎样验证？ |
| 多模态与语音专项 | ASR（Automatic Speech Recognition，自动语音识别）和 TTS（Text-to-Speech，语音合成）的结果怎样评估？ |

ASR、TTS 都按字母读。现有多模态笔记可继续复用，但语音评测和上述具体指标尚未系统展开。

Ragas 官方将上下文召回、忠实度、相关性和工具调用等评测分开，说明“总分高不高”之外还需要检查具体环节。[Ragas 指标目录](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)

## 七、题库中需要纠正或保留条件的说法

1. **Token 不是固定的字数单位。** 它是模型分词器处理的单位，不能固定按一个字或一个单词换算。现有 [[大模型从数据、Token到训练与本地部署]] 已解释这个问题。
2. **修复确认和回归测试应区分。** 前者检查原缺陷是否修好，后者检查改动是否造成其他不良影响。题库“回归验证”的一句话把两者混在一起了。[ISTQB 基础级大纲 §2.2.3](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
3. **探索性测试可以有明确目标、限时安排和过程记录。** 核心是边学习、边设计、边执行和评估，不能简单理解成凭直觉随意点击。[ISTQB 基础级大纲 §4.4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
4. **F1 综合的是 Precision（精确率）和 Recall（召回率），不是 Accuracy（准确率）和召回率。** 中文“准确率”有时被误用，学习时要对照公式和分母。[scikit-learn：F1 定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.f1_score.html)
5. **`conftest.py` 不能简单当成全局配置文件。** 它可按目录共享 Fixture 和本地插件行为，存在目录层级与可见范围。[pytest：Fixture 参考](https://docs.pytest.org/en/stable/reference/fixtures.html)
6. **RS-485 是电气接口标准。** 不能与 MQTT、Modbus 不加区分地视为同一层的业务通信协议；已有 [[边缘计算模块与边缘网关]] 作了区分。
7. **不能仅凭“检索到过资料”就判定错误一定出在模型生成。** 还应检查是否检索到正确版本、是否重排保留、是否完整传入模型，以及资料能否支持答案。参见 [[RAG、Naive RAG与GraphRAG]]；[Ragas 指标目录](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)也将不同评测维度分开。

“第一工具”“大厂标配”“最热”等表述属于题库作者的概括，未作为本次技术结论。题库里的项目数字也只是示例，不能当成自己的实际经历或本仓库的验证记录。

## 八、后续补充顺序

以下是根据本仓库缺口提出的整理顺序，实际深度应结合目标岗位：

1. **先补方法**：测试流程 → 缺陷管理 → 用例设计 → 分类与覆盖。
2. **再补接口实践**：复用 HTTP、登录和幂等基础，补请求、断言、关联、Mock、抓包。
3. **然后补自动化**：测试框架 → 数据和前置条件 → 浏览器/移动端操作 → 报告与持续集成。
4. **根据岗位补专项**：性能、移动端、AI 评测；车载、嵌入式、音视频按岗位要求展开。

优先围绕“登录—选课—进入直播间”这一条熟悉的业务线练习：写需求和用例、记录缺陷、校验接口和数据，再逐步自动执行。这样能把 [[全量测试、回归测试与测试分层]]、数据库、网络和 Agent 评测等已有知识连起来。
