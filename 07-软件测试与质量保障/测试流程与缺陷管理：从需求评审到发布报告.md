# 测试流程与缺陷管理：从需求评审到发布报告

## 一句话解释与生活类比

**软件测试是一套获取质量证据、发现问题并说明剩余风险的活动，不只是点页面找错误。**像装修验收：先明确交付标准，再安排检查、记录问题、复查修复，最后说明哪些合格、哪些还不能交付。

Bug（读“巴格”）常指软件缺陷。实际运行出现的不正确现象是失效；其背后可能是代码、需求、配置或数据中的缺陷。一次报错不能直接证明责任在某个人。

## 一、完整流程怎样连接

```mermaid
flowchart LR
    A[需求评审] --> B[风险分析与测试计划]
    B --> C[用例设计与评审]
    C --> D[准备环境和数据]
    D --> E[冒烟与正式执行]
    E --> F[缺陷定位与修复]
    F --> G[修复确认与回归]
    G --> H[报告与发布决策]
    H --> I[线上观察与复盘]
```

实际项目会反复迭代，不是一次走完的瀑布。需求变化后，测试范围、数据和预期也要跟着更新。

### 需求评审：先把模糊的话问清楚

“用户听课后可以领奖励”还不是可测试的完整规则。应确认：听多久、切后台算不算、同一账号几台设备、资格何时失效、断网如何计时、重复请求如何处理，以及什么证据证明已经到账。

评审产物是明确的规则、待确认问题及负责人。测试人员可以指出矛盾，却不能擅自替业务方发明规则。

### 测试计划：决定资源投在哪里

| 项目 | 教学例子 |
|---|---|
| 对象 | 课程观看资格模块，指定构建版本 |
| 范围 | 登录、权限、观看记录、资格判定；现金到账另用授权环境验证 |
| 风险 | 重复发放、越权、断网计时错误 |
| 方法 | 接口测试、数据库核对、少量端到端场景 |
| 环境和数据 | 预发布、虚构账号、隔离账本 |
| 时间和责任 | 谁准备数据、谁定位失败、何时出报告 |
| 通过条件 | 关键规则全部验证，无未处理的阻断缺陷 |

时间不够时按“发生可能性 × 后果”排序，再考虑覆盖成本；不应只挑最容易通过的用例。

## 二、怎样建立需求与用例的对应关系

追踪矩阵是“每条需求被哪些检查验证”的表。例如：

| 需求编号 | 规则 | 用例 | 结果/缺陷 |
|---|---|---|---|
| R-01 | 未购买不能观看 | C-01 页面进入、C-02 直接调接口 | 通过、失败/B-12 |
| R-02 | 同一资格只能领取一次 | C-03 顺序重复、C-04 并发重复 | 待执行 |

需求覆盖率可以定义为“有测试设计的需求数/纳入范围的需求数”。这只是设计覆盖，不能冒充执行通过率；一条需求有一条用例，也不证明所有异常都覆盖了。

用例字段建议包括：编号、关联需求、标题、优先级、环境、前置条件、输入数据、操作步骤、预期结果、实际结果、状态、证据和缺陷链接。预期要具体，例如“返回禁止访问且数据库没有新增观看记录”，而不是“结果正确”。

## 三、准入、准出与统计口径

**准入**决定是否具备开始某项测试的条件：版本明确、环境可用、基础依赖就绪、数据齐备、必要冒烟通过。

**准出**决定当前验证是否足以支持下一阶段：关键需求已验证、严重缺陷处理、阻塞项说明、报告完整、残余风险有明确负责人。阈值应事先约定，不能失败后临时降低。

例：计划 100 条，通过 80、失败 5、阻塞 10、未执行 5。

- 已执行通过率可定义为 80/(80+5)≈94.1%。
- 计划内通过占比是 80/100=80%。
- 阻塞 10 条不应当作通过。报告必须同时给原始数量和计算口径。

关键权限测试失败，即使总体通过率 99%，也可能阻止发布。质量不是把所有检查等权平均后的一个数。

## 四、缺陷生命周期

常见流转是“新建 → 分析确认 → 分派 → 修复 → 待验证 → 关闭”；复查仍失败则重开。重复、按设计如此、无法复现、延期也可以是处理结果，但需要理由和证据。各团队工具的状态名会不同。

**Resolved（已处理）不等于 Verified（已验证）**。修复者交付改动，验证者确认原问题消失，并检查相关影响。无法复现时先补环境、时间、输入、日志和版本，不能据此直接断言问题不存在。

### 严重程度与优先级

| 维度 | 问题 | 示例 |
|---|---|---|
| Severity，严重程度 | 对业务/数据影响多大？ | 普通用户能读取他人订单，影响很严重 |
| Priority，优先级 | 相对其他工作多快处理？ | 明天活动首页的明显错字，影响较小但可能急需修复 |

冷门功能崩溃是否紧急，还要看使用人群、替代路径和业务时点；不能凭“页面冷门”自动判为低优先级。

### 一张有用的缺陷单

```text
标题：[预发布][课程权限] 未购买账号直接请求播放接口得到有效地址
版本：build-demo-12；账号：测试账号 B；时间：附时区
前置：课程 C 需购买，B 没有订单
步骤：B 登录后请求课程 C 的播放地址
预期：拒绝访问，不生成可用播放凭证
实际：返回有效地址，测试播放器可开始播放
影响：绕过付费资格
证据：脱敏请求、响应、request_id、测试订单查询结果
复现：3 次均出现；仅限本次环境，不外推全部版本
```

只附一张“失败”截图不够。避免把真实密码、访问令牌、身份证和客户订单原文放入缺陷单。

## 五、争议、上线压力与漏测复盘

开发认为“不是问题”时，先对照规则、版本和复现证据。需求不明确则请产品确认预期；依然存在分歧，记录实际影响并由有权承担业务风险的人决策。测试报告负责呈现证据，不负责掩盖风险。

线上出问题先止损、保存证据、恢复服务，再分析：是需求遗漏、设计漏项、环境差异、实现缺陷、发布错包，还是监控没发现。补用例之外，还可能需要补门禁、告警和回滚能力。

缺陷密度通常是“缺陷数/约定规模”，规模可能是代码千行或功能点；不同口径不可直接比较。缺陷多也可能表示发现能力强，而不是质量一定更差。不能用缺陷数量鼓励拆单凑数。

## 六、报告与项目复盘模板

```text
版本、时间、环境、测试范围
计划/通过/失败/阻塞/未执行数量
关键需求验证情况与证据链接
遗留缺陷：严重程度、影响、绕行方式、负责人
没有验证的内容及原因
发布建议：可发布/附条件/不建议，以及理由
后续观察指标、回滚触发条件和复查安排
```

面试可以按“背景—风险—设计—发现—定位—改进—证据”解释自己的真实项目。没有实际数据就说明是练习，不能把题库“耗时从两小时降到十五分钟”变成个人经历。
