# 音视频与语音测试：起播、卡顿、音画同步、ASR与TTS

## 一句话解释与类比

**音视频测试关注声音和画面是否及时、连续、同步；语音 AI 测试还要检查内容是否识别或生成正确。**像看直播课：页面能打开、视频第一帧出现、老师说话能听清和字幕写对，是不同验收项。

## 一、先定义测量起点和终点

| 指标 | 可采用的定义示例 | 需要说明的条件 |
|---|---|---|
| 起播时延 | 用户发起播放到首个可见视频帧 | 是否包含鉴权、广告、自动播放限制 |
| 首音时延 | 发起播放到可听音频开始 | 与首帧可能不同步 |
| 卡顿率 | 播放中等待数据的时间/约定播放时间 | 是否包含首次加载、暂停、后台 |
| 丢帧 | 未按预期呈现的帧数量/比例 | 网络、解码、渲染层含义可能不同 |
| 音画同步偏差 | 相同事件的声音和画面时间差 | 正负方向、采集位置、阈值 |
| 端到端直播延迟 | 现场事件到观众端呈现 | 推流、转码、网络、缓冲全部包含 |

“秒开率”需定义一秒以内完成什么、哪些请求进入分母；只统计成功播放者会隐藏启动失败。不能用 HTTP 接口平均耗时代替真实播放器起播时间。

## 二、如何设计实际场景

先用带时间码、明显声画对应事件的测试素材建立基线，再测试清晰度切换、拖动、暂停恢复、切后台、网络切换、弱网、重连和长时间观看。

固定设备、浏览器、网络条件、编码、码率、分辨率与服务器版本。讲师推流端、分发链路和观众播放器都要保留时间与日志，避免只看一端猜问题。

WebRTC（Web Real-Time Communication，Web 实时通信）有标准化统计接口，可观察对应连接的网络与媒体统计，但字段是否可用及具体口径依实现而定；不能把所有播放器的指标都当成 WebRTC 数据。

## 三、为什么会卡顿或音画不同步

带宽不够可能导致缓冲；网络抖动带来不均匀到达；解码/渲染能力不足也会掉帧。CPU 高、热降频、后台任务和不合适的编码格式都可能参与。

缓冲加大通常有助连续播放，却可能增加直播延迟，因此“更低延迟”和“更少卡顿”需要结合业务权衡。检查同步时还要排除录屏工具和采集设备引入的偏差。

## 四、ASR：把声音识别成文字

ASR = Automatic Speech Recognition，自动语音识别，读 A-S-R。测试集应覆盖口音、语速、噪声、多人交叠、专有名词、数字、静音、短句和长音频。

WER = Word Error Rate，词错误率，读 W-E-R。常见公式：

```text
WER = (替换数 S + 删除数 D + 插入数 I) / 参考文本词数 N
```

参考文本是“请 打开 第一 节 课”，共 5 个词；识别为“请 打开 第二 节 课”，一个替换，WER=1/5=20%。分词规则不同可能改变结果。

CER = Character Error Rate，字符错误率，读 C-E-R，用字符作为单位；中文场景常结合它观察。需要固定标点、大小写、数字写法、空格和文字正规化规则。插入很多词时 WER 可以超过 100%，不能误以为程序一定算错。

还应单独看业务关键字段。例如“15 毫升”错成“50 毫升”，即使总错误率低，后果也可能很大。专业内容的正确性应由对应领域标准和人员确认。

## 五、TTS：把文字合成声音

TTS = Text-to-Speech，语音合成，读 T-T-S。检查读音、数字/单位、多音字、停顿、语速、自然度、漏读重复、截断和首音延迟。

MOS = Mean Opinion Score，平均意见分，读 M-O-S，常见方案让受试者按 1～5 等等级主观评分；评分维度、样本顺序、听音条件和人员必须约定。平均主观分不能代替逐句内容正确性检查。

“今天 12:30 上课，订单号 00123”适合检查时间、前导零和读法。语音助手还要测打断：用户说话后是否停止播放、上下文是否保留、旧合成音频是否错误继续输出。

## 六、多模态与端到端链路

图像、音频和文字组合时，测试缺一种输入、时间错位、过期图片、文字与图片冲突、噪声和跨轮引用。每一层正确不保证整体正确：识别文字错了，后续模型再聪明也可能执行错误任务。

记录原始测试素材、预处理版本、模型、逐层输出、耗时和最终动作；语音记录可能含个人信息，应使用授权素材和必要脱敏。
