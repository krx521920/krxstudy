# 车载测试入门：CANoe、CAPL、DBC、CANape与UDS

## 一句话解释与类比

**车载测试中的这些词分别指仿真测试工具、脚本语言、通信描述文件、标定工具和诊断协议。**像医院：检查设备、医生写的检查流程、化验指标字典和询问病情的格式，不是同一种东西。

ECU = Electronic Control Unit，电子控制单元，读 E-C-U；CAN = Controller Area Network，控制器局域网，常读“坎”。车内多个控制器可以经总线或车载网络交换信息，测试不只看一个软件界面。

## 一、先建立对象地图

| 名称 | 类型 | 核心作用 |
|---|---|---|
| CANoe | Vector 的开发、仿真和测试工具 | 观察通信、模拟节点、组织测试和报告 |
| CAPL | Communication Access Programming Language，通信访问编程语言 | 在相关 Vector 工具中编写事件驱动仿真/测试逻辑 |
| DBC | CAN 通信数据库描述文件格式 | 定义报文和信号怎样从字节转换为工程含义 |
| CANape | Vector 的测量与标定工具 | 观察内部变量、调整适用的标定参数及相关分析 |
| UDS | Unified Diagnostic Services，统一诊断服务 | 测试仪与控制器之间按服务进行诊断交互 |

CAPL 常近似读“卡普尔”，DBC、UDS 按字母读。品牌名称不需要生造全称；CANoe 与 CANape 虽来自同一厂商，定位和工程配置仍有差别。

## 二、DBC 为什么像“字典”

总线收到的是报文 ID 和数据字节。DBC 可以描述哪个报文的哪些位对应车速、温度等信号，以及位宽、字节序、符号、倍率、偏移和单位。

教学例：某信号原始值 1234，倍率 0.01，偏移 0，单位 km/h，则工程值为：

```text
物理值 = 原始值 × 倍率 + 偏移
       = 1234 × 0.01 + 0 = 12.34 km/h
```

如果字节序、起始位或倍率解释错，通信可能没有报错，显示值却错误。DBC 不是实际流量日志，也不是所有厂商全车参数的通用清单，必须与控制器和版本匹配。

## 三、CANoe 的典型工作流程

1. 确认被测控制器、网络类型、接口硬件和授权测试范围。
2. 建立工程，配置通道、通信参数及匹配的描述文件。
3. 在仿真或台架中提供需要的其他节点和输入。
4. 观察报文、信号、时间和错误，运行可重复的用例。
5. 对照预期时序与业务行为，生成报告并保留原始记录。

工具支持范围取决于版本、选件、许可、接口和设备。界面上能看到报文，不表示报文周期、内容、异常恢复都正确。

## 四、CAPL：事件驱动的逻辑

CAPL 具有类似 C 的语法风格，常围绕“收到某报文”“计时器到期”“系统变量变化”等事件执行代码。它不是 Python，也不是在任意控制器中运行的固件语言。

用自然语言描述一个测试逻辑：

```text
准备：仿真输入保持正常
动作：让车速信号从低于阈值变为高于阈值
观察：规定窗口内是否出现对应告警
恢复：输入回到正常值
判定：触发、时间、恢复行为均符合需求
```

实际 CAPL 代码需要工程里真实的报文/信号名称、事件定义和 API，不能脱离 DBC 与配置复制一段代码就声称能运行。对计时检查要考虑采样、总线负载和允许误差。

## 五、CANape 与“标定”

标定是在允许的范围内调整控制策略参数，使设备表现满足目标，例如阈值、曲线和控制增益；通常与测量内部变量配合。它不等于修改源代码，也不等于用万能钥匙改任意 ECU。

测量和标定还涉及对应描述文件、通信协议、访问权限与版本匹配。记录原始参数、修改值、单位和实验条件，才能重现对比。安全相关控制参数应在专门受控环境由具备资质的人处理。

## 六、UDS 的四个常见服务

UDS 用服务标识区分请求。题库中的 10、19、22、2E 通常是**十六进制**，应写成带 `0x` 的形式，不能误读为十进制编号。

| 服务 ID | 名称 | 中文用途 |
|---|---|---|
| 0x10 | DiagnosticSessionControl | 诊断会话控制 |
| 0x19 | ReadDTCInformation | 读取诊断故障码信息 |
| 0x22 | ReadDataByIdentifier | 按数据标识读取数据 |
| 0x2E | WriteDataByIdentifier | 按数据标识写入数据 |

DTC = Diagnostic Trouble Code，诊断故障码，读 D-T-C；DID = Data Identifier，数据标识，读 D-I-D。某个 DID 表示什么、允许哪个会话访问、是否可写，应以设备诊断规范为准。

请求可能得到肯定响应或否定响应；否定码可能表示服务不支持、条件不满足、格式不对或权限不够。诊断服务还受会话、超时和访问控制约束，不是只会发送几个字节就完成测试。

UDS 可以映射到不同传输方式，不能把 UDS、CAN 和诊断工具混为同一层。本文只解释服务职责，不提供对真实车辆写参、刷写或绕过访问控制的操作。

## 七、怎样设计诊断用例

| 维度 | 测试问题 |
|---|---|
| 支持范围 | 声明支持的服务/DID 能否正常工作，不支持时是否正确拒绝 |
| 输入 | 长度、格式、边界值和非法组合是否处理正确 |
| 会话/权限 | 错误会话、权限不足、过期后是否仍能写入 |
| 时序 | 响应是否在约定窗口内，延长等待与超时如何处理 |
| 状态 | 重复请求、重启、断线后状态是否符合规范 |
| 持久性 | 允许写入的数据在重启后是否按设计保留 |

一条读取请求成功不代表整个诊断协议正确；清故障码后没显示错误，也不代表物理故障被修好。
