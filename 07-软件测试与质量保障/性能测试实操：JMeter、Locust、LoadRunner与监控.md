# 性能测试实操：JMeter、Locust、LoadRunner与监控

## 一句话解释与类比

**性能测试用可解释的负载检验速度、吞吐、资源和稳定性，并找出系统何时、为什么不再满足要求。**像测试餐厅：不是把一万人塞到门口，而是说明多少人点什么菜、多久来一批、能等多久，以及厨房哪里开始排队。

并发、QPS（Queries Per Second，每秒查询数）、TPS（Transactions Per Second，每秒事务数）、响应时间和 P95/P99 的原理已有 [[高并发系统：瓶颈分析、扩容与稳定性治理]]。本篇重点讲怎样把它们变成实验。

## 一、不同性能测试回答什么

| 类型 | 要回答的问题 | 示例 |
|---|---|---|
| 基准 Benchmark | 固定条件下的参考表现是什么 | 单实例固定数据量，作为版本对比基线 |
| 负载 Load | 预期业务流量下是否达标 | 常态登录与选课流量 |
| 压力 Stress | 超出能力后怎样退化和恢复 | 逐步增加流量直到触发保护 |
| 突发 Spike | 流量骤增骤减能否应对 | 开课前集中进入 |
| 浸泡/长稳 Soak | 长时间是否出现泄漏和堆积 | 持续运行、观察连接和队列趋势 |
| 容量 Capacity | 在给定目标下能支撑多大规模 | 数据量增长后可保持的吞吐 |
| 全链路 | 实际依赖链在组合负载下怎样表现 | 网关、业务、缓存、数据库、消息系统共同参与 |

这些类型会重叠。“跑了 24 小时”必须同时说明负载、业务比例、设备、版本和错误情况。

## 二、负载模型：先把用户变成可量化行为

教学假设：开课前 5 分钟有 6,000 人进入，每人请求登录 1 次、课程详情 2 次。只考虑这三次请求，平均到达率约 6,000×3/300=60 请求/秒。真实峰值、失败重试和缓存会改变结果，所以不能只用平均数制定容量。

区分四个数量：在线用户、虚拟用户、正在处理的请求、连接数量。一个在线用户可以不发请求，一个页面也可能同时发多条请求。

闭合模型让固定数量用户“请求—等待—再请求”；服务变慢时，发送速率会自然下降。开放模型按到达率发起新请求，更接近某些外部流量场景，但工具和资源必须能维持目标。只看请求完成者的延迟，也会忽略排队和没发出去的请求。

## 三、JMeter 怎样组成一次测试

JMeter 常读“杰米特”，是 Apache 的负载测试工具。HTTP 压测通常发送协议请求，不会像真实浏览器一样自动渲染页面和执行所有 JavaScript。

```text
测试计划
└─ 线程组：虚拟用户数、启动过程、运行时间
   ├─ HTTP请求默认值：测试地址和公共设置
   ├─ CSV数据：每个用户的账号/课程
   ├─ 登录请求 → 提取令牌
   ├─ 查询课程 → 校验字段和业务结果
   ├─ 定时器：模拟等待或节奏
   └─ 结果记录：成功、失败、耗时
```

参数化让不同用户读取不同数据；关联把登录返回的动态令牌传入后续请求；断言检查返回是否真的正确。把同一个账号复制 1,000 遍，可能测试的是账号互踢和热点锁，不能当成 1,000 个独立用户。

先用图形界面调试少量请求；正式受控负载通常用非图形方式运行，并减少耗资源的监听器。对准备好的本地 `.jmx` 计划，常见命令形态为：

```bash
jmeter -n -t demo.jmx -l results.jtl -e -o report
```

`-n` 非图形，`-t` 计划，`-l` 原始结果，`-e -o` 生成报告；输出目录要求和插件兼容需按实际版本确认。运行前必须检查计划中的目标是自己的测试环境，而不是生产或第三方地址。

## 四、Locust 与 LoadRunner

Locust（近似读“洛克斯特”）用 Python 描述用户行为，适合把协议操作和数据逻辑写成代码。示意：

```python
from locust import HttpUser, task, between

class CourseUser(HttpUser):
    wait_time = between(1, 3)

    @task
    def list_courses(self):
        self.client.get("/api/courses", name="课程列表")
```

这里定义行为与思考时间，不包含目标地址、负载规模或业务断言。真实脚本需要设置授权测试主机，并把“HTTP 成功但业务失败”记录为失败。

LoadRunner 是性能测试产品家族，常见工作分为脚本/虚拟用户、场景调度、负载生成和结果分析。它适合需要对应协议、企业集成和已有资产的环境；具体名称、授权、协议包与部署方式应查所用产品版本，不能只凭“收费工具”推断性能更好。

工具的共同任务是产生可控负载与收集证据，不能替代业务建模。脚本录制后仍要处理关联、数据、等待和断言。

## 五、监控要贯穿整条链

| 位置 | 应记录什么 |
|---|---|
| 发压机 | 实际发送率、CPU/网络、是否自身饱和 |
| 入口与应用 | 连接、排队、线程池、错误率、P95/P99 |
| 数据库 | 连接数、慢查询、锁等待、磁盘延迟 |
| 缓存与队列 | 命中率、热 Key、积压、消费速度 |
| 用户端 | 首屏/首帧、卡顿和真实操作成功率 |

ServerAgent 在题库语境下通常指 JMeter Plugins 的 PerfMon 服务端采集组件，用于提供 CPU、内存等资源指标；它不是所有监控代理的统一名称。部署前检查版本与访问控制，采集端口不能随意暴露。

手机性能用 PerfDog、SoloX 等，见 [[移动端测试：ADB、日志、Monkey与性能诊断]]。服务器读数见 [[测试环境排障：Linux命令、资源监控与远程终端]]。

## 六、如何解释结果，而不是只贴一张图

例：吞吐不再增加，P99 上升，数据库连接池等待增加。它支持“连接或数据库可能是瓶颈”的假设，下一步还需检查慢查询、锁和数据库资源；不能立刻把连接数调大作为结论。

每次只改变少量有解释力的变量，重新跑同一负载，保留前后原始数据。缓存冷/热、数据规模、预热和后台任务应可比。不要把每台机器的 P95 简单平均成系统 P95。

报告至少写：目标与阈值、版本/配置、硬件、数据、业务比例、负载曲线、实际吞吐、错误分类、延迟分布、资源曲线、瓶颈证据和未覆盖范围。

全链路测试若替代了支付/短信服务，需要明确“这些真实下游未验证”。若要使用影子流量或隔离数据，必须确保写入、消息和第三方调用不会进入真实业务。

## 常见误区与练习

线程数不是 QPS；HTTP 成功不是业务成功；连接建立不是视频播放；平均延迟不能代表尾部；发压机耗尽也不等于服务端到极限。

先在本地服务用单用户验证业务断言，再逐步加到小规模，观察一张吞吐—延迟曲线，最后尝试长稳和异常恢复。本篇没有实际运行压测。
