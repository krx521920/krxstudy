# 物联网与嵌入式测试：MQTT、Modbus、RS485、OTA与仪器

## 一句话解释与类比

**嵌入式测试需要把代码、通信、电气信号和真实设备行为连起来验证。**像检查温控器：屏幕显示 25℃、传感器真测到 25℃、通信上报 25℃、控制器正确开关加热，是不同环节。

IoT = Internet of Things，物联网，读 I-o-T。先看 [[边缘计算模块与边缘网关]]、[[嵌入式系统为什么经常使用Linux]]。

## 一、先分清层次

| 对象 | 是什么 | 类比 |
|---|---|---|
| RS-485 | 差分电气接口标准 | 道路的物理规则 |
| Modbus | 设备数据交互协议家族 | 车辆交换货物的格式 |
| MQTT | 发布/订阅消息协议，通常经 Broker 分发 | 订阅主题的邮局 |
| STM32 | ST 的微控制器产品系列 | 设备里的小控制中心 |
| OTA | 远程分发和应用更新的机制 | 把新程序送达并安全换班 |

同样接 RS-485 的设备，波特率、地址和上层协议可能不同，不能接上线就认为能互通。Modbus 也不只运行在 RS-485 上。

## 二、MQTT：发布者、Broker 与订阅者

MQTT 通常逐字母读。设备向主题 `demo/room1/temperature` 发布消息，消息服务 Broker 根据订阅分发给订阅者。主题路由与消息内容是两层，订阅成功不说明温度单位正确。

QoS = Quality of Service，服务质量等级，读 Q-o-S。MQTT 的 0/1/2 级分别提供不同交付保证；QoS 1 可能重复，QoS 2 的协议级一次交付也不直接保证跨数据库、业务重试和外部动作的端到端“只生效一次”。

| 场景 | 重点检查 |
|---|---|
| 正常发布/订阅 | 主题、负载、时间、单位和接收者 |
| 重复与断线重连 | 是否丢失、重复，业务是否幂等 |
| Retained 保留消息 | 新订阅者得到的最近值是否被误认为刚采集的数据 |
| 会话与离线消息 | 配置下哪些状态应保留，过期后如何处理 |
| 权限 | 设备 A 不能订阅或发布设备 B 的受保护主题 |
| 异常数据 | 超长、缺字段、类型错误、非法单位能否被识别 |

用两台模拟客户端和测试 Broker，发送带事件 ID/序号的消息，主动断开其中一个，再核对序号和业务状态。Broker 接受了消息，不代表真实电机已执行命令。

## 三、Modbus：寄存器与功能码

Modbus 常近似读“莫德巴斯”。客户端请求读取或写入设备的数据项；常见对象包括线圈、离散输入、输入寄存器和保持寄存器。一个寄存器通常承载 16 位数据，但多寄存器组合成浮点数等解释需要设备文档。

例：设备说明温度保存在某保持寄存器，倍率 0.1。读取原始整数 253，应解释为 25.3℃。必须确认是否有符号、字节/字序、地址基准和单位。

文档写“40001”与报文中地址 0 可能属于不同表示法，不要机械照抄。Modbus RTU 的串行帧和 CRC，与 Modbus TCP 的封装不同；串口参数错、站点地址错和数据解析错应分别排查。

测试有效/无效地址、读写权限、边界值、异常响应、超时与设备重启。读取成功只证明拿到某组字节，不能证明选对了寄存器。初学先在模拟器或无危险输出的练习板上做只读验证。

## 四、RS-485：软件之外的排查

检查线缆、拓扑、收发方向、终端匹配、偏置、接地/隔离和电气条件。具体布线按设备与收发器设计，不能把某一套“两端接电阻”的口诀套到所有现场。

万用表能查看适用范围内的电压、电阻和通断等；示波器显示信号随时间变化，能观察时序、波形和干扰。串口能收到乱码，可能是参数或电气问题，也可能是取错协议层。

测量时仪器量程、输入等级、探头衰减和参考地都影响结果。普通接地示波器的地夹不能随意夹到带电节点，错误连接可能短路；不应断开保护接地来“解决”测量问题。初学只使用已知低压隔离练习电路，并遵循设备手册。

## 五、STM32 与固件

STM32 常逐字母加“三十二”读，是微控制器系列；常见 STM32 MCU 使用 Arm Cortex-M 核心，可运行裸机程序或 RTOS（Real-Time Operating System，实时操作系统）。它不等于一台普通 Linux PC；ST 的 MPU 产品线和具体型号又有不同能力。

典型链路：传感器 → 外设接口 → 固件读取 → 处理与控制 → 通信上报。测试应检查上电初始化、看门狗、异常复位、输入边界、资源消耗和时序要求。

例如断开传感器，设备应报告故障或进入约定安全状态，不能继续把旧值当作当前温度。嵌入式性能也包括截止时间，平均很快不代表每次都能按时响应。

## 六、OTA 升级为什么难

OTA = Over-the-Air，远程更新，读 O-T-A；在工程语境也可包括经有线网络远程更新。流程常包括下载、完整性/签名检查、版本兼容判断、写入、重启、健康确认和回滚。

| 中断位置/异常 | 应核验 |
|---|---|
| 下载一半断网 | 能恢复或重新下载，不执行残缺包 |
| 签名不符/错误型号 | 拒绝安装，原系统可用 |
| 写入途中断电 | 恢复机制符合设计，不只测一次理想重启 |
| 新版本启动失败 | 能回退或进入受控恢复路径 |
| 新版数据迁移后回退 | 旧程序能否理解数据，必要时如何恢复 |
| 重复更新/旧版本包 | 版本策略、防回滚安全规则与业务兼容 |

双分区 A/B 是一种设计选择：写入备用槽，再切换启动并确认健康。但它不是自动安全保证，启动标志原子性、存储损坏、密钥和数据格式仍需验证。不要把“固件回滚”与“所有业务数据一起回到过去”混为一谈。

## 七、台架、硬件在环、外场与耐久

台架是在实验室把供电、控制器、负载和测量设备搭起来。HIL = Hardware-in-the-Loop，硬件在环，读 H-I-L，通常让真实控制器与实时模拟的外部对象形成闭环；并非任何接了一块板子的测试都自动具备 HIL 的含义。

外场/实车检查真实环境，耐久测试关注长时间或大量循环后的磨损与退化。各层互补：仿真覆盖边界，台架便于控制，外场验证真实条件；机械寿命循环和软件浸泡测试的目标并不完全相同。
