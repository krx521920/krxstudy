# 数据专项测试：埋点、资损、隐私与一致性

## 一句话解释与类比

**数据专项测试检查系统留下的业务事实和统计记录是否可信，尤其关注少记、多记、错记和不该泄露的信息。**像快递签收：按钮被点了、包裹真的送到、财务记账和统计报表，是几条相关但不同的记录。

## 一、埋点是什么

埋点是应用在特定事件发生时记录结构化数据，例如进入课程、开始播放、播放失败、点击报名。它可以用于产品分析、体验监控或业务核对，不等同于所有调试日志。

事件先定义契约：

```json
{
  "event_name": "course_play_started",
  "event_id": "demo-event-001",
  "course_id": "demo-course-42",
  "session_id": "demo-session",
  "schema_version": 1
}
```

还应按需求定义事件时间、接收时间和必要环境信息。示例是虚构标识，真实埋点应尽量减少个人数据。

“播放开始”应该是用户点击按钮、播放器准备完成，还是第一帧真正显示？这必须先定义。不同团队采用不同含义时，报表数字无法比较。

## 二、怎样测试埋点

| 检查层 | 具体问题 |
|---|---|
| 触发 | 成功一次是否触发一次，失败有没有独立事件 |
| 内容 | 名称、类型、必需字段、版本、业务 ID 是否正确 |
| 发送 | 离线缓存、恢复重传、批量上报是否丢失或重复 |
| 接收 | 校验失败是否记录，限流和超时怎样处理 |
| 加工 | 去重、时区、会话划分、机器人过滤是否符合规则 |
| 报表 | 统计窗口和分母是否正确，是否等待加工完成 |

用固定测试会话执行 3 次开始、1 次失败，核对客户端原始事件、服务接收记录和最终报表。不能只看到网络请求成功就说报表准确。

重复上报可能是网络重试，应按事件 ID 等约定处理；但不同真实播放不能因为内容相同被误合并。客户端时钟可能不准确，需要同时考虑事件时间与接收时间。

## 三、资损测试：检查资金与权益不变量

资损指可能造成资金损失的业务问题，不限于支付接口报错。金额精度、优惠叠加、退款、重复回调、并发领取、库存和权益不同步都可能引发损失。

先写不变量，即任何有效操作后都必须保持的规则：

- 同一业务请求的有效入账次数符合规则。
- 模拟账本借贷或来源/去向可核对，不能凭空多出金额。
- 实际发放不超过已授权额度，退款不超过可退余额。
- 用户只能操作自己的订单，后台权限按角色限制。

这些规则应由业务确认，不能把教材的简化公式代替正式财务口径。

### 模拟奖励领取的测试矩阵

| 情况 | 需核验的结果 |
|---|---|
| 连续重复同一请求 | 只产生约定的一次有效权益/账本变化 |
| 同时重复请求 | 原子性保证，没有并发穿透 |
| 返回超时后重试 | 能查原请求结果，不盲目创建第二笔 |
| 同键不同金额 | 按契约拒绝冲突，不能偷偷复用错误结果 |
| 失败回调与成功回调乱序 | 状态符合事件规则，可追踪和补偿 |
| 重复退款、部分退款 | 累计额度与原交易匹配 |

测试使用模拟账本和隔离凭据，不需要真实发钱。幂等设计见 [[状态机与幂等性]]，接口侧方法见 [[接口测试与抓包：Postman、Apifox、Mock和HTTPS代理]]。

## 四、隐私、脱敏和加密是不同措施

脱敏展示如手机号只显示末四位；加密保护存储或传输中的内容；访问控制决定谁有权读取；删除/保留策略决定信息存在多久。做了其中一种，不代表其他问题自动解决。

检查同一敏感字段是否出现在页面、接口、URL、浏览器缓存、日志、报错堆栈、截图、导出、备份和分析平台中。页面打星但接口返回完整数据，仍需按实际权限与用途判断暴露范围。

日志可记录业务 ID、错误分类和必要上下文，避免完整密码、会话令牌、密钥。测试报告自身也要脱敏。合规要求取决于实际地区和业务，具体法律判断应另外核实，本篇只讲技术验证。

## 五、一致性验证需要时间窗口

同步交易与异步同步的预期不同。对允许最终一致的事件链，定义“什么时候应该一致、超时怎么办”；同时验证消息重复、乱序、延迟和消费者重启。

例：订单完成后积分允许在约定窗口内到账。应持续查询到完成或超时，核对只发一次；不是睡固定两秒后看一眼，也不是无限等待后宣称成功。
