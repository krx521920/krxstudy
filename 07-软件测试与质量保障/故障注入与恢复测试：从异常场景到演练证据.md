# 故障注入与恢复测试：从异常场景到演练证据

## 一句话解释与类比

**故障注入主动制造受控异常；恢复测试验证系统能否按承诺恢复服务和数据。**像消防演练：不仅让警报响，还要验证探测、疏散、应急通道和事后恢复。

先看 [[高可用、健康检查与故障恢复]]。本篇是设计方法，没有对真实服务执行断网、断电或重启。

## 一、四种相关但不同的检查

| 检查 | 目标 |
|---|---|
| 故障注入 | 制造延迟、超时、进程退出、资源限制等输入条件 |
| 容错 | 依赖出问题时能否限流、降级、拒绝不安全操作 |
| 故障转移 Failover | 主服务失效后是否转向可用副本，状态是否正确 |
| 恢复 Recovery | 服务、数据、队列和业务是否回到可接受状态 |

“容器自动重启”只解决其中一小部分。它可能启动但无法读数据，或不断重启而不能工作。

## 二、先写假设、边界和停止条件

教学假设：“课程推荐服务超时，不影响用户查看已购课程。”

先确认测试环境、受影响范围、允许的持续时间、负责人、恢复动作与停止阈值。正常状态下先记录可用性、延迟、错误和数据，然后只对指定依赖施加异常。

若超出约定范围、关键数据异常或恢复手段失效，应结束注入并恢复。演练需要可控和可撤销，不应把“制造更大故障”当成验证更充分。

## 三、场景表怎样写

| 故障 | 预期保护 | 需要证据 |
|---|---|---|
| 某下游慢 | 有限超时，不耗尽所有工作线程 | 超时记录、线程/连接池、无关接口延迟 |
| 缓存不可用 | 按设计回源、限流或明确失败 | 数据库负载、错误率、最终结果 |
| 消费者短暂停止 | 消息可恢复处理，重复消息不重复入账 | 队列深度、消息 ID、账本 |
| 单实例退出 | 新请求转到健康实例 | 路由、健康检查、错误窗口 |
| 资源配额不足 | 明确告警和拒绝，不静默丢失数据 | 容器/运行时日志、数据校验 |
| 凭据过期 | 认证失败可识别，不自动绕过权限 | 认证日志、阻止操作的证据 |

故障位置也重要：客户端发出前、服务接收后、写库提交后、回执发出前产生超时，业务结果可能完全不同。

## 四、恢复要看数据，不只看页面

RTO = Recovery Time Objective，恢复时间目标，读 R-T-O；RPO = Recovery Point Objective，恢复点目标，读 R-P-O。前者说明恢复时长要求，后者说明可接受的数据丢失时间范围。目标值要由实际业务制定。

测量时先约定起止点：从故障发生、检测到还是开始恢复计时；恢复到进程启动还是关键业务可用。不同起止定义得到的数字不可直接比较。

恢复演练流程：取得备份 → 在隔离环境恢复 → 验证数据库结构/数量与关键记录 → 检查关联、权限和实际业务 → 核对丢失/重复窗口 → 记录耗时与失败步骤。

备份文件存在、校验和正确或恢复命令返回成功，都不能单独证明业务恢复成功。旧密钥、对象存储、配置和依赖也可能是恢复必需品。

## 五、失败重试与雪崩

下游故障时所有请求立即重复三次，可能把压力放大；无限队列只会推迟崩溃。应验证重试上限、退避与抖动、总时限、取消传播和幂等边界。

系统恢复后，积压会同时释放，应观察恢复流量是否再次压垮数据库。测试不仅看故障中的最低点，也看从故障恢复后的几分钟或更长约定窗口。

## 六、一份演练记录

```text
假设：推荐依赖超时不影响已购课程查询
版本与环境：明确构建、配置、测试数据
正常基线：查询成功率、P95、依赖调用量
注入：指定依赖增加延迟，持续时间按计划
观察：降级提示、无关接口、线程池与错误分类
恢复：撤销延迟，确认指标和业务恢复
数据核验：没有重复操作或状态丢失
结论：支持/不支持假设；证据、限制和改进项
```

这里没有填虚构的成功数字；练习时用自己的实际结果填写。
