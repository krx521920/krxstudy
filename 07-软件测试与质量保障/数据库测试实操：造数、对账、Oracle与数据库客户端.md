# 数据库测试实操：造数、对账、Oracle与数据库客户端

## 一句话解释与类比

**数据库测试检查业务操作最终留下的数据是否正确、完整、一致且可恢复。**像核对收银小票和账本：屏幕显示付款成功只是一个信号，还要检查账本记了几次、金额和归属是否正确。

SQL（Structured Query Language，结构化查询语言，常逐字母读 S-Q-L）基础已在 [[SQL与关系型数据库学习地图]]。本篇将它用于测试，而不是重讲查询语法。

## 一、SQL 在测试中的四种用途

1. 准备初始数据：空账户、边界余额、过期课程、不同角色。
2. 验证最终状态：订单、库存、账本和关联记录是否符合规则。
3. 排查异常：用请求 ID、业务 ID、时间连接日志与数据。
4. 清理与恢复：只回收本次创建的对象，保留失败证据。

绕过接口直接插入数据可能漏掉业务校验、事件和缓存更新。因此业务流程测试优先使用正式测试接口或明确的造数工具；直接 SQL 造数适合已理解表结构与约束的受控环境。

## 二、一组可核验的对账例子

假设有 `orders(id, user_id, paid_cents)` 与 `order_items(order_id, price_cents, quantity)`。金额以整数分存储，避免把浮点误差误当成业务差额。

```sql
SELECT o.id, o.paid_cents,
       COALESCE(SUM(i.price_cents * i.quantity), 0) AS items_cents
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.id
GROUP BY o.id, o.paid_cents
HAVING o.paid_cents <> COALESCE(SUM(i.price_cents * i.quantity), 0);
```

这条教学查询找订单实付与明细合计不一致的记录。真实业务若有优惠、运费、税或退款，必须加入正式公式；不能用简化公式直接认定真实订单错误。

检查重复业务键可以使用：

```sql
SELECT request_key, COUNT(*) AS copies
FROM payment_events
GROUP BY request_key
HAVING COUNT(*) > 1;
```

它检查表里同键的记录数；系统也可能允许多条尝试记录，但只有一条生效，届时应按状态和账本记录核对。重复日志不等于重复扣款。

“每部门工资前三”要先确认是恰好三名员工还是前三个工资档次：前者可用 `ROW_NUMBER()` 加确定性并列排序，后者可用 `DENSE_RANK()`。已有 [[SQL窗口函数：排名、累计与同期比较]] 继续提供语法和示例。

## 三、造数与清理怎样可重复

为一次运行分配 `run_id`，生成独立账号和业务 ID；保存创建清单。测试结束按归属清理，有外键时考虑依赖顺序。不要用“删除所有测试用户”这种过宽条件。

事务回滚能隔离某些数据库测试，但异步任务、另一个连接、外部消息、对象存储和真实接口可能已经提交副作用，不会随当前事务一起撤销。

数据集要包含正常、空、极值、重复、失效和权限不同的记录。复制生产数据需要合法授权与脱敏；虚构数据更适合初学练习。种子固定有利复现，但敏感标识不能通过可预测种子生成真实凭据。

## 四、页面、接口、数据库、缓存不一致怎么办

按相同业务 ID 比较：页面展示 → 接口响应 → 应用处理 → 权威数据库 → 缓存/只读副本。还要记录时间，因为异步流程可能有约定的可见延迟。

强一致性业务不能用“最终会一致”搪塞；允许异步的业务则应定义可接受窗口，并检验超过窗口后的重试、告警与补偿。只查询副本可能读到旧值，不能立即判定写入失败。

对缓存分别测试命中、失效、更新、并发读写和缓存不可用。Redis 的穿透/击穿/雪崩原理见 [[Redis缓存与分布式协调]]，测试时要观察数据库压力与保护行为，而不只看缓存键是否存在。

## 五、Oracle 与 MySQL 等环境的测试差异

Oracle Database 是数据库产品，Oracle 公司也维护其他产品；它不等于 MySQL。已有产品定位见 [[SQLite、SQLCipher与PostgreSQL]]。

| 差异点 | 对测试的影响 |
|---|---|
| 字符串与 NULL | Oracle 文档所述空字符串处理可能不同，需专门验证空、空格和 NULL |
| 时间类型/时区 | `DATE`、时间戳精度和会话时区需要统一解释 |
| 分页与函数 | LIMIT、FETCH、字符串/日期函数可能不通用 |
| ID 生成与约束 | 序列、标识列及事务行为依产品和版本确认 |
| 事务和 DDL | 建表/改表可能有隐式提交，不能假设都能回滚 |
| 执行计划 | 估算计划与实际执行统计不同，观察工具各异 |

移植测试时，复用业务预期，分别适配数据库语法和事务假设。少量数据查询很快不能代表百万行也快；性能排查先证据，再看索引、统计信息、锁等待和计划。

## 六、Navicat 与 SQLyog

Navicat 是数据库客户端产品系列，不同版本支持不同数据库；Premium 等多库产品不等于所有产品都支持所有数据库。SQLyog 主要面向 MySQL 的图形化管理与开发。

客户端像遥控器，数据库是存数据和执行 SQL 的服务。连接需要主机、端口、账号、数据库/服务名及相应加密设置；装了客户端不会自动获得数据权限。

操作练习：新建只读测试连接 → 明确环境标签 → 打开查询窗口 → 查询限定 ID 的数据 → 查看执行计划 → 导出脱敏结果。执行 UPDATE/DELETE 前先用同条件 SELECT 核对影响范围，并按环境规则准备恢复；本篇不提供针对真实库的清理命令。

## 常见误区与练习

“数据库里有一条记录”不代表关联、金额、权限和状态都正确；“数据相同”也要考虑空值、时区、排序和精度。先在隔离练习库创建订单与明细，再有意制造一条金额不一致记录，用上面的查询找出来。
